# The tower

The workkit dashboard: mission control over everything the workflow system already knows — the cross-repo issue board, the live Claude crew and what it costs, per-repo health, and the daily brief. It carries two deliberate write paths: the intake dialog, which files a `status:inbox` issue, and the Board's drag, which moves an issue between the status columns. A view, never a second store: remove the tower and nothing is lost.

It is two processes. `tower/api/` is a plain-Node JSON API with zero dependencies, and `tower/app/` is the dashboard, an OMEGA app that reads it. They are split because the framework owns the chrome — the shell, the sidebar, the routing, dark mode — and hand-writing a second copy of all that was the thing v2 stopped doing.

## Run

One command, both halves (issue #97):

```sh
workkit tower    # the API on http://127.0.0.1:8693 + the dashboard on https://localhost:4300
```

`npm run tower` from the checkout root is the same thing, and `npm start` is its alias (issue #178) — all of them run `tower/start.sh`. Running it RESTARTS the tower: anything already listening on either port is a previous instance and is replaced, with a line saying so — the ports belong to the tower, and a leftover server should never make the fresh one die on the address being in use.

`tower/start.sh` starts the API and the dashboard's dev server together; one interrupt ends both, and either process ending takes the other with it. Each half can still be run alone (`node tower/api/server.js`, or `npm run dev` inside `tower/app`) when only one is wanted.

It is QUIET THROUGH STARTUP (issues #138, #158, #170): whoever typed the command asked for a dashboard, not for the framework's boot wall. It opens with `tower: starting the dashboard…`, so the quiet is never a terminal with nothing on it, and both halves then run filtered to the lines that read like a problem — error, warn, fail, fatal, exception, `EADDR`, a missing module, binary, file or permission, a signal, an `npm ERR!`, a port that was taken, stack frames — plus every line carrying omega's own `omega: ` prefix, which is the framework speaking as itself, and plus one `tower: dashboard at <url>` line once the app announces itself. That prefix is kept because a boot omega REFUSES is worded with none of those problem words ("the monorepo src-to-dist watch is not running", "dist is not built"): the whole refusal, remedy included, was dropped, and the run ended on a terminal that had said only that it was starting. Its benign prefixed notes now ride in beside its refusals, which is the price of taking the prefix at its word — one line each, against a swallowed refusal. The PHASE BOUNDARY for the app half is the first line omega tags `[web]` at column 0, the tag it puts on everything it forwards from the web target: before it is the manage cycle nobody asked for, after it is the dev server itself — its mkcert and asset lines, then the requests and rebuilds, which is the running log of the thing the terminal is now watching. The URL announce opens the phase too, whichever lands first, which is what this falls back to if that tagging ever changes; the manage cycle's own bracketed lines (`[11ty] Wrote…`) are why the trigger is that one prefix rather than any bracket. The API half owns no port, so neither trigger applies and it stays filtered for its whole life. Across both phases a drop list takes out known-benign lines whose wording would otherwise read like a problem: the macOS duplicate-library `objc` warning, and the omega manager's `Results:` summary when it says `0 failed` — one with real failures still prints. That URL is READ off the app's own line rather than composed, and matched at whatever port that line names rather than the one the tower asked for, because neither is fixed: omega serves https when a mkcert pair exists and plain http when it does not, and it takes the next free port when its own is busy; a trigger line is judged in the phase it OPENS, so the app's own URL line prints as itself with the announce standing beside it. A half that ENDS before that announce never came up, so the run says which one did — `tower: the app half ended before the dashboard came up` — and points at `npm run tower -- --verbose` for the rest of what it printed, since a filtered run has by definition shown less than the whole of it. A tower taken down from the outside after its announce is an ordinary shutdown and says nothing. It is quiet but not COLORLESS (issue #179): each half writes to a fifo, so omega's logger sees a non-tty and paints nothing, and the terminal ends up with plain text the tower never stripped — so when the tower's OWN stdout is a terminal it exports `FORCE_COLOR=1` into both halves, leaving a run that is piped or redirected plain and a `FORCE_COLOR` its caller exported untouched, a deliberate `0` included. Those escapes land on the very anchors the filter matches, so every pattern is judged against a color-stripped copy of the line and the ORIGINAL is what prints; the lines the tower composes itself — the announce, the one naming a half that ended — carry no color of their own. `--verbose` passes everything through unchanged, from the first line — `workkit tower --verbose` reaches this script — and `WORKKIT_TOWER_VERBOSE=1` is the same door for callers that pass no arguments.

The API answers on its own and is useful without the dashboard. The 9am job does not read it over HTTP — `jobs/brief-payload.js` composes the same payload from the same libs, so nothing has to be running at nine in the morning. The dashboard needs the API; with it down, every pane says so in a line and the page still draws.

| Knob | Default | Meaning |
|---|---|---|
| `TOWER_PORT` | `8693` (TOWER on a phone keypad) | listen port |
| `TOWER_BIND` | `127.0.0.1` | bind address — keep it loopback; front it with Tailscale for the phone |
| `TOWER_ALLOW_HOST` | (empty) | comma-separated extra hostnames the Host and Origin gate admits — put the tailnet name here |
| `KEEP_AWAKE_IDLE_MINUTES` | `45` | when a quiet session counts as idle, matching the keep-awake hook |

The dashboard finds the API at `http://127.0.0.1:8693`. Two overrides, neither needing a rebuild: `?api=http://host:port` in the URL, which points one link at another machine's tower, and `window.TOWER_API` from the console.

### The three modes

The app knows what is on the other end of it, and the answer is one of three. `omega dev` bakes `environment: development` into the page and a production build bakes `production`, and either override above points a page at a tower whatever the build says. So: **tower** — a machine's API, everything the dashboard has ever done, including its two write paths; **github** — a published copy holding a token, reading GitHub itself; **locked** — a published copy with no token, which is the page shell with the Settings page in it. The decision is made once, in `libs/tower/api.js`, and exported as `MODE` — with `LIVE` meaning "a tower", the question of which half answers, and `WRITABLE` meaning "anything but locked", the question every write gates on.

**The token is the key, and the auth.** A published copy bakes no data at all: every issue, count and summary is a live GitHub call made by the browser (issue #81). What unlocks those calls is a fine-grained personal access token the viewer creates and types in — Issues: Read and write, Metadata: Read, Discussions: Read, on the repositories the board covers, plus Contents: Read on the home repo, which is where the list of those repositories lives (issue #110). It writes because the site MANAGES those issues rather than displaying them: a card is dragged between columns and the dialog files one, exactly as on the machine. It is stored in that browser's localStorage and nowhere else: not in the repo, not in the build, not in a URL, and it is sent to `api.github.com` and to nothing else. **Where it is handed over is the Settings page** (issue #167): `/settings`, in the sidebar under the six views, and the one page that works with no token at all - because it is where one is typed. It owns all of it: the field, Save, Clear (the forget that used to be a Token button in every page's chrome), the permissions above, and the note that a classic token with the `repo` scope works too and is the only kind that does when the board spans two owners, since a fine-grained token belongs to a single resource owner. A copy reading a tower is told there that the machine holds the `gh` login and this copy needs no token of its own. Landing anywhere else without one routes to Settings, and the page that was asked for says the one true thing about itself on the way: a line pointing at Settings, in place of data it cannot load. A token GitHub refuses - expired, or not covering these repositories - is carried the same way: the reason rides the runtime's state to Settings, where it is drawn in the card's own alert, and every other page shows it in that same pointer line. There is no dialog any more. The prompt used to be a modal that could not be dismissed - no backdrop dismiss, no Escape, no close button - because behind it was a page with no data and no second place to type a token; the second place is now a page, so the modal is retired from the layout entirely. A viewer with no token sees no data, which is what makes the token the whole auth layer - and a real login can replace it later, since the page only ever needs the string handed over. The one place that ask is WRONG is this machine (issue #89): a locked page served from `localhost`, `127.0.0.1` or `[::1]` has no use for a token, because the tower API holds the `gh` login. It says the tower is not running or not connected, and gives the two steps that actually resolve it — `npm run tower`, then a link to this same page with `?api=http://127.0.0.1:8693`, since the mode is decided from the build and no reload alone will change it. The topbar's intake dialog says the same thing rather than asking for a token. That notice IS the page body there, and nothing routes anywhere - Settings is the one exception, since a viewer who opened it asked for it. The fork is `isLocalHost()` in `libs/tower/token.js` — read by the runtime for the body and by `lockedIntakeNotice()` for the dialog, on the hostname alone; the mode is untouched.

**What works off-machine, and what does not.** Overview, Board and Brief read GitHub through `libs/tower/github.js`, which answers in the same shapes the API serves — `/api/repos` from the roster read off the home repo (the public `data/home.json` says which repo that is; the list itself is private), `/api/board` from the same GraphQL sweep — one shared module (`libs/tower/sweep.js`) rather than a second copy of the tower's (issue #195), since the sweep's pure half has no transport in it and the app's side of the copy boundary is the side that travels — `/api/brief` from that sweep plus the summaries published as Discussions on the home repo. Crew, Usage and Health read this machine — its processes, transcripts and working copies — so a published copy says exactly that instead of drawing an empty page, and so do the Overview's crew and health panels. It WRITES the same way: the Board's drag and the intake dialog reach GitHub with the same token, through the same two paths the tower has — a move is the issue's labels read and written back with the old `status:` off and the new one on (one PATCH, so it is never unlabelled nor twice-labelled), and an intake is `POST /repos/:slug/issues` carrying `status:inbox` and `type:idea`. Both carry the endpoint's own refusals, made before anything leaves the browser — a blank title, an over-long body or a repo the site does not sweep for the intake; a number that is not a positive integer, a repo that is not a slug, a status the vocabulary does not define or a move to where the issue already is for the move — and the move refuses one more the endpoint cannot meet: a read that answered without the issue's labels is no base for a whole-set PATCH, so nothing is written. They speak REST where the reads speak GraphQL, because a mutation addresses a label by node id and REST speaks label names. A token that can read but not write is told so in those words, in place of the move it refused; a token that cannot see the repository at all is told THAT instead, since the two legs of a move fail for different reasons. Only a LOCKED copy writes nothing, and it says the one thing that fixes it: add a token.

A published copy is otherwise unchanged: every page keeps its mount, its sidebar and its topbar, and a page pointed at a tower with `?api=` runs fully live against it. It is served a path DEEPER, though, unless a custom domain says otherwise — `<owner>.github.io/<name>/` — and the build mounts only the URLs it emits itself. The ones this app assembles while it runs are its own: the Settings redirect a tokenless landing takes, the nav rewrite that carries `?repo=` from page to page, the tiles and see-all lines that point at the Board. Every one of them goes through `sitePath` in `libs/tower/scope.js`, which reads the prefix back off the `data-omega-path-prefix` stamp the build leaves on the page (issue #169) — a root-served copy carries no stamp, so nothing moves.

**Where a published copy comes from.** This app is also the SEED of the home repo: `workkit setup` copies it into `~/.workkit/tower`, where it becomes a project in its own right, and `workflow/publish.sh` builds THAT clone and pushes the output to the home repo's `gh-pages` branch, which GitHub Pages serves from the branch root (issues #27, #77) — the daily job after the morning brief, or `workkit publish` on demand. So nothing built is ever committed as source. The seed is a ONE-TIME write, so every publish first SYNCS the clone back from this folder by content and then MINTS its brand assets at the clone's brand root when the sync changed something, when the clone has never minted, or when the last mint failed (issue #129): without the sync a change made here reached the published dashboard only on a future fresh seed, and without the mint a freshly seeded clone published a broken logo, since `.omega` is one of the trees the seed leaves behind while the sidebar and the social tags reference the minted paths unconditionally. A mint that fails aborts the publish rather than building over it. That is also why a ship whose diff touched this folder republishes: the `workkit:ship` skill runs `workkit publish` after the release commit's CI is green, with the daily 9am publish as the backstop. The build runs in `targets/web` rather than at the brand root, because `omega build` is a command of `@omega.js/web` and the root's `omega` bin is the manager's (probed 2026-07-29). The build is LOCAL, never CI: the app consumes `@omega.js/*` by `file:` spec from a sibling omega checkout that no runner has, and on a machine without it `npm install` exits 0 while leaving nothing that can build, so the publish checks for the `omega` binary and skips cleanly rather than trusting an install.

Alongside the pages it writes exactly one file: `data/home.json`, which names the home repo and the branch of it the roster is on, and nothing else — safe to serve to anyone, since the site is served FROM that repo and its own URL already says so, and a branch name says nothing more once the repo is known. The branch is CARRIED rather than assumed (issue #112): the publish pushes whatever branch the home clone is on, and a page hardcoding `main` reads a 404 on a home repo whose default branch is not — a site published before that key existed still falls back to `main`. The ROSTER — `data/repos.json`, the `owner/name` slugs the site sweeps plus `home`, the repo its summaries are read from (`workflow/site-repos.js`, from the same roster the tower and the brief read) — goes to the home repo's DEFAULT branch instead (issue #110): Pages is public even when the repo serving it is private, and repo names are private when the repos are. The page reads it back through the GitHub API with the viewer's own token, at the branch the pointer names, which is why that token needs Contents: Read on the home repo. Neither file carries a timestamp, so an unchanged roster produces no commit on either branch. Whether anything publishes at all is `site.publish`, default off — and off takes an already-published site DOWN rather than freezing it (issue #113), while the roster keeps refreshing either way (issue #111).

### Phone access

Nothing listens beyond loopback. Put Tailscale in front and allow its hostname:

```sh
TOWER_ALLOW_HOST=<mac-name>.<tailnet>.ts.net npm run tower
tailscale serve --bg http://127.0.0.1:8693
```

## Who may reach it

The bind keeps other machines out. It cannot keep other PAGES out — any site can resolve a name it owns to 127.0.0.1 and reach a localhost listener — so the Host header is checked against an allowlist on every request, and a request carrying an Origin must carry one from that same allowlist.

CORS falls out of that one list. An allowed origin is echoed back in `Access-Control-Allow-Origin`, never `*`, with `Vary: Origin`; the preflight the page's POSTs trigger is answered with the methods, the headers and a ten-minute max-age — one answer covering both write paths, because a preflight is about the method and the headers rather than the path. The dashboard reaches the API exactly because `localhost` is already a name the tower answers to. A page this tower does not answer to gets a 403 for the whole surface — no header, and no data either.

## The pages

The app is an OMEGA brand root whose one app is the dashboard. The framework supplies the shell; the tower supplies the nav as a JSON file, one page per view, and a page module per page that draws from the API. It is also a BRAND in the omega sense (issue #53): one authored mark at `assets/logo/brandmark.svg` and one hex in `config/omega.json5` (`brand.color`), from which the assets service mints the sidebar mark, the favicons, and the social image, and the theme composes both modes' accent ramps.

| Page | What |
|---|---|
| **Overview** | the control room: a statgrid row (open, blocked, QA, in flight, live sessions, unpushed, unreleased), what is waiting on you, the live crew compact, health at a glance worst-first, and the queue by status as a doughnut. Each list stops at five with a line to the page that holds the rest, every tile and panel head points into the page that owns the depth, and each pointer carries the sidebar's repo scope (issue #183) — a narrowed tower stays narrowed on click. Under it, the board over time (issue #55): the open queue by status, closed per day, and inbox depth as charts, with a week-over-week line under the issue tiles — all read back off the published briefs, so they say why they are empty until two mornings have gone out. These charts' one home is this page (issue #177). Above the tiles it draws a line per repo that has something to say about the sweep itself: what went wrong reading it, that its issues are still arriving — "loading 100 of 340 open issues", the framework's inline wait, which clears as the last page lands (issue #194), on the machine and in a published copy alike — or that the sweep stopped at the ceiling with open issues it is not showing |
| **Board** | the full issue board — columns by `status:` in two regions (issue #196), filters for type, priority, assignee and `agent:ok`, all repos or one. The PIPELINE is the five stages in stage order — inbox, specced, building, qa, complete — read left to right as a flow; the SIDE POCKET beside it holds `blocked` and `backlog`, set apart in a card of its own because they are states of waiting rather than stages of progress. Both groups are cards drawn behind their lanes; every lane on the board is one width and every header on one line, and neither card wears a caption (issue #203). Which lanes are which is the vocabulary's own `pocket` flag, so the page holds no second list of statuses. A card is dragged into and out of a pocket like any other lane. A blocked card carries no line the others do not (issue #205): its OPEN QUESTION is in the dialog the card opens, not on the face of the card. A column reads in three priority bands — `priority:high`, then the unlabelled middle, then `priority:low` — most recently touched first inside each, so the top of a column is what to pick up next. Every card is one size, its title clamped to two lines; the whole title is in the dialog it opens. A card is DRAGGED between the status columns and the drop really relabels the issue: it moves at once, and a write that fails puts it back and says why. An open issue carrying no `status:` label has no column — that is a fault the pipeline forbids, not a place an issue lives — so it is named and linked in a danger alert above the board and appears nowhere else: no card, no column count. The board's one line above the lanes says "showing X out of Y" (issue #203): how many the filters let through, out of how many the board holds in all; the project selector owns the scope. A card also says what its issue is WAITING on (issue #103): a muted "waits on #12" chip in its chip row for each blocker the sweep is still carrying — the short form for a blocker in the same repo, `owner/repo#12` for one anywhere else — drawn only while that blocker is open, since a dependency on a closed issue is satisfied. Those dependencies are also a PICTURE: the `List | Graph` toggle in the toolbar, held in `?view=` beside the filters and narrowed by the same repo scope, swaps the columns for the graph of what waits on what — only the issues in a dependency, an arrow from each blocker to the issue it unblocks, its status on the node, and a dashed node for anything the board is not showing rather than an edge quietly dropped. The picture itself is mermaid text composed by `libs/tower/graphdef.js` and drawn by the framework's graph module. A board with no dependencies at all says so instead of drawing an empty diagram. It is a reading and not a surface: cards are dragged, opened and filed in the List view, and the line under the diagram says so |
| **Crew** | the running agents as an org chart, one tree per session under its repo: the session at the root titled `repo/chat`, a trunk down to its WORKING subagents, and a moving line into every one of them — each flowing the way it actually runs, left or right of the trunk. Every card wears its role as an icon at the top; a subagent's card leads with its CLASS and demotes its agent id to the line beneath; every node carries its class and model as coloured badges plus its token spend. The ones that have finished are behind one page-global switch, off by default. Narrow screens turn the same tree on its side — one spine down the left, an elbow into each card |
| **Usage** | where the tokens went — by model, by agent class, over thirty days, cache reads against fresh, and a cost derived from the token counts. A session's cache column is a pill rather than a number: green for tokens read from the cache, red for a session that read none and paid full price for its whole context, and a plain dash for one that has spent nothing at all — it has not missed the cache, it has not asked it anything |
| **Brief** | the mornings themselves (issue #181), under a banner whenever the newest published brief is older than yesterday (issue #172): the newest brief rendered in place — title, day, the whole text, a plain link to its Discussion — and under it the archive, every published brief and daily/weekly/monthly summary as a card (kind and date, title, an excerpt), newest first, each opening its full markdown-rendered text in the same dialog issues open in, box-with-arrow button included. No counts, no lists of issues: the queue is the Board's business and the numbers are the Overview's |
| **Health** | only what is broken (issue #182): a card per dirty repo naming each fault as a sentence with the act that resolves it under it — uncommitted files, unpushed commits, a branch that has never been pushed, unreleased CHANGELOG entries — and a danger alert per checkout that could not be read, the loudest thing on the page since nothing else about that repo is knowable. Above them the tower restart notice (a boot commit differing from the checkout's current HEAD, named with both short shas and the `npm run tower` that fixes it; either sha unreadable draws nothing) and the stale cloud brief (issue #172). Board and queue numbers appear nowhere here — an unanswered issue is the Board's business. Nothing broken → one all-clear line, held back until the health and brief feeds have actually answered, since "nothing is broken" said over an unread machine is the one sentence this page must never say. Last in the nav by design (issue #177) |
| **Settings** | the GitHub token this browser holds (issue #167): the field that saves one, the button that forgets it, and what the token has to be able to do - the fine-grained permissions, and the classic `repo`-scoped token a board spanning two owners needs instead. The only page that works with no token, which is what makes it the place a tokenless copy is sent; on a machine reading its own tower it says so, since the token is not that copy's credential |

**The project you are looking at is the sidebar's, and it follows you.** The selection is global, held in `?repo=` and nowhere else — nothing on the machine and nothing in localStorage remembers it — and every page whose data divides by repo respects it. Usage is the exception: token spend is machine-wide, and splitting it by repository would invent a number nothing measures. It is chosen from the **project selector** at the top of the sidebar (issue #104), the framework's own module — the button above the nav carrying the current project, and the dropdown under it: an All projects master row, then ONE row per repo on the roster - one row per project, never the same repo twice (issue #168). The menu is filled at runtime from the same `repos` feed the pages read, since a build-time nav file cannot name the repos that are on the machine when the page is open, and the button's name, tile and second line are patched to say which mode is in force. Clicking a row's NAME re-scopes the page you are on to that project alone, and every nav link is rewritten to carry the current value, so Overview → Board keeps the scope instead of dropping it on the floor. The value is a SET rather than a slug: `?repo=a,b` narrows the tower to a few repos, written by the box on each row — which is why the menu stays open while boxes are ticked — and read by every page through one parse (`libs/tower/scope.js`), so the Board's repo column, the Brief's lists, the crew's placement by working directory and the roster panels all mean the same thing by it. The boxes are on the rows only while the board is the whole one or a subset of it - a menu showing one project has none - and the master row is a toggle over all of them: ticking it fills the roster and shows the whole board, unticking it empties every box AND the board (issue #188) — the none state, written as `?repo=~` since an absent value already means everything, with the trigger reading `No projects` — so a subset builds up from a genuinely empty slate. The master row goes indeterminate while one is in force with the trigger reading `N of M projects` instead of All projects, and a menu you are working in keeps its shape — the redraw into the new mode waits until it closes. A long roster is worked two more ways, and neither of them is a selection. A **search box** sits above every row (issue #185): it takes the keyboard as the menu opens, narrows the rows to a case-insensitive match on the slug as you type, and is emptied when the menu closes, so the next open is the whole roster — the arrows walk what it left, Enter takes the row at the top of it, and a character typed on a row puts you back in the box. The menu scrolls at three fifths of the viewport with the box pinned to the top of it. And every row carries a **star** (issue #186): the projects wearing one are drawn above the rest, in roster order inside each group. That star is the one thing about the selector a browser remembers — a `tower.favorites` key in its localStorage, read through the same guard the token is (`libs/tower/favorites.js`) — and it is a habit rather than a choice: starring a project changes no scope, closes no menu and never reaches `?repo=`. A published copy works identically — the menu is fed by the roster it reads from GitHub, not baked into the site.

**Intake** is not a page: it is an action on the topbar, reachable from all of them. Repo select, title, optional body, one button; it files with `status:inbox` and `type:idea`, and triage does the rest.

**The Brief's archive is the Discussions read back** (issue #181). Both copies already downloaded the last window of brief and summary Discussions on every poll to parse the stats lines, so the payload now carries their texts too, as `documents`: kind decided by the title's prefix (`brief: ` against the summaries' `daily:`/`weekly:`/`monthly:`), the machine-marker comments stripped, newest first, capped at forty. Nothing new is fetched — the tower reads them off its one cached Discussions slot (`tower/api/lib/documents.js`), the browser off the same single GraphQL read that carries the history — and a copy whose Discussions were unreachable draws the failed-feed line every page draws rather than an empty archive.

**The history is the published briefs read back** (issue #55). Every morning's brief Discussion carries one machine-readable line, `<!-- workkit-stats: {…} -->` — the day's open counts by status, what the day closed, the inbox depth, and each repo's open count — composed by `jobs/stats.js` from the same payload the digest was written from and appended mechanically the way the cc-news cursor is, never asked of the model. `tower/api/lib/history.js` reads the last ~35 back off the home repo's Discussions and the browser mirrors the read, which is what the Overview's charts draw with the framework's charts module; a brief that predates the line is skipped, a failed read draws the unread sentence, and a morning whose sweep failed published no line at all — a missing day, never a board of zeros. History accrues from the first brief that carried the line; there is no backfill.

**That same read answers whether the brief still runs** (issue #172). The newest entry's date is the last morning that published, so `/api/brief` carries it beside the series — arithmetic on the array, never a second round trip — and a published copy's browser build attaches the same verdict off its own read (issue #176), so the Health and Brief pages draw the one line the whole tower says it in, on the machine and off it. FOUR answers, and the last two are never each other: today's morning or yesterday's is fresh and draws nothing; anything older is stale, in red, naming the day; a board that has published no brief carrying the line has never published one; and a history that could not be read says exactly that, since a failed read is neither a stopped brief nor a healthy one. Calendar days in UTC, the unit `jobs/stats.js` dates a brief in — the post happens once a morning, so "yesterday's" is the honest window and a 24-hour clock would call a 09:05 read of a 09:00 post stale.

**Clicking an issue** — on the Board or the Overview — opens it in a dialog on the page you are on: number, repo, status and chips, the body rendered, who holds it, when it was filed and last touched, and how many comments are waiting. It also says which issues it is tangled with (issue #127): a line under the dates naming what it "waits on" — the same blockers the Board's cards wear a chip for, judged the same way, so a blocker the sweep no longer holds is satisfied and named nowhere — and the inverse, what it "blocks", read at the moment the dialog opens by asking which issues on that board name this one. Nothing is fetched for either: both directions come off the board payload already in memory, and neither is stored. Each name is the short `#12` in its own repo and the whole `owner/repo#12` anywhere else, and clicking one opens THAT issue's dialog in place, so a chain of dependencies is walked without leaving the page. A BLOCKED issue also says the question it is waiting to be told (issue #205): its newest comment, which is where the spec puts that question — folded to one line on the sweep and cut at 280 characters — drawn under the dates as a danger alert labelled "Open question", and drawn on no other status, since the newest comment on an issue that is moving is not a question anybody waits on. An issue that neither waits nor blocks draws no line at all. Nothing navigates to github.com by itself. The box-with-arrow button does, in a new tab, and it is on the dialog and on each issue while it is hovered or focused. The body is rendered by the framework's markdown renderer, which escapes first and never passes markup through, because an issue body is text from an API and may say anything.

**An agent's activity is one glyph.** Wherever an agent is drawn — the Crew chart, the Overview's crew table — a spinning green gear says its transcript moved within the last twenty seconds, the same gear still and faint says it moved within the last minute, that gear on a MUTED card says it has been quiet longer than the minute, and nothing at all says it has been quiet longer than five (issue #99) — an agent that pauses between turns stays on the page, faint, rather than vanishing at sixty seconds and taking the page's answer to "who is running" with it. Every threshold and all the arithmetic are the page's, so an indicator ages from green to gray to muted to gone between reads, and the mute is a class on the card and on the Overview's row (`data-live-card`) that the second hand takes off the moment the agent moves again; the API's own 45-minute liveness window is far too coarse to say whether something is happening right now. That ageing is a SECOND HAND, not a poll (issue #65): the feeds land every ten seconds and the freshness is measured in seconds, so a one-second timer patches the indicators the last paint drew — re-reading the raw stamps off their own `data-live-*` attributes and writing only the label and the classes that actually changed — and the number beside the glyph counts up while a phase crossing lands on time. It patches rather than repaints because a repaint restarts the very spin it exists to keep turning; the timer's one home is `libs/tower/clock.js` and the arithmetic's is `agent.activityTick`, which the paint decides from too, so a card's colour and its label can never disagree. The Crew page and the Overview put how long since it last moved beside the glyph, and how long it has been running on hover; on the Board a `building` issue spins the gear whether or not anyone is assigned — the status itself says the work is in motion (issue #141) — while a `specced` issue with an assignee carries the still version, which says only that someone holds it. One helper draws all of them: `libs/tower/agent.js`, which also owns the claim gate and the role icons. The agent dialog wears the same glyph and is kept live by the same rule (issue #108): a dialog lives in the layout, outside the mount a paint writes into, so one left open used to hold the stamps it opened with — gray at twenty seconds and gone at sixty while the card behind it kept spinning, since the second hand only ever DECAYS what it walks. Every paint now refreshes whichever agent dialog is open, from the registry that paint just rewrote, so the dialog and the card are two drawings of one agent: it spins while the agent works and decays when it actually stops. That refresh patches the header's stamps and rewrites only the rows under it, for the same reason the second hand patches, and it says how fresh the agent is exactly once — the header's ticking age, which is what the frozen "Last activity" row said in words beside it.

**Clicking a crew card** opens that agent's dialog: the tool it last reached for and when, its model, effort, token counters and cost, how long it has been running and when it was spawned, and the path to its transcript. Fields the payload does not carry are left out rather than drawn as dashes. Keyboard-reachable, like every issue card.

**Status, type, and priority carry one colour each, and it is decided in one place.** Every colour the tower dyes a name with is `libs/tower/format.js`'s, in theme tokens and never a hex of its own: a status is the colour of its Board column header wherever it is said, including the chip in the issue dialog, a type is a categorical ramp slot no status or priority holds, and a priority is the theme's signal accent at the `high` end and the faint ink at the `low` end — chips that can sit in one row without being read as one vocabulary, since no two of them share a hue. Normal priority is the label that is absent, so it draws no chip at all. Both are painted through the framework's tone chip, so dark mode follows.

**An empty state is a shape, not a missing panel.** Where a column, a panel or a page has nothing in it, it draws a muted Font Awesome glyph above one quiet line — a fitting icon per place, a check where empty is good news, a chart where a reading has not arrived — so a board that is up to date reads as finished work rather than as something that failed to load. One helper (`format.empty`), one voice.

**Models and crew classes carry one colour.** A model id and an agent class are drawn as coloured badges wherever they appear — the Crew cards, the Overview's crew table, the Usage table — and the Usage charts draw each bar in that same colour, so a row in a chart and a badge in the table below it are recognizably the same thing. Which name falls in which tone is `libs/tower/format.js`; the colours are the framework's categorical ramp (`.omega-tone-1..6` on `.omega-badge-tone`), so dark mode follows. Anything clickable — every issue card and row — warms and lifts under the pointer and settles again on press, which is the framework's `.omega-interactive`.

**Refreshes are in place.** A section that has never answered shows a spinner naming the read; the chrome shows one while a refresh is in flight; and a poll that changed nothing writes nothing, so the page keeps its focus, its scroll and its open panels. A refresh that fails leaves the last good answer on screen and marks the feed unavailable rather than replacing a full board with an error line.

## Endpoints

| Route | What |
|---|---|
| `GET /api/repos` | the roster — the repos this machine has registered in `~/.workkit/.repos.json` that still carry their committed opt-in, plus the home clone at `~/.workkit/tower`, which carries no opt-in of its own and is recognized by path; the settings location is a library option, not an environment knob (cache 60s, `?fresh=1` bypasses) |
| `GET /api/board` | the GraphQL sweep, normalized to the label vocabulary, each issue carrying the body, dates and comment count the issue dialog reads — bodies over 4,000 characters are cut and flagged `bodyTruncated` (cache 60s, `?fresh=1` bypasses). It PAGES (issue #194): GitHub caps a connection page at 100 open issues, so a repo past that is asked again with the cursor its last page ended on — the first page of every repo rides the batched requests, the pages after it go one repo to a request — until GitHub says there is no next page or a ceiling of 1,000 open issues per repo stops it. A repo entry's `truncated: true` now means that ceiling. The sweep is served AS IT ARRIVES rather than at the end: the request that starts one answers with the pages that have landed, every repo still being paged marked `loading: true`, and the continuations run on behind that answer so the next poll carries more — which is what lets the dashboard on the machine draw the board page by page exactly as a published copy does. The finished board carries no such mark, is what the 60s cache holds, and is the same payload the browser's sweep ends on; a new sweep never blanks the last finished board. Only THIS endpoint is served a sweep in flight; everything derived from the board waits for a finished one. A continuation that fails leaves the pages that arrived on the board and the reason on their repo, the way one unresolvable repo does. Each issue also carries `lastComment` (issue #196): its newest comment folded to one line and cut at 280 characters with an ellipsis, `''` where there is none — the open question the issue dialog draws for a blocked issue. Each issue also carries what it is BLOCKED BY (issue #103): GitHub's native edges merged with the inline `Depends on:` fallback the spec defines, with closed blockers dropped as satisfied — the one read the Board's chips, the graph, the issue dialog and the brief's ordering all work from |
| `GET /api/sessions` | live sessions from the keep-awake markers, each carrying its transcript path and the two file times a page ages — `lastActivity` and `aliveSince`, ms epochs (cache 5s) |
| `GET /api/health` | git health per roster repo, plus a `meta` block beside the per-repo map — `bootCommit`, `startedAt` and the live `currentHead` of the checkout this process runs from (cache 5s) |
| `GET /api/telemetry` | token accounting and subagent attribution, with `byModel`, `byClass` and thirty days of history; every row also says its last tool call and where its transcript is (cache 5s) |
| `GET /api/telemetry/<id>` | one session's row of that same answer |
| `GET /api/brief` | the daily brief, assembled from the board and health above, plus the summaries and the history read back off the home repo's Discussions. The board it reads is the last FINISHED one, never a sweep still arriving (issue #194): where none has finished it drives the sweep to its end and waits, because a morning composed from half a repo's issues is a wrong answer rather than an early one |
| `POST /api/intake` | `{ repo, title, body? }` filed through `gh issue create`; the repo must be on the roster |
| `POST /api/issues/status` | `{ repo, number, from, to }` relabelled through `gh issue edit --remove-label --add-label`, one call so the issue never carries two statuses. Everything is judged before `gh` is reached: a positive integer, a slug shaped like one AND on the roster, and two different statuses from the label vocabulary — anything else is a 400 |

Anything outside `/api/*` is a 404. The dashboard is the OMEGA app, not this process.

Failures are soft and never cached: a lapsed `gh` login returns `{ ok: false, reason: … }` and the next read retries. One unresolvable repo does not blank the board — its entry carries the error and the rest render.

## Telemetry, and why it is careful

Token counts come from the transcripts Claude Code already writes. Three facts shape the code:

- **Transcripts reach gigabytes.** Reading one whole throws. Each file is streamed in chunks and its totals cached by size and mtime, so a second call reads only the bytes appended since the first; a file that shrank re-reads from zero.
- **Usage lines duplicate.** One API response is written as several lines, one per content block, each repeating the same usage — and a resumed session replays its history. Counts are deduplicated by message id; raw summing overstates a busy session by a large multiple. The measurement behind that claim lives in the module header, next to the code it justifies.
- **A finished subagent goes quiet and stays quiet.** Its transcript is never touched again, so recency is the liveness signal: each row is stamped `working` or `done` against the same idle window `sessions.js` derives a session's state from, one constant serving both tiers. The read cache is pruned to the transcripts each pass named, so a session that ended is forgotten rather than held for the life of the process.
- **A subagent's class is not in its own file.** `agent-<id>.jsonl` sits beside `agent-<id>.meta.json`, whose `toolUseId` is the parent's tool_use id, and that tool_use names the class. `meta.agentType` carries the same value and is the fallback when the parent line has been compacted away.

Cost is derived from a pricing table in the library, hand-entered from published rates and commented as a snapshot. An unpriced model reports its tokens with a null cost, never a zero — a partial total would render as a real number.

## The dependency posture

`@omega.js/*` is consumed by relative `file:` specs into the sibling Omega checkout, matching the `omega-brand` precedent. They flip to registry ranges when OMEGA publishes, which happens before workkit does. Until then the dashboard cannot build without that checkout on disk. The API has no such dependency and never will.

## FontAwesome Pro

The app ships against the free tier and every icon it draws today is a free `fa-solid` glyph. Pro is supplied, never vendored — the framework's icon chain (`[env dir, pro npm, free]`, documented in the omega monorepo's `docs/shared/icons.md`) picks it up with zero code changes here. Either route works: set `OMEGA_FONTAWESOME_ROOT` in `tower/app/.env` (see `.env.example`) to a Pro SVG download, or authenticate the `@fortawesome` scope machine-globally and add `@fortawesome/fontawesome-pro` to `tower/app/package.json`. Once supplied, Pro styles (`fa-light`, `fa-sharp`, …) simply start resolving.
