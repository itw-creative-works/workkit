# Tests

- What a test in the kit must be worth and what it may cost.
  - It is the one list every test-writing brief, the verifier's WORTH check and `safety:test-bar` point at.
- Then the shape every repo's test runner keeps, and the runner the kit ships to keep it.

## The bar

### Worth

- A case earns its place only if its failure means real behavior broke. Never:
  - a test of a test helper;
  - an expected value computed from the implementation;
  - a language or library guarantee;
  - a removed string's absence;
  - a file's existence or executable bit;
  - a regex over source, markup or stylesheet text;
  - a prose pin on a doc, skill, agent or prompt;
  - a wording or ANSI repeat of a case beside it;
  - a second case with the same break as a named one;
  - a case that only confirms a log line was written.
- Anything a builder can check once by looking is checked once and recorded in the `Proof:` line, never a test.
  - Examples: a file is there, a doc says X, a bit is set.
- A removed feature gets no test at all.
  - No test beats a tombstone.
  - The WORTH check reads a removed-thing case as a miss.

### Cost

- A case runs in-process through a seam when one exists, and spawns the real script only when the wiring is the thing under test.
- A world is built once per process through `seeded()` and copied per case.
- A scratch folder comes from `mkTmp()`.
- No fixed path, port or sleep, so the suite never needs the serial tail.
- A wait bound is the runner's shared deadline, or a short bound for a negative case.
  - The shared deadline is `SPAWN_DEADLINE`: the default bound of `until` and `elapsedUntil`, and the default `deadline` of `run` and `start`.
  - A short bound is passed to `until`, or as `deadline` to `run` or `start`.
  - A case's own limit is `CASE_DEADLINE`, the door's default; a `timeout: <n>` it states is a literal bound like any other.
  - `safety:test-bar` names a literal bound on write.
    - A literal inside quoted text (a fixture's or a child program's) is excepted.
- A timing case asserts order, never a measured duration.
- A live probe sits behind a named flag, its `skip` value naming the flag while it is unset.

## The shape

- What a repo's root runner does, whichever runner it is.
  - The kit ships one that keeps it (below).
  - A repo on another runner (a framework's own devkit runner, say) keeps the shape with its own.
- A suite has one shape: Node's own test functions, `describe`, `test` (or `it`) and the hooks (`before`, `after`, `beforeEach`, `afterEach`), with `expect` to assert.
  - On the kit's runner they all come from `workkit-core/test` (below).
  - The file holds its cases and nothing that runs them: no export, no runner function, no closing line.
  - So a file runs alone with `node <file>`, and exits 1 when a case fails.
- A `describe` body runs when the file is collected, before any case runs.
  - So a constant written between two cases is evaluated before the first case.
  - Setup that must run between cases lives in a hook or in the case that needs it.
- A resource a case opens (a server, a watcher, a child that stays) is closed in `t.after` or an `after` hook, never after the assertions.
  - A failed assertion throws, so a close below it never runs, and a suite whose own process stays alive waits out its deadline.
- Each suite file runs in its own process, as many at once as the machine has cores less one.
  - Its output prints whole, in sorted order, so two suites never interleave.
- A suite that touches a shared path (a fixed folder, a port) says so in its own file name: `*.serial.test.js` (`.mjs` and `.cjs` too).
  - The path goes in a comment at the top of the file.
  - Those suites run one at a time after the parallel wave, in sorted order.
  - No list file names them: the runner reads none.
- A world is seeded once per process (`seeded()`) and copied per case.
- A path in a world's env is spelled for the program it is handed to: `shellPath` for a bash, native for a node a case starts itself.
  - Only Git Bash turns `/d/a/x` back into `D:/a/x`, for a program it starts; a node handed it straight reads `D:\d\a\x`.
  - A world only a node reads keeps every path native, as the home suites' world does (`test/scripts/home/helpers.js`).
  - A world whose temp folder moved (`nodeTempEnv`, `mkRepo`'s `forNode`) spells a path written into bash text with `gitPath`, since Git Bash's `/tmp` moved with it (`AGENTS.md` § Tests).
  - The `workkit` command is a node, so its suites' world is native: `runCli` in `test/scripts/workkit-cli/helpers.js` starts `workflow/workkit.js` with the running Node, and `inNode` and `startInNode` call one of the command's functions in a node of its own, its `kit` built from the overrides a case hands in.
    - Beside them: `npmrcEnv(world)`, a scratch user npmrc so an npm on the system PATH reads and writes no other; `machineLinks(world, call)`, the machine steps through `inNode` under it; `windowsForm(p)`, a path as `workkit.cmd` and the Windows PATH line spell it; `lines(text)`, each line trimmed.
    - `test/scripts/workkit-cmd.test.js` holds the `workkit.cmd` cases: `renderCmd`, the copy the machine steps write, and the doctor's lines for it and for the PATH, each Windows half reached through the system argument.
  - The home suites start `workflow/home.js` with the running Node too: `inHome(world, [verb, ...args])` in `test/scripts/home/helpers.js` runs one verb from the world's root, the caller's voice at its defaults, and answers `{ code, out, err }`; its `seeded(world)` clones the home and seeds the runner, its code the seed's.
  - The tower start suites start `tower/start.js` through `test/tower/start/helpers.js`, which guards each start (`guarded(env)`), so a starter that ignored its seams reaches neither the real app nor the live tower's API port and home:
    - a guard folder first on its `PATH`, of `npm` and `omega` stand-ins (`stubToolJs`) that say `the suite reached the real <name>` on stderr and exit 1;
    - a scratch home (`HOME`, `USERPROFILE`, `WORKFLOW_HOME`) and a `TOWER_PORT` free a moment before.
  - A run: line meant for Linux runs under `MSYS2_ARG_CONV_EXCL=*`, so Git Bash rewrites no argument that looks like a path (`/workkit/`).
- A stand-in a case puts on a PATH is a Node program, built by `stubToolJs`, the one builder (`AGENTS.md` § Tests), so it needs no compiler on Windows.
  - It does a fake's file work in Node: a read, a write, a folder, a copy, a wait. No `cat`, `mkdir`, `cp`, `sleep`, `grep` or `tr` runs inside one.
  - A test file starts a shell only where a start from a shell is the case's subject: the `git` shim, git's hook files, npm's script shell, a skill line, the starter's `bash` name, a descriptor a shell hands over, a `run:` line.
- `test/scripts/shell-list.test.js` holds three lists, each entry with its reason, read against the tree's own text:
  - the test files that may hold a shell `#!` line or start `bash` or `sh`;
  - the programs a kit Node file outside `test/` may start by name;
    - A name is seen as a literal at the start, under a `program:` key or as any `<name>.exe` literal, or held in a constant of the same file: a literal, either arm of a choice of two, a template's or a `path.join`'s last part, and an array's first element below a destructure (`const [cmd] = ...`).
    - A constant whose value starts with another name (`awake`, `opener()`) is followed to that name's constant, read the same way.
    - A start handed a function's parameter stays unseen.
  - the shell files that stay.
  - A use off a list fails its case, naming the file; so does a listed test file that no longer uses a shell, and a listed program no kit Node file is seen starting ("on the list, started nowhere"), so no list goes stale.
- Every scratch folder comes through one seam (`mkTmp()`), which removes them all when the process exits.
- A suite or a case that cannot run here states a `skip` value, its reason, and the run lists every skip after the totals.
  - A whole file skips through its outer `describe`'s `skip` option: `describe('supervise', { skip: skipOnWindows() }, () => { ... })`, the kit's helper in `test/lib/supervise.js`. A suite that needs a tool states `needs` there (its bullets below).
    - `test/lib/supervise.js` also holds the detached-run suites' shared fakes and worlds: `actsAfter`, `writesAfter`, `rootHolding`, `rootWith`, `handLock`, `claimNaming`, `tagOf`, `deadPid`, `holding`, `attachArgv`, `underEndWait`, `ridesSignals`, `nodeBody`, `launchBody`.
    - A run's paths as a case names them: `runPathsUnder` in `test/lib/run-paths.js`, and `repoMarkerPath` beside the record paths in `test/lib/suite-record.js`.
    - A `workflow/lib` export asked under a world's env: `kitUnder(env, file, name, asks)` in `test/lib/kit-under.js` calls `<name>` of `workflow/lib/<file>` once per ask, each ask an argument list, all in one node of its own under `env`, so the machine folder, the temp folder and git's config it reads are the world's.
      - The answers come back in order, as JSON brings them. A call that throws in that node throws in the test with its message, and the asks after it are never made.
      - `kitUnderAsync(env, file, name, asks)` is the same asks started without waiting, so several nodes ask at one moment; it resolves the answers, or rejects as `kitUnder` throws.
    - A job's function called in this process under a world's env: `underEnv(over, fn)` in `test/lib/under-env.js` awaits `fn` with the keys of `over` laid on `process.env`, and puts every key back after, however `fn` ended.
    - A Node below the kit's floor, and a count of a call's Node starts: `olderNode` and `recordingNode` in `test/lib/node-fakes.js` (`AGENTS.md` § Tests), the second also older than the floor with `older: '<version>'`. A case that builds a PATH and needs a `node` puts `NODE_DIR` (`test/lib/platform.js`) on it.
    - The heal started by its suites: `heal` in `test/scripts/workflow-standards/helpers.js` always applies `seededEnv(env)`, which seeds a scratch workflow home and Claude home and throws when either would land in the machine's own `~/.workkit` or `~/.claude`.
    - The `schtasks` a Task Scheduler case puts first on a PATH: `schtasksStub(dir, { exists, create, createErr })` in `test/lib/schtasks-stub.js`, a Node stand-in recording each call (`calls()`, `creates()`), answering `/query` and `/create` by the state `set()` changes, and keeping a copy of the file `/create /xml` named (`kept()`).
    - `run` of `lib/runs.js` driven the same way, as npm's script shell (`workflow/script-shell.js`) calls it, so a signal to the call reaches that node:
      - `runJob(dir, script, { lock, root })` is the job the script shell hands `run`: `node -e <script>`, its log in `<dir>`, its lock there unless `lock` names one, `root` null unless given.
      - `runUnder(job, { env, before, launch })` runs it to its end in a node of its own and answers `{ res, answers }`: the harness run's result (its status the `rc`, its output the run's) and what `run` resolved, null when the call ended first. `before` is source run once `runs.js` is loaded, `launch` a launch seam's source.
      - `startRun(job, { env, before, launch, detached })` is `runUnder` started without waiting: the harness start handle, its pid the call's, plus `answers()`, null until `run` resolved.
    - A spin of `workflow/lib/spin.js` driven in a node of its own: `driveSpin(mode, { env, frames, terminal })` in `test/lib/spin-call.js` spins around a real child that holds until the case releases it, so a case sees the frames while the call runs; `terminal` is a file a logged command's terminal device stands in for (`WK_COMMAND_TERMINAL` names it), the frames watched there.
      - `drivePoll(key, { env, frames, counts })` drives the poll of `workflow/lib/flows.js` the same way, the key typed once its countdown drew; `framesIn`, `secondsOf` and `spinArgs` read and start them.
    - A line of `workflow/lib/voice.js` spoken in a node of its own: `speak(lines, vars)` in `test/lib/speak.js` runs the lines after `const v = require(voice.js)` under a scratch home, color off unless `vars` say otherwise, and asserts the node ended clean; `voice-titles`, `lib-log`, `twins` and the heal's `healing` suite share it.
    - The streams a terminal question of `workflow/lib/flows.js` is handed in place of the process's own: `ioOf(input, { tty, open })` in `test/lib/io-streams.js`, a stdin holding the input and a stderr that keeps what it was told (`said()`).
  - A skip value is `false` or the reason text, never another falsy value: `false` and `undefined` run the case, and `true` or a reason skips it.
    - For `''`, `0` or `null`, Node runs a case's body anyway and labels it skipped, and on a `describe` it cancels the children, which fails the run.
  - A helper that decides a skip (the kit's, a repo's own) returns `false` or the reason. `needs` alone also throws for a missing tool outside a cloud session (its bullets below).
- The run ends with one totals line, `N passed, M failed (Ns, K suites)`, with `, C cases skipped` after the failed count when there are any.
  - A monorepo root's run that started its members names them last: `(Ns, K suites, P members)`.
  - A skipped `describe` counts as one case skipped.
- The kit's runner then prints one more line, `slowest: <suite> <s>s, ...`, naming the five slowest suites of the run by wall time, slowest first.
- Under a failing case's message the runner prints the first stack frame that names the suite file: the suite's line, the one calling the seam when the assertion sits in one.
- A case's `t.diagnostic()` lines and its own prints (`console.log`, `console.error`, `process.stdout.write`, `process.stderr.write`) sit at the case indent in the suite's block.
  - A diagnostic line prints under its case's mark. Node's own totals lines never print.
- Any failure exits 1. A suite that fails whole is one failure, named by how:
  - `load <suite>`: the file died of an uncaught error, or would not parse, before any case ran, with the error's message.
    - Only Node's own uncaught-error report counts, never an error line the suite printed.
  - `run <suite>`: anything else that ends a suite without its result.
    - A late failure after the cases (a timer's throw, an unhandled rejection), with the thrown message.
    - A suite process that exits or is killed, with the code or signal and its last output.
    - A suite process that exits before its cases are reported (a `process.exit(0)` partway through): `exited with code 0 without a result; last output: ...`, the cases already counted kept.
    - A suite that exits with its output held open by a process it started, and no result of its own.
    - The suite deadline: `timed out after <n>s without a result; last output: ...`.
  - `empty <suite>`, `registered no test`: a file that registered no case, so it proves nothing.
    - So is a suite whose process exits before Node reports any case (a first case calling `process.exit(0)`): it sends the events of a file with none, and still fails the run.
  - A suite in the old shape (a runner function it exports) fails as `load` or `empty` and counts no pass.

### The kit's runner

- It is the npm package `workkit-core`, built in this repo at `packages/core/`.
  - It is a workspace member released at the kit's version.
- The package holds:
  - `test/run.js`;
  - `test/tools.js` (the `tools` verb) and `test/convert.js` (the `convert` verb);
  - its library in `test/lib/` (`harness.js`, `cases.js`, `expect.js`, `lexer.js`, `log.js`, `node-test.js`, `process.js`, `proc-state.js`, `scratch.js`, `seed.js`, `spawn.js`, `suites.js`, `suite-path.js`, `pick.js`, `serial-name.js`, `members.js`, `kit-module.js`, `paint.js`, `convert-read.js`, `convert-map.js`, `events.js`, `app-cases.js`, `mods.js`, `suite-deadline.js`, `on-path.js`);
    - `pick.js` picks a run's suites and its serial tail by name (`serial-name.js`, importing nothing so `safety:test-bar` reads it too), and stops a run on a leftover list file; `mods.js` is `modCase`; `suite-deadline.js` reads the suite deadline a run holds, for the runner and `modCase`; `on-path.js` finds a command's files on the PATH, for `needs` and `modCase`;
    - `members.js` reads a monorepo root's members and runs one member's `npm test`; `kit-module.js` loads a kit file the package ships a copy of (`kitModule(stem)`); `proc-state.js` reads whether a process, or every member of a group, ended and waits uncollected, for `alive` and `groupLives`, through the kit's `workflow/lib/proc-state.js` (`ended` handed the starter of `workkit-core/run`);
      - `proc-state.js` also holds what `spawn.js`'s end throws for a target alive after SIGKILL: `groupMembers(pgid)`, each member of the group `/proc` shows with its state letter (`[{ pid, state }]`, empty without `/proc`), and `survivedText(who, pid, members)`, the text naming them;
  - the export `workkit-core/test`, the entry `harness.js` builds: Node's case functions, its own `test`, `it`, `needs`, `hasLaunchd` and `WORKKIT_DIR`, and every export of `process.js`, `scratch.js`, `seed.js`, `suites.js`, `log.js`, `spawn.js`, `expect.js`, `events.js`, `app-cases.js` and `mods.js`;
  - plus `workkit-core/run`, the kit's `workflow/lib/run.js` its prepack copies in as `run.cjs`, which the library's `run` and `start` launch through;
  - plus the kit's `workflow/lib/expand-workspaces.js`, copied in as `expand-workspaces.cjs`, the expansion of `workspaces` the publish plan, the package record and the runner share;
  - plus the kit's `workflow/lib/proc-state.js`, copied in as `proc-state.cjs`, the process-state reads `lib/lock.js` and the library's `proc-state.js` share.
  - `kit-module.js` reads each of the two: in the kit's own checkout the kit's file, so a copy a local `npm pack` left there never wins; elsewhere the packed copy.
- It is ES, and a CommonJS suite `require()`s it alike.
- Its README (`packages/core/README.md`) lists the exports.
- The door, `workkit-core/test`, hands out Node's own `describe`, `before`, `after`, `beforeEach`, `afterEach` and `mock`, untouched.
  - Its `test` and `it` are Node's behind one thin wrap: a case that states no `timeout` gets `CASE_DEADLINE`, 120000 ms.
  - The wrap carries every property Node's word carries (`skip`, `todo`, `only`, `mock` and the rest), each Node's own.
  - Its limits: a case marked `.only` or `.todo`, and one stating `timeout: null`, get no default; a subtest inherits its parent's limit.
  - Under `node <file>`, Node's own reporter names the wrap's file as a case's location; the kit runner's failure frame names the suite's line.
  - A suite that takes `test` from `node:test` itself runs too, with Node's own default, no limit.
- A repo installs it with `npm i -D workkit-core` and sets `"test": "workkit test"`.
  - Inside `npm test`, npm puts `node_modules/.bin` first on PATH, so `workkit` is the package's bin.
  - The bin runs the runner over the repo with the arguments npm passes on.
  - The bin runs `test`, `tools` and `convert`; any other verb exits 2, naming the global `workkit` command.
- `workkit test [paths] [--filter=<text>]` in a terminal is the global command.
  - It hands its arguments to the repo's own `npm test`, run at the repo root, and does nothing else.
  - So the one recorder, npm's script shell, sees the run and records it as `docs/project-state.md` § The proof says.
  - So `workkit test`, `npm test`, `workkit test test/x.test.js` and `npm test -- test/x.test.js` land in the same runner with the same arguments.
  - A repo whose package.json has no `test` script gets one error line and exit 1.
  - The global verb started inside an `npm test` means the package is missing.
    - It exits 1 with `workkit-core is not installed here: run npm install` rather than loop.
- `needs(...tools)` names the commands a suite or a case runs, as its `skip` value: `describe('render', { skip: needs('hugo', 'ffmpeg') }, () => { ... })`.
  - Each is a command name looked up on PATH (on Windows, with each `PATHEXT` extension).
  - All found, it is `false`, and the cases run.
  - With one missing, in a cloud session (`CLAUDE_CODE_REMOTE` is `true`), which may lack it, it is the reason, `needs <tool>`, each missing one named (`needs hugo, ffmpeg`), and the run lists the skip with it.
  - Anywhere else, CI included, it throws `needs hugo, ffmpeg, not installed`.
    - A call at the top level (an outer `describe`'s `skip`, or a bare statement) stops the file while it is collected: `node <file>` exits 1 with the message, and the runner reports `load <suite>` with it.
    - In a case's `skip` inside a `describe`, the throw fails that `describe`, and its other cases are cancelled with it.
    - So a missing tool on a developer's machine or in CI is loud, never a quiet skip.
  - A bare `needs('hugo');` statement throws the same way outside a cloud session, failing the file; in one it does nothing, so the value goes in a `skip` option.
  - A call with no argument, or with one that is no string or an empty one, throws `needs() takes one or more command names`.
- `workkit tools` prints every command the repo's suites name through `needs()`.
  - It prints one per line, sorted and unique, for a cloud setup to install before the run.
  - It reads each `needs(` call, a `skip` value's among them.
  - It reads the suites the runner would run, never loads one.
    - So a nested folder's suites are in its list unless that folder holds its own `package.json`.
  - A `needs()` argument that is not a string literal is one line, exit 1: `✖ tools: <file>:<line>: needs() takes string literals only`.
  - The global verb runs the kit's own copy of this bin at the repo root, so it answers before `npm install`.
- `workkit convert [paths...]` rewrites a suite in the old shape in place onto Node's test functions through the door.
  - The old shape: a runner function the file exports, its cases on the removed words (`group`, the harness `test`, `assertEq`), a `selfRun` line last.
  - No path means every suite the runner finds. A path is read as the runner reads one: from the start folder, a `\` in it as `/`, a folder naming every suite under it.
    - Anything that names no suite is `No suite matches <arg>`, exit 1, before any file is touched.
  - It rewrites a file only when every statement of its runner is a label, a case or a constant, and maps each one for one:
    - a `group('x')` and the cases under it to `describe('x', () => { ... })`, and `await test(name, fn)` to `test(name, fn)`;
    - `assert(value, message)` to `expect(value, message).toBeTruthy()`, and `assertEq(actual, wanted, message)` to `expect(actual, message).toBe(wanted)`;
    - `skip(name, reason)` to `test(name, { skip: reason })`;
    - `testUnless(condition, reason)(name, fn)` to `test(name, { skip: condition ? reason : false }, fn)`, so a falsy condition never skips;
    - a same-file alias (`const onMac = testUnless(...)`) the same way at each case through it, when cases are its only reads: its line goes, the comment above it stays;
    - the harness `require` line to the door's names the file uses; and it drops the export, the `summary()` return and the `selfRun` line.
  - A file whose every line ends in CRLF keeps CRLF, the lines it writes included.
  - It prints one line per file: `converted <path> (<n> cases)` (`(1 case)` for one), or `left <path>:<line> <why>` with the file left byte for byte.
    - A file already on Node's functions is left, never listed as converted, so a second run changes no file.
  - It exits 0 once it ran, whatever it left.
  - What it leaves, for a person to convert, each with the why its line gives:
    - a removed word with no mapped form (`failureOf`, `stripAnsi`, the harness `log`), or a local variable named like one: `uses <word>, which has no mapped form here`, the likeliest in another repo;
      - `failureOf` becomes `expect(fn).toThrow(...)` or `await expect(promise).rejects...` from the door, `stripAnsi` Node's `util.stripVTControlCharacters`;
    - cases made in a loop: `cases made in a loop`;
    - an awaited line or a helper call between cases: `an awaited constant between cases, a setup`, `a call to <name>, no label, case or constant`;
    - a whole-file skip: `a whole-file skip`;
    - a backtick inside a template's placeholder: `a template literal nested in another template's placeholder`;
    - a constant or a same-file alias one group declares and a later group reads: `<name>, a constant of an earlier group, read in a later one`;
    - as a last guard, a file whose converted text would hold an `expect` with no matcher: `the converted text would hold an expect with no matcher`.
  - A repo on the package runs it, then converts by hand each file it lists.
  - The global verb runs the kit's own copy of this bin at the repo root, as `workkit tools` does.
- `start()`'s child has its stdin ignored; with `input` the text is written to it, then it is closed.
  - With `stdin: 'open'` it is a pipe `start` never ends: `input`, if given, is written first, and the caller writes and ends it through `child.stdin`.
  - A closed pipe (EPIPE, EOF) is ignored, as it is for `input`; any other stream error fails `done`.
  - Node closes it once the child is gone, so `start` adds no close of its own. `end()` and the deadline end the process, and close no stream first.
  - Any other `stdin` value throws at the call, naming `stdin`, so a misspelt one never starts a child with no stdin.
- `start()`'s `end(signal)` climbs the kit's ladder (`endRun` in `workflow/lib/run-lock.js`): `SIGINT` then `SIGTERM` then `SIGKILL`.
  - It starts from the rung named, and the rungs are 1.5 s apart.
  - Each rung is sent only while the child (a detached child's whole process group) still lives.
    - So `end('SIGKILL')` is one send.
  - On Windows it is one `taskkill` tree end, `endTree`'s.
    - `endTree` runs `taskkill.exe` from `System32` under `SystemRoot`, never through PATH, with `/T /F /PID <pid>`. A nonzero exit is no failure.
    - One that cannot start throws `endTree: taskkill could not run (<message>)`, and an unset `SystemRoot` throws naming it.
    - It takes the platform, the program runner and `SystemRoot` as seams (`endTree(pid, signal, seams)`), so a case reaches that arm on any machine.
    - It ends a test's own child. The kit's own end, `endTreeOf` in `workflow/lib/tree.js`, ends a whole supervised run instead: it reads the Windows and the Git Bash process tables and ends each process of the tree, so it reaches what `taskkill /T` misses. The package cannot require it, since it is published alone.
  - `alive(pid)` is false for anything but a positive integer, since 0 or a negative pid reaches a whole group.
    - It is false, and `groupLives(pid)` too once every member is, for a process that ended and is not yet collected.
  - A real signal the system refuses for the pid itself rejects `end()` (and throws from `endTree`), naming the pid and `EPERM`.
    - A refused group falls through to the pid, since a leader that exited unreaped refuses its group.
    - The zero probe reads a refused group as gone.
  - A target still alive one grace after `SIGKILL` rejects, naming it, so `end()` never waits unbounded.
  - On Windows, once a detached leader has exited, `end()` reaches no grandchild.
    - `taskkill /T` finds a tree only through a living root.
- It reads every suite under the folder it starts in, the package root under `npm test`.
  - A suite is a file named `*.test.js`, `*.test.mjs` or `*.test.cjs`, in any folder.
  - It never reads:
    - `node_modules`;
    - a file or folder whose name starts with `.` or `_`;
    - a folder below the start folder that holds its own `package.json`, a nested package that runs its own suites;
    - a file git ignores.
  - A start folder inside a git-ignored folder, at any depth, holds no suite.
  - Outside a git work tree, or with no `git` on the PATH, the ignore rule skips nothing.
    - Any other git failure inside a work tree stops the run with git's own message.
  - No folder name is special: `test/`, `tests/` and `lib/` are read like any other.
  - Every printed suite name is its path from the start folder, with `/` on every platform (`test/hooks/x.test.js`).
    - The `▶` heading, a failure, a skip and the `slowest:` line all print that name.
  - A run that finds no suite, and starts no member, exits 1: `No test file found (*.test.js, *.test.mjs, *.test.cjs)`.
- A run covers every suite.
  - First the parallel wave, then the serial tail: every suite named `*.serial.test.js`, `*.serial.test.mjs` or `*.serial.test.cjs`, one at a time, in sorted order.
  - Then, from a monorepo root, each member's own `npm test` (below).
  - It runs Node suites and nothing else, and reads no list file.
    - A plugin's own tests run as one case of a Node suite, `modCase` (§ A plugin's own tests).
    - A case that must not run on a machine skips itself in its own suite, with its reason.
  - A `test/lib/serial.js` or `test/lib/skip.js` in the repo stops the run with one line and exit 1 before any suite runs, so a suite never loses its run-alone or skip rule in silence:
    - `test/lib/serial.js is no longer read: name a suite *.serial.test.js to run it alone`;
    - `test/lib/skip.js is no longer read: skip a case in its own suite`.
  - Suite paths narrow the run.
    - Each is a path from the start folder, a `\` in it read as `/`, a trailing `/` fine.
    - A file is one exact suite.
    - A folder names every suite under it, by the rule a bare run reads by: none in `node_modules`, under a name starting with `.` or `_`, git-ignored, or below a folder holding its own `package.json`.
    - A suite named twice (a file, and a folder that holds it) runs once. A narrowed `*.serial.test.js` suite runs in the serial tail.
  - A path matching no suite exits 1 with `No suite matches <arg>`, the argument as typed, and runs nothing.
    - So does a folder holding no suite, or one holding its own `package.json`, and a path that resolves outside the start folder (`..`). The start folder itself (`.`) names every suite.
- `--filter=<text>`, once, anywhere among the arguments, runs only the cases whose full name holds the text, in the suites the run would run anyway.
  - `workkit test --filter=<text>` and `npm test -- --filter=<text>` both carry it.
  - A case's full name is its `describe` path and its own name, joined by single spaces: `--filter=outer` runs every case under `describe('outer')`, and `--filter="outer alpha"` the one.
  - The text matches as typed: upper and lower case count, and no character is a pattern.
  - An empty text (`--filter=`, or `--filter` alone) exits 1 with `--filter needs a text`, and the flag given twice with `--filter is given once`; nothing runs.
    - Any other argument starting with `--` is a path, as before (`No suite matches --other`).
  - The run prints `filter: <text>` before the first suite.
  - A case left out prints nothing and counts nowhere. A suite with no case left prints nothing, not even its heading, and is no failure: the `registered no test` rule does not apply.
  - A run in which no case matched exits 1: `No case matches <text>`.
    - From a monorepo root that is no case of its own and none in any member it started: every member wrote the no-match line (below). A member whose matching cases were all skipped matched.
  - From a monorepo root a filter alone starts the members a bare run starts, each handed the text (below). A filter with suite paths starts none.
  - A filtered run writes no proof record (`docs/project-state.md` § The proof).
- Each suite file has a deadline, `SUITE_DEADLINE` (600 seconds).
  - `TEST_DEADLINE=<seconds>` in the environment sets it for one run.
    - A value that is no positive number, or above 2147483 (more than node's timer holds), exits 1 before any suite runs: `TEST_DEADLINE must be a positive number of seconds, got <value>`.
  - A worker not closed when it passes, and with no result sent, has its process group ended.
    - `endGroup` climbs `end()`'s ladder over the worker's process group, so a worker on `SIGINT` or `SIGTERM` runs its exit handlers and removes its scratch folders.
    - A child the suite starts detached leads its own group, so it is the suite's own to end.
    - Its file is one failure, `run <suite>`: `timed out after <n>s without a result; last output: ...`.
    - The run goes on to the next file and exits 1.
  - Once the suite's own process exits, the worker waits one grace (`PIPE_GRACE_MS`, one second) for its output to close, then reports what it counted.
    - So a child the suite left running, still holding that output, never holds the run, and is left alive.
  - A suite whose own process stays alive (an open server, a live timer) waits for the deadline and fails as timed out.
  - Off Windows a signal to the runner's group reaches no worker, so on `SIGINT`, `SIGTERM` or `SIGHUP` the runner ends every live worker's group the same way, then exits 128 plus the signal's number.
    - Meanwhile it prints nothing more: no block for a suite that ends while it waits, and no member or totals line.
    - A second of the three while it is ending sends `SIGKILL` at once, before anything else runs, to every group the first began to end that still lives, its worker exited or not, then exits 128 plus that second signal's number.
      - So `workkit prove`'s ladder on the runner (`endRun`) leaves no worker behind: its `SIGTERM` has the runner KILL every worker before its own `SIGKILL` comes.
    - A runner ended by `SIGKILL` cannot; a worker then ends its own tree only once its event loop notices the parent gone.
- A run with no suite path, bare or under `--filter` alone, from a folder whose `package.json` lists `workspaces` also runs each member's own `npm test`, after its own suites.
  - Members are read by the publish plan's rule (`workflow/lib/expand-workspaces.js`): a literal folder, or `dir/*`. Any other pattern stops the run with the plan's own line before any suite.
  - A member with no `test` script is not started. A narrowed run starts none, and a run started in a member's folder is that member's own.
  - They run one at a time, in sorted folder order, each under a heading `▶ <member name>: npm test`, its output showing as it runs. A failed member stops none after it.
    - Each starts through the kit's program starter (`workflow/lib/run.js`) on every platform: on Windows it finds npm and quotes each argument by its one rule.
    - A member's script may run steps of its own before the runner (`npm run prepare && workkit test`).
  - Each is handed a summary file of its own (`WORKKIT_TEST_SUMMARY`), and the kit's runner writes its counts there.
    - A member whose run writes no line did not run the kit's runner, so it fails by name, whatever its exit: `✗ <name>: its test script did not run workkit's runner`, with ` (exit <code>)` after it when it exited other than 0.
  - Under a filter each runs `npm test -- --filter=<text>`, the text one argument, whole.
    - On Windows it arrives whole through Git Bash, which the starter uses when Git for Windows is there. Without it the starter runs `npm.cmd`, whose `%*` reads the line again, so the starter escapes each argument twice and the text arrives whole there too.
    - npm appends it to the member's script, so a script that ends in the runner takes it (`node pre.js && workkit test`). A script that ends in another command does not, and its cases all run.
    - Each is handed a no-match file of its own too (`WORKKIT_TEST_NO_MATCH`). A member whose run ends with no matching case prints its own `No case matches <text>` under its heading and writes one line there.
    - Such a member is the row `⊘ <name>: no case matches`, with no count and no failure, whatever its exit. One that exits 1 without the line fails as on a bare run.
    - A member whose runs counted a pass or a failure is never that row, the line written or not: its counts and its exit code decide.
      - So a script chaining a passing run and one matching nothing (`workkit test a && workkit test b`) exits 1, the row `✗ <name> (exit 1)`.
  - The run ends with one row per member before the totals: `✓ <name>`, `⊘ <name>: no case matches`, or `✗ <name> (exit <code>)`.
    - The totals add each member's counts, an exit other than 0 with no failed case counting one, and name the members: `(12.3s, 4 suites, 3 members)`.
    - The exit is 1 when any suite or any member failed.
  - A signal that ends the run while a member runs ends that member's process group, prints no row for it and no totals line, and exits 128 plus the signal's number.
  - Its limit: a member's run has no deadline of its own; its suites keep theirs.
- `WORKKIT_TEST_SUMMARY=<file>` in the environment, set by `workkit proof red` for its command and by a root run for each member it starts, has the run add one line to that file on every exit it makes itself; a forced end (`SIGKILL`, any signal on Windows) writes none.
  - The line is `{"passed":<n>,"failed":<n>}`, the counts the totals line prints, the members' included; a run that stops before any suite ran writes both as 0.
    - A member whose run stops before its runner (a step of its script fails, or its script runs another runner) counts as one failed test in its root's line.
  - The runner takes the variable out of its environment at its start, so a run a suite starts writes no line. Unset, no file is written.
  - How the proof reads it: `agents.md` § Crew sizing.
- `WORKKIT_TEST_NO_MATCH=<file>` in the environment, set by a root run for each member it starts under a filter, has a run that ends with no matching case add one line to that file: the filter text, as a JSON string.
  - The runner takes it out of its environment at its start, as it does the summary file's, so a run a suite starts writes none.
- Every suite runs on Node's own runner, its `run()` in the suite's worker. No file's text is read to pick a shape.
  - Its pass, fail, skip and todo events are counted into the totals and the lists.
    - Node's own pass for the file is not a case, so a file that registered none is `empty <suite>`.
  - A test holding a failing subtest counts one failure, the subtest's; a passing one counts beside its subtests, as Node counts it.
  - Its block:
    - A heading `[outer › inner]` prints before a case whose `describe` path differs from the case before it.
    - A case with no `describe` after a headed one is set apart by a blank line.
    - A test that holds subtests heads them the same way.
    - Each case prints one mark line: `✓ name`, `✗ name`, or `⊘ name: reason` for a skip or a todo.
    - Under a failed case, at the case indent: its message, then the first stack frame that names the suite file.
    - A failed hook prints Node's line, then the thrown error's message.
    - A skipped `describe` prints one `⊘` line with its reason, for all its cases.
  - In the failure list and the skip list after the totals, a case is named `<suite> › <describe path> › <case>`.
    - A case under no `describe` is `<suite> › <case>`.
  - What the suite itself prints arrives in its own order, at the case indent.
    - Node's runner hands it over before the case's result, so it can land above that case's heading.
- The runner and its workers write no color code of their own, and no line carries a time stamp.
  - They remove the codes Node adds to a failure under `FORCE_COLOR` (an uncaught error's report, a case's or hook's message and its stack frame) with `util.stripVTControlCharacters`. A suite's own printed output is left as it is.
  - The parent paints what it prints through `paint(text, stream)` (`test/lib/paint.js`), by Node's own rule for its stdout (`util.styleText`): color at a terminal or under `FORCE_COLOR`, none on a pipe, in a file or under `NO_COLOR`.
    - `NO_COLOR` set to any text wins, `FORCE_COLOR` or not: the painter reads it first, where Node's own rule would let `FORCE_COLOR` win.
  - A line is painted by how it starts after its indent: a `✓` mark green, a `✗` line red, a `⊘` line and `slowest:` gray, a `▶` line, a `[outer › inner]` heading, the totals line and `Failures:` bold. Any other line is left byte for byte.
  - `node test/lib/paint.js` is the same painter as a filter: standard input to standard output, each whole line painted once its line end arrives, what follows the last line end written when the input ends.
  - So a run's log file is plain, and the kit's terminal view of a long run paints it as it shows it (`workflow/README.md` § `lib/attach.js`).
  - With `FORCE_COLOR` in the run's environment the parent paints into its log file too. Every program a suite starts inherits it as well, and Node then colors what they print (`console.log` of a number), so set it for a run only when no suite reads such output.
- A run a case starts (`workkit test` in a scratch folder) is a run of its own.
  - Node's runner runs nothing under `NODE_TEST_CONTEXT`, the variable its own test files inherit, so the runner drops it from its environment as it starts.
  - A case that starts a suite file with `node <file>` passes an env without that variable.
- The repo's `test/lib/harness.js` is the one re-export: `module.exports = require('workkit-core/test')`.
  - So every suite's `require('../lib/harness')` stands as it is and reaches the whole library.
  - `test/lib/` otherwise holds the repo's own seams.
  - A `*.test.js` file there is a suite like any other, so the runner runs it.
    - `safety:test-bar` still names it at the write as a test of a test helper (its `helper-test` line, `docs/hooks.md` § `safety:test-bar`).
    - The first rule is about finding, the second about worth.
- The library exports `expect(actual, message?)`, the assertion form of Jest.
  - Its names and behaviour are Jest's (its `expect` 29.7), so a reader needs no kit doc.
    - `toBeTypeOf` is the one name from Vitest.
  - The matchers:
    - `toBe`, `toEqual`, `toStrictEqual`, `toMatchObject`;
    - `toBeTruthy`, `toBeFalsy`, `toBeDefined`, `toBeUndefined`, `toBeNull`, `toBeNaN`;
    - `toContain`, `toHaveLength`, `toHaveProperty`, `toMatch`, `toBeInstanceOf`, `toBeTypeOf`;
    - `toBeGreaterThan`, `toBeGreaterThanOrEqual`, `toBeLessThan`, `toBeLessThanOrEqual`, `toBeCloseTo`;
    - `toThrow`.
  - The forms are `.not`, `.resolves` and `.rejects`, and `.not` after either of the last two.
  - A failed matcher throws an `Error` named `AssertionError` that carries `actual` and `expected`.
    - Its message is `expected <actual> to <verb> <expected>`, with `not to` under `.not`.
    - With a `message` given, `<message>: ` leads it.
  - A misused matcher throws an `AssertionError` saying what it expected, under `.not` too.
    - Examples: a length that is no whole number, a path that is no string or array, a value of the wrong kind.
  - `expect.fail(message)` throws the `AssertionError` with that message.
  - `expect.extend(matchers)` is the one way a repo or a framework adds its own matchers.
    - Each matcher is `(actual, ...args) => ({ pass, message })`, `message` a function returning the failure text.
    - Inside it, `this.isNot` and `this.promise` (`''`, `'resolves'` or `'rejects'`) say how it was called.
    - A name a built-in matcher holds throws.
  - It deliberately lacks Jest's asymmetric matchers (`expect.any`), snapshots and mocks.
- CI fetches the runner like any dependency.
  - The install brings the package, so no step clones the kit for it.
  - The test step of the kit's CI (`ci.yml`, and the kit's own `checks.yml`) sets no `FORCE_COLOR`, so a CI log is plain and a suite's own programs print as they do on a pipe.
  - The heal's rewrite of `checks.yml` to the kit's caller drops a `FORCE_COLOR` an older copy carries.
- The standards heal names a participating repo whose test script does not run this runner.
  - It is one line: `npm i -D workkit-core` and `"test": "workkit test"`.
  - It is skipped when the repo's devDependencies name `workkit-core`, whatever its test script.
    - A script of the repo's own may wrap `workkit test` (`workflow/README.md`, the `standards/` row).

### A plugin's own tests

- A Claude Code plugin's tests run through `claude plugin test <folder>`, and a Node suite holds them as one case.
- `modCase(folder)`, from the door, registers that case: `claude plugin test (<the folder's own name>)`.
  - It starts `claude plugin test <folder>` in the folder through the kit's program starter, so on Windows a `claude.cmd` starts too.
  - It passes when the tool exits 0.
  - It fails on any other end. Its message holds how the tool ended (`exited with code 3`), each test the tool named in a `(fail) <name>` line, and the tool's output.
  - With no `claude` on the PATH it is skipped: `no claude binary on PATH`. A `claude` that is found and does not start fails it, with the reason.
    - Found is any file or link on the PATH named `claude`, or on Windows also `claude` with a `PATHEXT` ending, runnable or not, a link to nothing included, so a missing `#!` program or a broken link fails it rather than skipping.
  - Its deadline is the suite deadline the run holds (`TEST_DEADLINE`, else `SUITE_DEADLINE`), since one case holds the whole tool run.
    - The tool is ended 10 seconds before it, or at half of it when that is less, so a tool that never ends fails the case with `timed out after <seconds>s` and its output.
  - A folder that does not exist throws `modCase: no folder <folder>` at the call, failing the suite.
  - It is a case like any other: `--filter` and suite paths treat it as they treat every case.
- A repo calls it from a host suite of its own; the kit's is `test/mods.test.js`, over the kit's root and its `test/mods/` suites:

```js
const path = require('node:path');
const { modCase } = require('workkit-core/test');

modCase(path.join(__dirname, '..'));
```

### Cases that run inside an app

- Some cases cannot run in the suite's process: they run inside another program, a browser page, an extension's service worker, an Electron process.
  - The host suite starts that program, and each case's result comes back to Node's runner as one case of the suite.
- Each in-app case reports its result as one event line: `EVENT_PREFIX` (`__WORKKIT_TEST__`), then one JSON object, on one line.
  - `id`, unique in its session; `name`; `status`, `passed`, `failed` or `skipped`; `durationMs`, a number.
  - With `skipped`, `reason`; with `failed`, `error`, `{ message, stack }`, the stack optional.
- `eventLine(event)` gives the line, with no line break in it whatever the error text holds.
  - It reads nothing outside its own body, so a host sends its text (`eventLine.toString()`) into any realm and calls it there.
  - That is the whole app side the kit ships: no case engine and no `expect` for the app, and no launch code for a browser or Electron, which stays in the framework that needs it.
- `parseEventLine(line)` gives the event, or `null` for a line without the prefix (the program's ordinary output).
  - A line with the prefix that is no valid event (broken JSON, no `id`, a `status` outside the three, a `failed` with no error message) throws `not a valid event line: <line>`.
- `appCases(cases, drive, options)` is the host session, called at the top of a suite or inside a `describe`.
  - `cases` is a list of `{ id, name }`; each becomes one case named `name`, in the list's order.
  - `drive(onLine)` is the host's own async function, called once, when the first of its cases a run selects starts.
    - A run whose `--filter` leaves out every one of them never calls it.
    - It starts the program, calls `onLine(line)` for each line the program prints, and resolves when the program is done.
    - A host reads a child's lines with Node's own `readline`.
    - `drive` bounds its own program: the session ends nothing a `drive` started, so a `drive` that never settles holds the run until the suite's deadline.
    - A program `drive` starts through `start` ends at `start`'s `deadline`, so that deadline bounds the whole session; its default, `SPAWN_DEADLINE`, is shorter than a case's `CASE_DEADLINE`.
  - A `passed` event passes its case, a `failed` one fails it with the event's message and stack, a `skipped` one skips it with the reason.
  - A case settles when its event arrives, so a long session reports as it goes.
  - A case with no event fails when `drive` settles: `no event reported for <id>` when it resolved, the error it rejected with when it rejected.
  - The session adds one last case, `app session`, which fails naming each fault: `event for an unknown id <id>`, `<id> reported twice`, `not a valid event line: <line>`, and the message of the error a rejected `drive` gave.
    - So a rejection after every case reported shows in `app session`.
    - Its faults, a late rejection among them, show only when `app session` runs: a `--filter` that leaves it out shows none.
  - `options.timeout` is each case's `timeout` in milliseconds, under the door's wrap and its limits (§ The kit's runner).
  - A case list with an id twice, or an entry with no string `id` and `name`, throws where `appCases` is called.

```js
const readline = require('node:readline');
const { describe, appCases, start } = require('workkit-core/test');

describe('the popup', () => {
  appCases([{ id: 'opens', name: 'opens' }, { id: 'saves', name: 'saves a note' }], async (onLine) => {
    const app = start(process.execPath, ['app/run-cases.js']);
    readline.createInterface({ input: app.child.stdout }).on('line', onLine);
    const { status } = await app.done;
    if (status !== 0) throw new Error(`app/run-cases.js exited with ${status}`);
  });
});
```

### The budget

- `tests.budget` is the whole minutes a repo allows its root run.
  - It is set in the repo's `.workkit/settings.json`.
  - Or in `~/.workkit/settings.json` under the same key, for every repo that sets none.
- The suite record carries the recorded run's wall time (`workflow/README.md`, the `lib/records.js` entry).
- When a commit's recorded run took longer than the budget, the commit gate prints a line beside its proved line.
  - The line: `test-budget: the root run took Nm, the budget is Mm`.
  - The commit still passes.
- With no budget there is no line.
- The gate's side: `docs/hooks.md` § `safety:commit-gate`.

### The checks

- The supervisor of an `npm test` (the root's or a narrowed one), of `workkit prove` and of a `workkit supervise` run reads its run at every check and judges it by evidence. The CI watch is not read: it waits on GitHub and ends by itself.
- `tests.check` is the minutes between checks, default 5, set where `tests.budget` is.
  - A value that is not a finite number above 0 stops the run before it starts: `detach: tests.check must be a number of minutes above 0 (got <value>)`, exit 2.
- Each check reads two things:
  - output: whether the run's log was written since the last check;
  - work: whether the run's processes used the processor since the last check.
- Within a check the processes are read every 5 seconds at most, and at least 4 times, so a child that lives a moment is still seen.
  - A process new since the read before counts as work, whatever its time.
  - Otherwise the processor time gained across the check's reads counts once it reaches 1 percent of one processor over the check's length.
  - On Linux a process's time includes the children it has waited for, so a short-lived child's time reaches its parent.
- The run's processes are the command and every process under it by parent, a child in its own session included.
  - The supervisor and its `caffeinate` are never among them.
- A read of the processes that fails puts one line in the log, `detach: could not read the run's processes (<message>), so the checks are off`, and the run goes on to its own end.
- The verdicts:
  - output or work: alive, and nothing happens;
  - neither, two checks in a row: frozen. The log gets the evidence, then the run is ended and exits 124.
  - no output for six checks in a row, with work among them: a look. The run goes on, and the call attached to it prints the evidence and exits 125.
    - A green end of that run still writes its record.
- The evidence is one line per process seen in the check, `detach:   <pid> <seconds>s <command>`, the seconds those it used in the check.
- A frozen log ends `detach: no output and no processor use for <N> minutes, so the run was ended (exit 124)`, under the body's own `<prefix>: exit 143`.
- After a look, the next one is asked after six more checks with no output.
- An `end` file in the run's lock folder is read within a second and ends the run: its log ends `detach: the run was ended on request (exit 143)`, and the run exits 143.
  - Ctrl-C on the call that started the run writes that file, so the whole run ends and the call exits 130 (`workflow/README.md` § `lib/runs.js`).
  - The supervisor answers by an `ending` file in the lock folder while it ends the run. The call that asked (Ctrl-C, `workkit watch --end`) waits 30 seconds for that answer, then for as long as the supervisor lives, so a slow end is never reported as a failed one. A failed end removes `ending` with `end`.
- Ending a run: each of its processes gets a terminate signal, and what still lives 10 seconds later a forced end.
  - A signal the system refuses is passed over, so every other process still gets its own.
  - An ended run exits with its own code once its whole tree is gone, never the code the command's exit would give.
- An end that fails, with the command still alive, records nothing: the log gets `detach: the run could not be ended (<message>), so it goes on`.
  - The `end` file is removed, and the run goes on to its own end. A later end request can try again.
  - The checks stay on, so a frozen run is tried again at its next frozen verdict.
  - With the command itself gone, the log gets the failure as `detach: <message>` (a refused signal: `detach: could not signal <pids> (<message>)`), then the closing line, and the code is recorded as always.
- A busy run is never ended, however long it takes.
- On macOS every supervised run holds the machine awake (`caffeinate -i`), so idle sleep does not pause it.
- On Windows no processor time is read, so there is no frozen and no look.
  - An end there has no terminate signal, only the forced end. It reads the Windows process table (PowerShell from `System32` under `SystemRoot`, never through PATH) and Git Bash's own (`ps -el`), and ends each process of the run once, forced, a suite an `npm test` started inside it included (`endTreeOf` in `workflow/lib/tree.js`).
    - A read that fails, or runs past its 60 seconds, fails the end as above. How it reads, what bounds it and its one known limit are in the mechanics below.
- The mechanics: `workflow/README.md` § `lib/detach.js`.
