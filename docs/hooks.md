# The hooks: what each one does

The behavior detail behind `AGENTS.md` § Hooks, which keeps one line per hook. The rules they enforce live in [`project-state.md`](project-state.md); this file describes how each hook executes them.

Four hooks carry a README of their own beside the script, and it is their deeper home: [`hooks/safety/tree-guard/README.md`](../hooks/safety/tree-guard/README.md), [`hooks/safety/release-taken/README.md`](../hooks/safety/release-taken/README.md), [`hooks/docs/session-guard/README.md`](../hooks/docs/session-guard/README.md), [`hooks/docs/change-tracker/README.md`](../hooks/docs/change-tracker/README.md).

## How they are wired

- Registered in `hooks/hooks.json`, every command routed through `hooks/loader.sh`, so settings reference a hook by `prefix:name` rather than by a path.
- A LOADER-level failure fails open (exit 0). The hook's own exit code passes through untouched, which blocking hooks (exit 2) need.

## Platforms

The hooks run on macOS, on Windows under Git Bash, and on Linux. Where a spelling differs between them the branch is taken once, never in the hook that needs it: in [`hooks/_lib.sh`](../hooks/_lib.sh) for what only a hook asks, and in the engine's [`workflow/lib/platform.sh`](../workflow/lib/platform.sh) for what the engine asks too, which this library then points at under its own `hook_` name:

- `hook_is_macos` / `hook_is_windows` / `hook_is_linux`, over `hook_uname_s`: the platform reading. `$OSTYPE` answers first (the shell sets it, so it costs no fork and needs no PATH) and `uname -s` only for a name that split does not know. The personal hooks carry the same four names and the same shape, so one mechanism spans both sides.
- `hook_sha1`: the one digest. macOS ships `shasum` and no `sha1sum`, a Linux machine often the reverse, and a key computed with a different tool is a different key. Every marker and cache name goes through the same digest, the four markers through `hook_review_marker_path`, `hook_triage_marker_path` (above it) and the suite and qa record paths in the engine's `workflow/lib/suite.sh`, each built by `wk_marker_path`: a skill writes the first two, the engine's npm `script-shell` wrapper (`workflow/script-shell.sh`) the suite marker, and `safety/proof-guard` the qa record (`wk_qa_marker_path`), the tree its touched-test run proved at the qa flip. The same derivation names the two run locks and the TMPDIR fallback logs of the detached suite run and CI watch (`workflow/lib/suite.sh`). A machine with neither tool is refused loudly rather than keyed to an empty string, which would be one marker shared by every repo on it. The engine keys the suite record with the same digest, so the body is `wk_sha1` in `workflow/lib/platform.sh`, beside `wk_marker_path`, the one derivation of a marker's path, and `hook_sha1` is one line pointing at it, the way `hook_jq` points at `wk_jq`.
- `hook_jq`: the CRLF-safe jq. jq on Windows is a native program whose stdout is in text mode, so it writes CRLF and a value read bare carries a `\r` into whatever is compared or written next. The engine reads the same JSON with the same tool, so the body is `wk_jq` in `workflow/lib/platform.sh` and `hook_jq` is one line pointing at it: the strip has one home, and jq's own exit status comes back, so a predicate still answers what it answered. `hook_jq_default <default> <jq args...>` is the same pointer for the read that carries a default: jq writes the values it parsed before it fails on a later one, so a `|| printf <default>` in the substitution hands back that partial answer with the default stuck on the end of it, and the default is taken here only when jq wrote nothing. Three hooks call `wk_jq` by that name instead, sourcing the seam directly: `docs/session`, `docs/session-guard` and `safety/vendor-guard` each promise in their header to source no shared hook helper, so they take the body from its own file rather than through a library they do not load.
- `wk_repo_slug` / `wk_slug_from_remote`: what a repo is CALLED, which is platform-shaped too. git stores a remote exactly as it was typed, so a Windows checkout's origin comes back a native path with backslashes, and a reader that took only a forward slash answered nothing about it. The rule lives once in the engine's [`workflow/lib/slug.sh`](../workflow/lib/slug.sh) (its Node twin is `slugFromRemote` in `workflow/slug.js`), and `safety/release-taken` reaches it by its ENGINE name through this library rather than parsing an origin of its own: a hand-rolled parse beside the one home is drift spelled shorter.
- `hook_file_mtime`: BSD `stat -f` against GNU `stat -c`, each spelling accepted only when its output is digits, since the GNU one prints `?` and exits 0 for the flag it does not mean.
- `docs:checkpoint`'s `date -r <epoch>` against `date -d @<epoch>` chain, and `docs:session`'s date maths done in jq, are the portable form of a clock question.

`hooks/_lib.sh` is the library's entry and keeps the seam, `hook_jq` and the engine sources; it sources its helper groups (the markers, the command-text reads, the manager's reads, the proof read, the PreToolUse notice, the deadline wait, the test-path shapes, the working-diff path list, the `gh issue edit` read, the full-run judgment, the AGENTS.md budget measurement) from [`hooks/lib/`](../hooks/lib/), one file per group, so a hook still sources `_lib.sh` alone.

On Windows the engine's address must be a real symlink: Git Bash answers a plain `ln -s` with a copy unless the MSYS runtime is told otherwise, and a copy of the engine at `~/.claude/workkit` hides the `scripts/` folder beside it, which is what the skills' fallback resolves through. The daily heal sets that flag and, when a link still could not be made, removes the copy and says so rather than leaving a stale engine at the address.

The skills carry no platform-bound command at all: the two that record a marker run [`scripts/review-marker.sh`](../scripts/review-marker.sh) and [`scripts/triage-marker.sh`](../scripts/triage-marker.sh), which source `hooks/_lib.sh` and write exactly the path the guard reads.

One limit is named rather than worked around: `safety:proof-guard`'s deadline walk at the qa flip uses `pgrep`, which Git Bash does not ship, so there it ends the suite process alone instead of its whole tree.

## `workflow:standards`: SessionStart

- Runs the engine's heal in a participating repo, once per repo per day. What the heal writes: `workflow/README.md`. The standard it heals to: the spec § Enforcement.
- Adds the one check that is the hook layer's own: every wired hook resolves, is executable, parses, the pieces they source parse, and the tools they call are present.
- Reports only what it fixed: the heal runs under `QUIET=1`, which is what silences its skips at the source, and the indent and the glyph every remaining line opens with are stripped before the report goes into the session's context. An undecided repo hears one offer and is never written to.
- The same daily run calls `workkit update --auto`, the machine-side upkeep: it updates a schedule a human already installed and installs nothing fresh.
- Above every gate sits the setup pester. A machine with no `~/.local/bin/workkit` is told, every session and in any directory, to have the user run `workkit.sh setup`, a prompt, never an install.

## `docs:state-check`: SessionStart

- Announces open `status:inbox` issues, a non-empty `.workkit/capture.md`, a repo `CLAUDE.md`, and an AGENTS.md that breaks its budget.
- A repo `CLAUDE.md` is announced with the one fix its shape calls for (the spec § Repo docs): pointer only (every non-blank line the bare `@AGENTS.md`) says delete it with `git rm`; content with no `AGENTS.md` beside it says `git mv CLAUDE.md AGENTS.md`; content beside an `AGENTS.md` says merge it by hand. The user-level `~/.claude/CLAUDE.md` is never announced.
- The AGENTS.md announcement covers both halves of that budget: a file over 250 lines, and a file carrying any line over 400 bytes: the density rule, since a markdown paragraph is one source line. It names the rule and says `docs:board-guard` bounces writes until it fits. The limits and the measurement are the ones board-guard reads: `HOOK_AGENTS_MAX_LINES` and `HOOK_AGENTS_MAX_BYTES` in `hooks/_lib.sh`, measured by `hook_agents_budget` in `hooks/lib/agents.sh`.
- It measures in BYTES, pinned with `LC_ALL=C`, the same unit and the same pin board-guard uses.
- The inbox count is cached about 30 minutes per repo, and only silence is cached: triage drains `status:inbox` on GitHub and leaves no local trace, so a non-empty count is asked again every session, and the first session after the drain goes quiet with no help from the skill.

## `docs:session`: SessionStart

- Injects a participating repo's `.workkit/agents/session.md` on every source (the task queue a compacted or restarted session reads first) and warns when it has grown past the light bar.
- Under a `---` rule that keeps them clear of the file's last heading, the injection closes with one line per reader.
- The manager is told to open its first reply in plain words with the state above.
- The owner (who otherwise cannot see that anything survived) is told on the visible channel, a top-level `systemMessage`, that saying "continue" resumes the queue.
- Silent for a header-only or absent file, closing lines and owner line included.
- Participation is a committed `.workkit/settings.json` at a GIT ROOT, with a deliberate `"enabled": false` as the repo's no (read through `wk_settings_declined`, the engine's one home of that spelling). No git toplevel means no repo at all and the hook says nothing: outside a repo the settings file a cwd carries is the MACHINE's own state, which the user profile holds on Windows, where every temp directory sits under it.
- It also names a cloud brief that stopped arriving: the 9am job records the newest published brief's date in `~/.workkit/brief-status.json` (`WORKFLOW_HOME` moves the folder, for this file and the settings file below alike), and past one whole calendar day (UTC) the injection LEADS with one line: the date, the gap, `workkit setup --token` as the fix, and `gh run list --repo <home> --workflow brief.yml` as the check, the slug read from `~/.workkit/settings.json` and the clause left off rather than guessed.
- The marker's OWN age is part of the answer: past the same bar, `checkedAt` older than a whole day swaps the diagnosis for `this machine last checked <date>` (a laptop that was off is not a token that expired) and the check clause rides either wording.
- That half is a FILE read and nothing else. A session start never waits on the network. A marker that is missing, unreadable, or missing either date says nothing at all; the line rides alone in a repo with no session state, and alone it carries no `systemMessage`.
- The one-whole-day bar is `FRESH_DAYS` in `tower/api/lib/history.js`, which asks the same question for the tower's pages. Change both together. What they count diverges on purpose: the tower reads briefs carrying a stats line, the marker counts any `brief: `-titled Discussion.

## `workflow:reload-guard`: SessionStart + UserPromptSubmit

- Stamps the load-time surfaces at session start: `hooks.json` content, plus the `agents/` and `skills/` file list and mtimes.
- Injects one line when they change. Hook-script, skill-body, and engine edits are already live, so only these need `/reload-plugins`.
- Each change nags once.

## `manager:resolver`: PreToolUse (Task/Agent)

- Supplies each crew spawn's model from `hooks/manager/resources/ladder.json` and the live session model. The crew contract: [`agents.md`](agents.md).
- The config is three layers deep-merged, each beating the one before: the ladder (`MANAGER_LADDER` overrides its path), the `manager` block of `~/.workkit/settings.json` (`WORKFLOW_HOME` moves the folder, `MANAGER_USER_SETTINGS` names the file), then the one at the repo's git root. A layer overrides only `mode`, `enabled` and the three `tiers`; `classes` and `ladder` stay global. No git root means no repo layer, since a non-repo directory's settings file is the machine's own.
- A merged `enabled: false` turns this hook and `manager:profile` off; a layer that cannot be read adds nothing.
- Per class: the advisor gets the frontier rung, the scout the fast rung, and the worker and verifier the weaker of the workhorse rung and the session's own, so the crew never outspends the session. Any other agent type passes through untouched.
- `mode: rewrite` emits `updatedInput` carrying the model; `mode: advise` blocks a class spawn not already carrying it, naming the model to re-issue with. The Agent tool's model is an alias enum (`sonnet`, `opus`, `haiku`, `fable`), so the ladder's values are aliases. `MANAGER_DEBUG=1` logs one decision line per spawn to `${TMPDIR:-/tmp}/claude-manager-resolver.log`.

## `manager:spawn-guard`: PreToolUse (Task/Agent)

- Warns (never blocks) when a crew spawn carries a hand-passed `model` param, or when a frontier session spawns the advisor.

## `manager:addon`: SubagentStart (`^workkit:`)

- For a spawn whose `agent_type` is `workkit:<name>`, reads `${WORKFLOW_HOME:-~/.workkit}/agents/<name>.md` and returns its text as `additionalContext`, under a one-line header: `Personal add-on for workkit:<name> (from <path>):`. What an add-on is for and what it cannot change: [`agents.md`](agents.md) § Personal add-ons.
- No file, or a blank one: exit 0 with no output, the normal case. Any other agent type exits 0 the same way, so the matcher is the first filter, not the only one.
- A file that exists but cannot be read: a `manager:addon:` line naming it on stderr and exit 1. SubagentStart cannot block a spawn, so Claude Code shows that line as a hook error notice in the subagent's own transcript and the agent runs as shipped.

## `manager:profile`: UserPromptSubmit

- Injects the manager standing instruction in frontier/workhorse sessions only: delegate to the crew, keep the todo checklist current, announce each spawn.

## `docs:checkpoint`: UserPromptSubmit

- Matches the compaction phrases on every prompt, case-insensitively: `compact` (which carries `compaction` and `/compact`), `context` beside `full`, `low`, `running out` or `window` on the same line (and the spoken order, `running out of context`, `out of context`, `low on context`), `clear the chat`, `clear this chat`, `new chat`, `fresh session`, `start over`.
- A match injects one instruction: run the `workkit:checkpoint` skill before anything else in the turn, then answer the line. What the skill does with the chat is its own home, [`skills/checkpoint/SKILL.md`](../skills/checkpoint/SKILL.md).
- A marker under `${TMPDIR:-/tmp}/claude-checkpoint-marker`, keyed by session id, holds the time of the last fire. The second fire in a session asks for a DELTA instead, naming the time the instruction was last issued, so the second run files only what has been spoken since. A payload with no session id gets the full line and writes no marker.
- Fails open: no `jq`, no prompt, or a payload that does not parse is silence. It never exits 2, so a prompt is never blocked.

## `workflow:feature`: UserPromptSubmit

- Matches an issue-work line on every prompt, case-insensitively, with a curly apostrophe read as a straight one. A STRONG match is `#N` or a queue phrase as whole words; a WEAK match is a bare number.
  - The bare number is 2 to 4 digits bounded by non-alphanumerics. Single digits (`1.2.3`) and digits glued to letters (`a1234b`) stay silent, while a year, a port, a time or a two-digit version part fires.
  - The phrases: `work on`, `work the`, `do issue`, `the issues`, `next issue`, `what next`, `what's next` and `what's left` (each with or without the apostrophe), `continue`, `resume`, `keep going`, `what now`, `next one`, `go now`, `lets do`, `let's do`, `finish up`, `task list`, `the queue`, `the batch`, `open items`, `the board`. A phrase inside a longer word is silent: `framework only`, `presume`, `discontinued`.
- A match injects one instruction: load the `workkit:feature` skill before working the issue. The build procedure itself is the skill's own home, [`skills/feature/SKILL.md`](../skills/feature/SKILL.md).
- A marker under `${TMPDIR:-/tmp}/claude-feature-marker`, keyed by session id, makes every later fire in the session silent: the skill is already in context, and a compaction summary keeps the skills invoked. Only a STRONG match writes it. A weak match injects the line and leaves no marker, so a false fire (`port 8080`) never spends the session's one load and a later `work on #374` still fires. A payload with no session id gets the full line every time and writes no marker.
- Fails open: no `jq`, no prompt, or a payload that does not parse is silence. It never exits 2, so a prompt is never blocked.

## `safety:vendor-guard`: PreToolUse (Edit/Write)

- Blocks edits to generated, vendored, and gitignored files. `_attic/`, `.workkit/` and `.env*` are excepted.

## `safety:commit-gate`: PreToolUse (Bash)

- Blocks `git commit` unless: a green root `npm test` recorded the tree it commits, new source files come with test files, code carries a fresh review marker, any added CHANGELOG entry matches the format, and a commit closing an issue (`Fixes #N`) stages the entry it closes against.
- The hook's entry, `run.sh`, parses the command and classifies what the commit carries (a shell redirect after the clause, `2>&1` or `> out.txt`, is syntax, never a pathspec, the `&` inside one never splits the clause, and one ahead of `git`, its subcommand or a shell's `-c` string never hides it).
- A stage-and-commit compound bounces, except in a repo with no origin. A PreToolUse hook reads the index before the in-command `git add` runs, so it cannot see what the commit will carry. Stage first, then commit.
- A check that stands down says so out loud, one visible line, instead of skipping in silence; the no-origin skip below is the one silent stand-down, by design. Every stand-down of one run arrives in ONE notice, a line each, printed as the gate exits 0; a bounce prints none.
- The record is required only for a commit carrying CODE in a repo whose root declares a `test` script. A docs-only commit, a version-only bump in any `package.json` (exact pins equal to its version may move in lockstep with it), and one in a `.claude-plugin/plugin.json`, root or nested, need none and stand check 5 down.
- A commit whose files are ALL heal bookkeeping stands checks 1 and 2 down; the record is still required. Three arms, each proving its file is exactly the heal's output: the `.workkit/settings.json` version stamp (only `version` differs from HEAD, and never a new file); the DELETION of a linter copy once no workflow in the tree the commit produces still runs it; and a `.github/workflows/checks.yml` whose blob is byte for byte the heal's rewrite of HEAD's file. The copies, the still-runs question and the rewrite are `workflow/changelog/changelog-job.sh`'s, the file the heal runs, so the two cannot disagree. A tool that fails inside an arm (any tool a check runs, `git` exiting past the probe's absent-means-no 1 included) is not a no: the gate blocks naming the arm, the failed command and its stderr, never the review bounce an unknown answer would otherwise read as.
- Check 3 lints the CHANGELOG entries the commit adds through `wk_changelog_lint` (`workflow/lib/changelog.sh`), the rules being `workflow/changelog/changelog.js`'s: every staged `CHANGELOG.md` as the index holds it, the working tree under `-a/--all`, and the repo's own `CHANGELOG.md` for a pathspec commit. The function is the one home of the message as well, and `script-shell.sh` runs it before a root `npm test` starts, so a bad entry stops the run in its first second rather than at the commit after it. With no `node` on PATH the check is skipped.
- Check 5 runs no tests; it reads the record. A green `npm test` at the repo root records the id of the working tree it started on, through npm's `script-shell` (the record's shape and home, and the wrapper that writes it: `workflow/README.md`, the `lib/suite.sh` and `script-shell.sh` rows), and the gate compares it with the tree the commit carries: the REAL index's id (`wk_suite_index_tree`), or under `-a/--all` the index plus every tracked change (`wk_tree_hash -u`), so a commit whose content differs from what ran is not proved. A pathspec commit (`git commit -m x -- <path>`) carrying code bounces outright, since the gate cannot build its tree to compare: stage the files and commit from the index. On a match check 5 stands down in one line. When the record proves the tree on disk and the commit carries another (an untracked file or an unstaged edit it leaves out), the bounce names that gap and its fix (`git add -A`, or stash what the commit leaves out); any other case bounces, naming `npm test` at the repo root as the fix and the log that run writes its output to (`wk_suite_log_path`, `.workkit/suite.log` where git ignores it), and when npm's `script-shell` (read with `npm config get`, compared by physical path with the `script-shell.sh` beside the hook's own engine) is not the kit's wrapper, the bounce says so and names `workkit setup` first; with no npm on PATH that clause is left out. On Windows npm's shell is the built `script-shell.exe` in `~/.workkit` (its path is `wk_script_shell_exe` in the engine's `workflow/lib/platform.sh`, the one setup builds to), which hands the call to the same wrapper under Git Bash, so the comparison there is with that file, and a deleted file is not the kit's wrapper either, so its bounce names `workkit setup` too. A nested package's suite is the root `test` script's job, never the gate's (spec § The proof).
- The gate judges the repo its session directory (the input's `cwd`) stands in, and skips one with no origin (`hook_originless_cwd` in `hooks/lib/commit.sh`, over `hook_repo_has_origin` and `wk_repo_slug`): a scratch or fixture repo is outside the pipeline, so its commit exits 0 and prints nothing, stage-and-commit in one call included, while the bounces that place the commit (a `cd`, `git -C`, `--git-dir`, `--work-tree`, `GIT_DIR`, `GIT_WORK_TREE`, a wrapped commit) still apply. A fixture commit is made from inside the fixture, one Bash call to `cd` and the next to commit, and a brand-new local repo gets the gate the moment it has a remote. A commit made by a script file (`bash file.sh`, a Makefile, a package script) is not seen, since the gate reads the Bash command text; the proved-tree record the ship checks and CI are the backstop.
- A commit the gate cannot PLACE bounces as well: the `pushd`/`popd` spelling of the directory change, which the `cd` test covers too, and a session directory inside no repository at all, a background subagent's steady state, where the gate bounces rather than standing down.
- Check 6 is the proof: every issue the message closes (the same `Fixes/Closes/Resolves #N` parse check 4 uses) must already carry a comment whose line starts `Proof:`. It reads the issue the way `safety:proof-guard` does, names every unproved issue in the bounce, and fails open with one line on the visible stand-down notice when `gh` cannot answer.
- Check 7 is the stage: every OPEN issue of this repo the message names, as `#N` anywhere in it (a trailer, `Refs`, the subject), must be at `status:complete`, the owner's pass. The bounce names each other issue and its stage (`#12 is at status:qa`, or no status label). A closed issue passes, and a message naming no issue passes (a release commit, a small fix found on the way). A pull request passes too, merged or open: `gh` answers a PR number as well, and a `/pull/` url marks it as no work item (a trailer naming one asks no proof either).
  - A `#N` glued to a run that opens with a letter, `_`, `.`, `/`, `-`, `&` or `$` (digits may follow inside it) is not read: `owner/repo2#N` is another repo's, `page#12` a URL fragment, `&#12` an entity, `$#` shell. A run of digits alone opens none, so `#123#456` reads as #123 and #456. One in a code span IS read, since the rule is plain text, not markdown.
  - Checks 6 and 7 share ONE read per named issue (`hook_issue_view` with `state,labels,comments,url`, the answers `hook_view_stage` and `hook_view_has_proof` in `hooks/lib/proof.sh`), run only where a `CHANGELOG.md` marks the repo as in the pipeline, and fail open the same way: one line per issue `gh` could not answer, on the visible stand-down notice.

## `safety:commit-language`: PreToolUse (Bash)

- Bounces commit messages using kill/destroy/dead wording, suggesting the neutral terms.
- Bounces a subject line that is not Conventional Commits, or that carries a version number outside `chore(release)`.
- It reads only real `git ... commit` commands, and only the quoted spans of their message flags (`-m`, `--message`, `-F`, `--file`), so a file named `kill-switch.md` never bounces. With no message span it scans every quoted span, toward gating. The format checks run only on flag spans read from the commit token onward, and merge, revert, fixup and squash subjects pass. Two accepted misses: a bare `git commit -F - <<EOF` body is unquoted, and the `'\''` apostrophe-escape idiom splits a span mid-word. One accepted false positive: the vocabulary scan keeps its whole-command reach, so a flag-adjacent quoted span elsewhere on the line (a `grep -F "..."`) can bounce; reword it, or set `HOOK_DISABLE=1` for that one command.
- It skips a commit whose input `cwd` sits in a repo with no origin, the scratch or fixture repo outside the pipeline, through the same `hook_originless_cwd` the gate asks, printing nothing; with no `cwd` in the input the message is still checked. A brand-new local repo gets the check the moment it has a remote. A commit made by a script file (`bash file.sh`, a Makefile, a package script) is not seen, since the hook reads the Bash command text; the proved-tree record the ship checks and CI are the backstop.

## `safety:release-taken`: PreToolUse (Bash)

- Bounces a release whose version a provider ALREADY has, at the one moment the number is still free to change: the release commit (a real `git ... commit` carrying the `chore(release): <x.y.z>` subject) and `npm publish`. Found afterwards, a taken version costs a second release rather than a different number.
- The release commit asks npm for every package with publish intent, each at its own `package.json` version, and asks `github-release` once for the repo at the subject's version. The publish asks npm only: the GitHub release legitimately precedes it in the ship pipeline. A publish naming its workspaces (`--workspace=<x>`, `--workspace <x>`, `-w <x>`, `-w=<x>`) asks about those members alone, matched by package name or by path from the root, so a family published one member at a time is not bounced by the member published a moment ago. Every publishing clause of a chain counts (a redirect's `&` never splits its clause, and a redirect word before `npm`, the subcommand or a workspace value is skipped, never read as one), and one naming no workspace checks the whole set; a name that matches no member, a quoted name and an empty one stand down out loud, and `--workspaces` keeps the whole set.
- The project is the package.json at the git toplevel for a commit and at the cwd for a publish, plus every `workspaces` member (a literal directory, and `dir/*`; any other glob shape is named on stderr and skipped). Publish intent is the publish plan's rule, and [`workflow/ship/publish-plan.js`](../workflow/ship/publish-plan.js) is its home: the hook asks npm about exactly the packages the plan would not skip, plus a workspaces root that carries the intent itself, since a plain `npm publish` at that root publishes it.
- Providers are sibling scripts under the hook's `providers/`, one contract (`providers/<name> <package-name> <version>`, exit 1 = taken), so a third provider is a file rather than an edit. They run concurrently: a family of ten packages costs one round trip.
- A check that CANNOT be made (offline, unauthenticated, no origin, the tool missing) stands down out loud on stderr and never blocks, the way `safety:proof-guard` does. Cannot tell is not free.
- The escape is the loader's `HOOK_DISABLE=1` and nothing narrower: releasing over a taken version is the owner's deliberate call, not a per-command habit.
- It declares a 30 second timeout in `hooks/hooks.json`, the way `safety:commit-gate` declares its own: `gh release view` takes no timeout flag, so the wiring is what bounds a hung one.
- The hook's own README is its deeper home: [`hooks/safety/release-taken/README.md`](../hooks/safety/release-taken/README.md).

## `safety:tree-guard`: PreToolUse (Bash)

- Blocks the git commands that DISCARD a working tree, since the tree is shared and no agent can see what else is uncommitted in it.
- What it bounces: `git checkout` carrying a pathspec, a `git switch` carrying `--discard-changes` or `--force`, `git restore` without a bare `--staged`, every `git stash` spelling, a forced `git clean`, and `git reset --hard`, found anywhere in a compound (the `&` inside a redirect never splits the clause) and through the prefixes `hook_peel_prefixes` in `hooks/lib/commit.sh` peels, the one list the commit finder, `safety:release-taken` and `safety:proof-guard` read a command word through too.
- A plain branch switch stays legal. Where that line sits is the hook's own README.
- Always on, with one escape: `WORKKIT_ALLOW_DISCARD=1` on the command, the owner's deliberate discard, which the guard stands aside for out loud.

## `safety:issue-guard`: PreToolUse (Bash)

- Blocks a `gh issue create/comment/edit`, a `gh pr create/comment/edit/merge/close`, a `gh api graphql` carrying a discussion or issue mutation, or a `gh api` REST WRITE to an issue or pull endpoint (a read of the same path is untouched), whose outbound text carries a local `.env` value or a token-shaped string.
- Every repo is assumed public (the spec § Issue anatomy).
- It names the key or the kind, never the match.
- Local `.env` values come from the session directory and the repo root above it, the committed example and template variants skipped. Its limits: a mutation is known by its keyword in the command text, so an operation kept in `--input <file>` or a shell variable is not seen, and a REST body on stdin is not a file it can open.

## `safety:proof-guard`: PreToolUse (Bash)

- Blocks `gh issue edit <N> ... --add-label status:complete` and `gh issue close <N>` when one `gh issue view <N> --json comments` finds no comment whose line starts `Proof:`. The rule is the spec's (§ The proof): a missing proof is a hard gate, not a note at ship time.
- Two closes pass, in any quoting: `--reason "not planned"` (`-r` is the same flag) and `--duplicate-of <M>`. Nothing was built on either, so there is nothing to prove. Every other label flip but the qa one below, and every read, is untouched.
- The issue is read from every positional argument (`hook_gh_issue_numbers` in `hooks/lib/gh-edit.sh`): a bare number or `#N` wherever it sits among the flags, and an issue URL, whose repo then drives the read. A flag takes the next word as its value unless gh gives it none, so `--milestone 12 ... 14` reads only #14. A `--repo`/`-R` on the command rides the read in every spelling gh takes, attached ones included, so a cross-repo flip is judged against its own issue.
- Fails open, out loud: no `jq`, no `gh`, a view that exits non-zero, or a `--repo` value it cannot resolve (a variable, a substitution) leaves the command alone and says on stderr that the gate did not run. An unreadable `--repo` is never answered by reading the local repo instead.
- A gated command behind a directory change bounces instead of being judged: a `cd`, `pushd` or `popd` clause ahead of a flip to `status:qa` or `status:complete`, or ahead of a close the gate reads, moves the command into a tree and repo other than the session directory the hook was handed, so the gate cannot place it. The bounce says to run the `cd` in its own Bash call first, then the `gh` command alone. A directory change after the gated clause, or beside a close that proves nothing, is not one. The test is `hook_clause_changes_dir` in `hooks/lib/commit.sh`, the one the git-commit finder asks too, so `safety:commit-gate` (which bounces) and `safety:release-taken` (which stands down) read a directory change the same way.
- Clause boundaries are quote aware, in ONE awk pass: a `;` or a `|` inside a quoted body is data and never splits a clause, so a body cannot cut the clause before its `--add-label`. A redirect's `&` (`2>&1`, `&>file`) never splits its clause either, on the awk path or the fallback, and a redirect word before the issue number, an `--add-label` value or the `--repo`/`-R` value is skipped, never read as one (a bare `>` takes its target with it). Detection reads the quote-stripped copy of each clause; the flag values are read off the clause's raw shell words, where a quoted span stays inside its word, so a flag named in a body is data.
- Two literal tests on the raw command come first, so a `gh issue edit` that cannot be a flip never reaches the walk: the text has to spell `status:complete`, `status:qa` or `gh issue close`, which none of the three commands can do its work without.
- The flip to `status:qa` runs the touched test files itself, once per command and once per tree, from `checks/qa-tests.sh`. It collects the working diff at the repo root (`hook_working_paths` in `hooks/lib/tree.sh`: tracked changes against HEAD and untracked files, the same list `scripts/red-proof.sh` and `scripts/review-covers.sh` read; the committed leg below; deletions excluded), and runs the test-shaped ones (`*.test.*`, `*.spec.*`, `*_test.*`, the `hook_is_test_name` shape in `hooks/lib/paths.sh`) that are `.js`, `.mjs` or `.cjs` with `node --test`. Whether `node --test` can prove a file is read from its TEXT before the run: it runs only when it names `node:test` (a require or an import) or runs itself (`require.main === module`), since a self-running suite reports as one file-level test and a subtest count cannot tell it from an empty file. A red file blocks the flip with the file list and the output's last lines.
- The run happens once per tree, so a batch parking its issues together on one unchanged tree pays for it once. Before the run the hook hashes the working tree (`wk_tree_hash`: untracked files in, ignored ones out), and hashes it again after a green run; only when the two match does it record that hash in its own file beside the suite record (`wk_qa_marker_path`, `${TMPDIR:-/tmp}/claude-qa-marker/<sha1 of the repo root>`), never the suite record itself, since a green root suite and a green touched-test run answer different questions. A green run that changed the tree, whose tree cannot be hashed afterwards, or whose record cannot be written, still passes, and its notice adds one clause saying no record was written and the next flip runs the files again. A later flip whose hash the record holds (`wk_qa_proved`) runs nothing and says so in one notice, followed by the same not-run notes every pass notice carries; any edit makes a new hash and the next flip runs the set again, while an edit undone byte for byte is the recorded tree again. A blocked flip records nothing, a flip with no runnable touched test file records nothing, and a hash that cannot be taken runs the files and records nothing. The record's write and read are the suite record's own bodies (`workflow/lib/suite.sh`), so the two cannot drift.
- A pass is heard as one line of stdout JSON (`hook_pretool_notice` in `hooks/lib/notice.sh`): the files that ran green, or that nothing did, plus three kinds named as not run, never green and never a block: a test-shaped file `node --test` cannot run, a `.js`, `.mjs` or `.cjs` one it cannot prove (a describe or it file for another runner, a module that only exports its cases), and a file under a `test`, `tests` or `__tests__` folder that is not test-shaped (a helper, a fixture, a runner such as `tests/run.js`), which is never executed. The committed leg reads the commits since `origin`'s default branch, else since this branch's upstream; with neither, or when HEAD shares no merge base with it, the notice says those commits were not read. The run's stand-downs speak on the same channel, one notice each: a flip whose `--repo`/`-R` value names another repo than this tree's origin (owner/name, any letter case, read through `wk_repo_slug`) is that repo's issue, so the run does not happen here, while one naming the origin runs it like a flip with no flag, and one it cannot read (a variable, a substitution) says the value went unread and the run did not happen, never that it names another repo; a session outside any git repository, or a PATH with no `node`, stands it down the same way.
- The run has a fixed 540s deadline, under the 600s timeout `hooks/hooks.json` gives this hook, so a hung test bounces instead of being cancelled into an allow. The run has no escape: no env var stands it down. A layer skipped on purpose is recorded in the `Proof:` line for the reader, naming the layer and the reason; it is never handed to the hook.
- The third stage of the same gate is `safety:commit-gate` check 6, the `Fixes #N` trailer. Both answer through `hooks/lib/proof.sh`: this hook calls `hook_issue_has_proof`, and the commit gate reads the same pattern off its shared view through `hook_view_has_proof`. The ship asks the same question outside a hook, in `workflow/ship/ship-items.sh`, the pattern's twin on the shell path, pinned to the helper by `tests/scripts/ship-items.test.js`. The `Proof:` pattern has two more homes, `PROOF_LINE` in `tower/api/server/validate.js` and in the dashboard's `libs/tower/github/writes.js` (pinned by `tests/tower/app/github-writes.test.js`); all four change together.
- The tower Board's own move of a card to Complete applies the same gate off the same read, on both of its write paths; the one difference is that a read the board cannot make refuses the move, where this hook stands down. Detail: `tower/README.md`.

## `safety:spec-guard`: PreToolUse (Bash)

- Matches `gh issue edit <N> ... --add-label status:specced`, the label read whole in every spelling `safety:proof-guard` reads its flips in (`--add-label=status:specced`, a quoted list such as `"priority:high,status:specced"`). A `--remove-label status:specced`, a body that names the label, and every other command pass untouched and read nothing. The clause walk, the issue-number read and the `--repo`/`-R` forwarding are the `hooks/lib/gh-edit.sh` helpers both guards share, so a cross-repo flip is judged against its own issue.
- Reads the issue once, `gh issue view <N> --json body` through `hook_issue_view` in `hooks/lib/proof.sh`, from the session's directory, and takes the `## Spec` section: the text from that heading to the next `## ` heading outside a code fence, or the end, CRLF read as LF. The issue number is read the way proof-guard reads it (`hooks/lib/gh-edit.sh`: every positional, flag-first forms and URLs included).
- Passes when the section's non-blank text is exactly `None needed: small item.`, or when it holds a `### Contract` heading. The Contract's shape (Files, Names, Cases) is the spec's: `docs/project-state.md` § Specs. A `### Contract` outside the Spec section does not count.
- Anything else blocks, a body with no `## Spec` section included, with exit 2 and one line (`block` in [`run.sh`](../hooks/safety/spec-guard/run.sh)) that leads with `BLOCKED this flip`, names the issue, and asks for the Contract's three parts or the small-item line before the flip.
- A flip whose own clause also edits the body (`--body`, `-b`, `--body-file`, `-F`) blocks before any read, with exit 2 and one line (`block_body_edit` in `run.sh`) that leads with `BLOCKED this flip` and says to edit the body in its own command first, since the read would judge the old body.
- A flip behind a directory change bounces instead of being judged, the way proof-guard's does: a `cd`, `pushd` or `popd` clause ahead of it names an issue in a repo the hook cannot place, so the bounce (the shared one in `hooks/lib/gh-edit.sh`) says to run the `cd` in its own Bash call first, or, where the directory resets between calls (a subagent), to flip from a session whose directory is that repo. A directory change after the flip is not one.
- Fails open, out loud: no `gh`, a view that exits non-zero, a body that does not parse, or a `--repo` value it cannot resolve (a variable, a substitution) leaves the command alone with one line on stderr in proof-guard's shape (`skipped` in `run.sh`), naming the issue and the reason and saying the spec gate did not run on this command. An unreadable `--repo` is never answered by reading the local repo instead. No `jq` is silence.
- The tower Board holds the same rule on its drag to Specced, in both move twins (`specOk` in `tower/api/server/validate.js`, restated in the dashboard's `libs/tower/github/writes.js`), with one difference: a body the board cannot read refuses the move, where this hook stands down. The rule's three homes (`sg_spec_ok` in `run.sh` and the two `specOk` copies) change together: `tests/tower/app/github-writes.test.js` pins the two headings and the small-item line in all three, and the bodies in `tests/tower/spec-bodies.js` hold the two `specOk` copies to one answer. Detail: `tower/README.md`.

## `safety:suite-guard`: PreToolUse (Bash)

- Blocks a REPEAT full suite run: the root suite on a tree a green root `npm test` already recorded. The first full run on a tree passes this check, since it is the deliberate one; a second on the same unchanged tree pays the same minutes twice. The rule is the spec's (§ The proof). There is no escape: a changed tree is a new tree, and its first run passes this check (the building hold below still applies).
- A full run is the ROOT suite: `npm test`, `npm run test`, npm's `t` alias and npm's own flags in front of any of them (`npm --silent test`) from a directory whose nearest tested package is the root, and the root's `scripts.test` run directly from anywhere in the repo (`node tests/run.js` here). From inside a nested package that declares its own `test` script, `npm test` is that package's suite and is never judged. `hook_suite_root_run` in `hooks/lib/suite.sh` is the guard's judgment.
- It holds for EVERY class, the manager included, which the `docs/agents.md` rule alone could not reach: that one is written to the worker and the verifier.
- A narrowed run passes untouched, since it is what proves a change: `npm test -- <scope>`, `node --test <file>`, `node tests/<dir>/<name>.test.js`, `npx omega test <scope>`, and the test script carrying an argument. A script whose name merely opens with `test` (`npm run test:unit`) is another script and is never this one. EVERY occurrence is judged, not the first: `npm test -- one && npm test` is a full run.
- Detection is the command TEXT in two passes, with no clause walk. The first is cheap and raw, one awk pass, and nothing else runs for a command that cannot be a suite run; only a command that matched pays for the second, over the heredoc-stripped and quote-stripped copy (`hooks/lib/commit.sh`), so a MENTION of the suite bounces nothing: a commit message, a `gh issue comment`, a heredoc body. Only a full run on the stripped copy pays for the tree hash and the marker read (`wk_tree_hash`, `wk_suite_proved`).
- Blocks a root run while any open issue of the repo is at `status:building`, since the full suite runs once, at the commit, after every item in the tree is parked and passed. The stage label alone holds it, never `agent:working`: an `agent:ok` item keeps that claim through the park until the ship close, so it would hold the ship's own run. The bounce opens `suite-guard: the full suite runs once, at the commit, after every item in the tree is parked and passed;`, names each such issue as `#N (status:building)`, says that work has to finish (tests green, its `Proof:` comment, its own park) and never a relabel, and asks for the narrowest test instead. The read is `hook_issues_building` (`hooks/lib/proof.sh`), one `gh issue list` from the repo root. The proved-tree bounce stays first, since it is local and cheap; this check runs only for a command already judged a root run, and stands down silently in a repo with no origin (no `gh` call at all) and when `gh` or `jq` is missing or `gh` cannot answer.
- The proved-tree bounce names the marker path. Fails open and silent: no `jq`, a session directory inside no git repository, or no root test script leaves the command alone, and no marker or a marker naming another tree leaves it to the building hold.

## `safety:capture-guard`: PreToolUse (Read/Grep/Bash/Edit/Write)

- Gates `.workkit/capture.md` in both directions: the owner's capture surface, whose one sanctioned touch is the triage drain.
- A read of its contents AND a rewrite of it (Edit/Write, `>`, plain `tee`, `sed -i`, `perl -i`) need the marker the `workkit:triage` skill records, stale after 30 minutes.
- An APPEND (`>>`, `tee -a`, or the capture CLI (`wk.sh note`, which names no path)) is blocked with the marker or without, since adding to it is the owner's alone.
- Counting stays open.
- The marker is keyed to the capture file's repo root, or for a file in no repo the `.workkit` folder's parent, so the skill and the guard name one file. A Grep is gated only when its path points at the file or its folder (the file present there) or its glob names it; a repo-wide search stays open. A Bash command is judged by what it runs against the path: a reader (`cat`, `head`, `tail`, `less`, `more`, `grep`, `sed`, `awk`, `bat`), a rewrite or an append, and the capture CLI in command position. A count and a bare mention are neither.
- A substring tripwire, not a sandbox: an interpreter-level write and a case-folded path pass. It fails open on its own errors.

## `docs:board-guard`: PostToolUse (Edit/Write)

- Bounces an `AGENTS.md` write that breaks the spec's budget (§ Repo docs). A `CLAUDE.md` write passes: `docs:state-check` names its fix at session start.
- `AGENTS.md`: the size budget, ≤250 lines, and the DENSITY rule beside it: no line over 400 bytes, since a markdown paragraph is one source line and a file can pass the line count while carrying a book in fourteen of them.
- A density violation lists the first few offenders as `line N (M bytes)` and says to bulletize or move the detail into `docs/<topic>.md`.
- The unit is BYTES, and the measure is pinned to it with `LC_ALL=C`: one-true-awk counts bytes while gawk counts characters under a UTF-8 locale, so an unpinned rule would judge the same file differently on macOS and Linux. One rule, one unit, everywhere it is described.

## `docs:changelog-guard`: PostToolUse (Edit/Write)

- Bounces a CHANGELOG entry that is an essay instead of one short linked paragraph, only entries the write ADDED.
- It lints through `wk_changelog_lint_file` in `workflow/lib/changelog.sh`, the linter resolution `safety:commit-gate` check 3 and `script-shell.sh` share, and stands aside with no `node` on PATH.

## `docs:session-guard`: PostToolUse (Edit/Write)

- Bounces a write that leaves `.workkit/agents/session.md` past either cap: a bullet over 350 chars, or the file over 40 content lines.
- It judges the resulting file, which is why it is POST.
- The same bar `docs:session` warns at; the `workkit:ship` prune is what normally keeps it under.

## `safety:test-reminder`: PostToolUse (Edit/Write)

- Asks at edit time whether a written code file needs a test, with one line in the agent's context: `<path> has no test naming it. Does this change need one? If not, say why in the Proof: line.` The rule it serves is the spec's (§ The proof): whether a change needs a test stays judgment, and a "no" is recorded in the `Proof:` line.
- A code file is the one `safety:commit-gate` check 1 asks about, through the same helper, `hook_is_code_path` in `hooks/lib/paths.sh`: a code extension, outside a test folder and a test name, never a `*.config.*` file or anything under `_attic/`.
- A test NAMES the file when its text carries the basename with its extension as a whole word (`thing.js`, `run.sh`; `index.json` never names `index.js`, nor `webapp.js` `app.js`), or `<parent>/<base>` when more than one repo file shares the basename (a root-level file keeps the basename), or a require or import path ending in the stem (`require('../lib/thing')`). The tests read are the repo's tracked and untracked test-shaped files, the `hook_is_test_path` shape; the first hit ends the search.
- Once per file per session: a marker under `${TMPDIR:-/tmp}/workkit-test-reminder`, keyed by session id, holds each file already asked about. A payload with no session id is asked every time, since silence would hide the question.
- Never a bounce: it always exits 0, and the answer is the agent's. Fails open and silent: no `jq`, no file path, a file that does not exist, a directory inside no git repository, or a file whose repository is not the session directory's (a multi-root session's other repo is left alone).

## `docs:change-tracker`: Stop

- Nags about uncommitted work, keeping the issue true, promoting findings out of `.workkit/`, and unfiled captures.
- Once per change: it stays silent on every stop that follows while nothing has moved.

## `manager:close-guard`: Stop

- Warns (never blocks) when a frontier session did the bulk editing itself, or when worker output ended the turn with no verifier pass.
- The warning is user-visible only and never continues the turn.
- The turn is the transcript tail after the last real prompt, skipping meta entries, tool results, subagent entries, and the system-injected pseudo-prompts, known by shape (the text opens with a `<tag>`) since the IDE's list keeps growing. A tail with no real prompt in it is silence.
