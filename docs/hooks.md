# The hooks: what each one does

The behavior detail behind `AGENTS.md` § Hooks, which keeps one line per hook. The rules they enforce live in [`project-state.md`](project-state.md); this file describes how each hook executes them.

Every hook runs in process, in the hooks module (§ The hooks module); `hooks/hooks.json` wires no shell hook.

## How they are wired

- `hooks/hooks.json` holds one key, its `modules` list, naming the hooks module, `./register.js` (§ The hooks module). Settings and the hooks log name a hook by `prefix:name`, never by a path.
- The shell left under `hooks/` is no hook: `hooks/_lib.sh` and `hooks/lib/*.sh` are the library `scripts/*.sh`, `workflow/prove.sh` and the snapshot entry source (§ Platforms).

### The hooks log

Every hook fire leaves one line in `hooks.log`, which lives in the workkit folder (`~/.workkit`; `WORKFLOW_HOME` moves it, and `wk_hooks_log` in `workflow/lib/platform.sh` is the one spelling of the path). It has one writer: the hooks module writes every fire of a dispatch through `logFires` in `hooks/register.js`, one read and one whole-file write with `$.fs` per dispatch (the line and the cap are `hooks/mods/log.js`'s). The line is tab-separated: `<iso>\t<hook>\t<event>\t<session_id>\t<cwd>\t<verdict>`, the time in UTC, the hook as settings name it (`docs:checkpoint`), the event, session and folder (the module names the classic event, or `agent.spawn`, asks the session for an id the event does not carry, and logs the session's folder from `$.session.cwd()` wherever the input carries no session `cwd`: `agent.spawn`, the Agent tool's `PreToolUse`, whose `cwd` is a subagent's, and the `tool.call` chains), and the verdict `run`, `stood-down` (not opted in, § Where every hook stands down) or `crashed` (a guard that threw: a `tool.call` chain then refuses the call, the `classic.PostToolUse` Bash chain refuses nothing). A `tool.call` guard's fire is logged under `PreToolUse`. `HOOK_DISABLE=1` leaves no line. A log past 10,000 lines is cut to its last 5,000 before the next line is added. A write that fails never stops the hook. The module's write is a read and a whole-file write, since `$.fs` has no append: two sessions writing at the same moment can lose one of their lines, which the log accepts. `workkit log` prints the last 40 lines, `-n <N>` that many, and `--follow` keeps printing new ones.

## Where every hook stands down

A hook runs only when the repo it acts on has opted in, and steps aside silently when the answer is no. One reader answers it, `settingsOptedIn` in `hooks/mods/gate.js` over the repo's `.workkit/settings.json` text; the repos it reads differ by handler (§ The hooks module): the Bash chain asks `optinRepo` in `hooks/mods/optin.js`, by the rules below, and every other handler `folderOpted` in `hooks/mods/guards.js`, the repo holding one folder.

- Opted in: a `.workkit/settings.json` at the repo root that is not `"enabled": false`. A file with no `enabled` key counts as opted in, the legacy format; one that cannot be read counts as declined. The rule is the engine's (`workflow/lib/participation.sh`), and `tests/hooks/twins.test.js` holds the reader to it.
- The repo it acts on:
  - an Edit or Write: the repo holding the file it writes, a linked file read where it really is, walked up from the nearest folder that exists, as spelled, else from that folder's physical path (`~/.claude/settings.json` and a path through `~/.claude/skills` name the dotfiles checkout only behind the link);
  - a Bash command with a `gh` clause that names a repo, by `--repo`/`-R` or by an issue or pull request URL (every clause that names one, read through `ghRepo` in `hooks/mods/gh-edit.js`, so quoted text and a heredoc body never count): each named repo's folder on this machine's roster (`rosterPath` in `hooks/mods/optin.js`, `wk_roster_path`'s rule), and each rostered root counts. A repo the roster does not list, or lists as declined, is not opted in. Those roots decide alone only when every step is a `gh` clause and each names a repo. A `gh` clause naming no repo adds the `cwd`, and in a command holding any other step the roots join those of the rule below, so `git commit && gh pr create --repo <other>` is still judged by its `cwd` too. A `gh` repo value it cannot read (a variable, a substitution) runs the hook, from any `cwd`, so the hook's own read can bounce it;
  - any other Bash command: the repo holding its `cwd`, plus the repo of every folder a `cd` step lands in. The hook runs when any of those repos opted in.
    - A plain `cd <folder>` is followed past the shared prefix peel (`cdStep` in `hooks/mods/command.js`), the folder absolute or relative to where the earlier steps left it. A subshell's `cd` is undone at its `)`. A `cd` in a heredoc body or inside quotes is never a step.
    - A command the walk cannot place runs the hook, so a guard fails closed. The fail-closed forms: any step naming `cd`, `pushd` or `popd` as a word that is not a plain `cd` it can follow (`pushd`, `popd`, `env cd`, a bare `cd`, a flag, `~`, a variable or substitution, a quoted folder, a folder with a space or a trailing redirect, `echo cd`), and a relative `cd` with no `cwd`; git's `-C`, `--git-dir` or `--work-tree`; a `GIT_DIR=`, `GIT_WORK_TREE=` or `CDPATH=` assignment; `eval`; an interpreter's `-c` string (`isInterpreter`); a quoted command word; and a backtick, or a `$(` inside quotes, in a command the cheap test below flags.
    - The `gh` repo read comes first. Then a cheap test spares most commands the walk: it flags `cd`, `pushd` and `popd` matched as whole words (`namesDirChange`), `eval`, a short flag cluster holding `c` or `C`, `--git-dir`, `--work-tree` and the three assignments. A command whose text holds no `--repo`, `-R` or issue or pull request URL, and that the cheap test does not flag, adds no fork, so a hash or a path holding the letters "cd" costs nothing;
  - anything else: the repo holding the input's `cwd`. A payload with no `cwd`, and a `cwd` outside every repo, stand down.
- The safety and manager hooks stand down with the rest. Three run everywhere, since they speak to the machine rather than to a repo: `workflow:standards` (its setup reminder; its own gate keeps the heal per repo), `workflow:reload-guard` (the restart notice) and `safety:issue-guard` (the machine's secrets must not leave it, whatever repo a `gh` write names). The guard chains name their one, `safety:issue-guard`, in `hooks/mods/optin.js`; the module names its other two in `hooks/mods/gate.js`.
- `optinRepo` answers `{ root, opted }`: opted when any repo root it found opted in, and opted for a Bash command it cannot place (the fail-closed forms above, and a `gh` repo value it cannot read), so the guards run.

## Platforms

The hooks run on macOS, on Windows under Git Bash, and on Linux. Where a spelling differs between them the branch is taken once, never in the hook that needs it: in [`hooks/_lib.sh`](../hooks/_lib.sh) for what only a hook asks, and in the engine's [`workflow/lib/platform.sh`](../workflow/lib/platform.sh) for what the engine asks too, which this library then points at under its own `hook_` name:

- `hook_is_macos` / `hook_is_windows` / `hook_is_linux`, over `hook_uname_s`: the platform reading. `$OSTYPE` answers first (the shell sets it, so it costs no fork and needs no PATH) and `uname -s` only for a name that split does not know. The dotfiles hooks load these helpers from this lib through `~/.claude/workkit`, so one mechanism spans both sides.
- `hook_sha1`: the one digest. macOS ships `shasum` and no `sha1sum`, a Linux machine often the reverse, and a key computed with a different tool is a different key. Every marker and cache name goes through the same digest, the four markers through `hook_review_marker_path`, `hook_triage_marker_path` (above it) and the suite and package record paths in the engine's `workflow/lib/suite.sh`, each built by `wk_marker_path`: a skill writes the first two, the engine's npm `script-shell` wrapper (`workflow/script-shell.sh`) and `workkit prove` (`workflow/prove.sh`) the suite marker, and the same wrapper the package record (`wk_pkg_marker_path`), the packages a green `npm test` other than the bare root run proved on a tree, which `safety:proof-guard` reads at the qa flip. The same derivation names the two run locks and the TMPDIR fallback logs of the detached suite run and CI watch (`workflow/lib/suite.sh`). A machine with neither tool is refused loudly rather than keyed to an empty string, which would be one marker shared by every repo on it. The engine keys the suite record with the same digest, so the body is `wk_sha1` in `workflow/lib/platform.sh`, beside `wk_marker_path`, the one derivation of a marker's path, and `hook_sha1` is one line pointing at it, the way `hook_jq` points at `wk_jq`.
- `hook_jq`: the CRLF-safe jq. jq on Windows is a native program whose stdout is in text mode, so it writes CRLF and a value read bare carries a `\r` into whatever is compared or written next. The engine reads the same JSON with the same tool, so the body is `wk_jq` in `workflow/lib/platform.sh` and `hook_jq` is one line pointing at it: the strip has one home, and jq's own exit status comes back, so a predicate still answers what it answered. `hook_jq_default <default> <jq args...>` is the same pointer for the read that carries a default: jq writes the values it parsed before it fails on a later one, so a `|| printf <default>` in the substitution hands back that partial answer with the default stuck on the end of it, and the default is taken here only when jq wrote nothing.
- `wk_repo_slug` / `wk_slug_from_remote`: what a repo is CALLED, which is platform-shaped too. git stores a remote exactly as it was typed, so a Windows checkout's origin comes back a native path with backslashes, and a reader that took only a forward slash answered nothing about it. The rule lives once in the engine's [`workflow/lib/slug.sh`](../workflow/lib/slug.sh) (its Node twin is `slugFromRemote` in `workflow/slug.js`), and `safety:release-taken` reads it through `repoSlug` in `hooks/mods/command.js`, over that file's `slugFromRemote`, the module's copy of the Node twin shape for shape, since a hooks module cannot import CommonJS: the three change together.
- `hook_file_mtime`: BSD `stat -f` against GNU `stat -c`, each spelling accepted only when its output is digits, since the GNU one prints `?` and exits 0 for the flag it does not mean.
- `_hook_snapshot_copy` in `hooks/lib/snapshot.sh`: the snapshot copy. macOS clones with `cp -c` and Linux copies with `cp --reflink=auto`, walking into a folder only where it holds a `node_modules`; Windows streams through `tar`. Every platform leaves out `.git` and every `node_modules` (the fill rebuilds those: § `workflow:snapshot`). Given paths after its two folders, it copies only those, each one whose parent folder the destination holds.

`hooks/_lib.sh` is the library's entry and keeps the seam, `hook_jq`, the engine sources and the constants; it sources its helper groups (the markers, the tested package a path sits in, the working-diff path list, the red-proof snapshot) from [`hooks/lib/`](../hooks/lib/), one file per group, so a script still sources `_lib.sh` alone. Its consumers are the scripts the skills and agents run (`scripts/*.sh`), `workflow/prove.sh`, the snapshot entry and the dotfiles hooks; no workkit hook sources it.

- The reads the module's guards share each have one home under `hooks/mods/`: the command text (`command.js`: the strips, the redirect `&` fold, the prefix peel, the step split and its folder walk `stepDirs`, the cd step, the interpreter list, the git-commit finder, the line-by-line test `anyLine`), the `gh` command text (`gh-edit.js`, with the clause walk `ghSteps` and the gh guards' `denyAfter` and `ghSkipped`), the `gh` calls (`gh.js`: `issueView`, `buildingList`), their answers and the `Proof:` pattern (`proof.js`), the settings and the one safe JSON parse (`settings.js`: `parseJson`, `isPlain`), the proved-tree records, the tree hash and the tested package (`suite.js`, with `LONG_RUN_MS`, the ceiling of every long program run), the roster and the path fold (`optin.js`) and the marker paths and the folder rule for what the shell spelled (`markers.js`). Three hook files are shared homes as well: `test-reminder.js` (the code and test path shapes, `CODE_EXT`, the regex escape `escaped`), `changelog-guard.js` (`isChangelog`, `linterPath`) and `change-tracker.js` (`unfiledCount`). A guard on the chains imports from these and the modules above, never from another chain guard.
- The settings read is `settingGet` in `hooks/mods/settings.js`: one key's value from the `.workkit/settings.json` at the git root of a folder when the key is there, else from `~/.workkit/settings.json` (`WORKFLOW_HOME` moves it), else nothing, a literal `false` being a value; `settingsLayers` reads the two files for a folder once. It picks one layer where the manager config (`managerConfig` in `hooks/mods/manager.js`) deep-merges three; `docs:change-tracker`, `safety:capture-guard` and `safety:findings-guard` read `findings.file` through `findingsOn` (true when the setting reads `true`, the one read all three make) and `findingsRoute` (the route sentence the two guards print; the change-tracker's stop instruction words its own: a `status:inbox` issue while on, chat under 🧭 Findings for the owner to answer file or drop while off).

On Windows the engine's address must be a real symlink: Git Bash answers a plain `ln -s` with a copy unless the MSYS runtime is told otherwise, and a copy of the engine at `~/.claude/workkit` hides the `scripts/` folder beside it, which is what the skills' fallback resolves through. The daily heal sets that flag and, when a link still could not be made, removes the copy and says so rather than leaving a stale engine at the address.

The skills carry no platform-bound command at all: the two that record a marker run [`scripts/review-marker.sh`](../scripts/review-marker.sh) and [`scripts/triage-marker.sh`](../scripts/triage-marker.sh), which source `hooks/_lib.sh` and write exactly the path the guard reads.

## The hooks module

Twenty-nine hooks run inside Claude Code itself, in one hooks module: `hooks/hooks.json` names it under `modules` (`./register.js`), and the session loads it once, so dispatching a fire starts no process: a hook runs only the programs it asks for (`git`, `gh`, `node`, an engine entry). [`hooks/register.js`](../hooks/register.js) is the one file that touches `$`, the engine's interface: it gathers each hook's facts (a file's text, a `git` or `gh` answer, a stored marker), gates the hook, logs the fire and answers the event. Most hooks gather in their mods file, every guard through its `<name>Guard` gatherer and the session hooks through `<name>Gather` (`standardsGather`, `sessionGather`, `closeGuardGather`, `changeTrackerGather`); `register.js` hands them the engine calls as plain functions (`ioOf`), so no mods file touches `$`. Each hook's logic is plain functions over plain data in `hooks/mods/<name>.js`, so the logic suites under `tests/hooks/` `require()` them straight, and only the wiring suites need the engine: `tests/mods/*.test.ts`, run by `claude plugin test` (`npm test`'s mod half, AGENTS.md § Tests). An edit to the module reaches a session only on `/reload-plugins`, which is why `workflow:reload-guard` counts its files among the load-time surfaces. The `hooks/` folder carries its own `package.json` (`{ "type": "module" }`), so node reads the module as ESM from the start rather than guessing its type.

The module registers one handler per event, and each runs its hooks in a fixed order:

| Handler | Its hooks, in order |
|---|---|
| `classic.PostToolUse` (Edit/Write) | `docs:board-guard`, `docs:changelog-guard`, `docs:session-guard`, `safety:test-reminder`, `safety:test-bar`: the first block wins, and the hooks after it do not run |
| `classic.SessionStart` | `docs:state-check`, `workflow:standards`, `workflow:reload-guard`'s stamp on a `startup` or `resume` source, then `docs:session`: its context last, and one `$.ui.log` line the owner sees when state carried over |
| `classic.UserPromptSubmit` | `manager:profile`, `workflow:reload-guard`, `docs:checkpoint`, `workflow:feature`, their contexts in that order |
| `classic.SubagentStart` (`^workkit:`) | `manager:addon` |
| `classic.PreToolUse` (Task/Agent) | `manager:spawn-guard`: its warning as `additionalContext`, and one `$.ui.log` line the owner sees |
| `agent.spawn` | `manager:resolver`: `next({ ...e, model })`, or `{ deny }` in advise mode |
| `classic.Stop` | `manager:close-guard`: its warning as one `$.ui.log` line and nothing else, since a Stop context would continue the turn; then `docs:change-tracker`: its nag as the `block`, which continues the turn on purpose |
| `session.end` | none: it deletes every `$.store` key of the ending session |
| `tool.call` (Bash) | `BASH_GUARDS` in `hooks/mods/guards.js`, in this order: `safety:commit-gate`, `safety:commit-language`, `safety:release-taken`, `safety:tree-guard`, `safety:issue-guard`, `safety:proof-guard`, `safety:spec-guard`, `safety:suite-guard`, `safety:capture-guard`, `safety:findings-guard`. The first `{ deny }` refuses the call and the guards after it do not run; every notice goes to Claude as one `context` entry on the result and to the owner as one `$.ui.log` line |
| `tool.call` (Edit/Write) and (Read/Grep) | `FILE_GUARDS` (`safety:vendor-guard`, then `safety:capture-guard`) and `READ_GUARDS` (`safety:capture-guard`) in `hooks/mods/guards.js`, the same runner, event and answers as the Bash chain, logged under `PreToolUse`. The event carries the tool's input flat beside `tool`, `tool_use_id` and `agentId` and no folder, so the cwd is `$.session.cwd()`; an Edit or Write is gated by the repo holding the file, a Read or Grep by the cwd's (`gateDir`). An empty chain passes the event straight on |
| `classic.PostToolUse` (Bash) | `POST_BASH_GUARDS` in `hooks/mods/guards.js`, the same runner: `workflow:snapshot`, its notice as one `additionalContext` entry and one `$.ui.log` line, never a block |

- **The answer.** Every handler calls `next(e)`, so the settings hooks beneath still run, and puts its hooks' contexts ahead of theirs; a block joins any block from beneath. A hook adds one `additionalContext` entry or nothing. The three `tool.call` chains answer `{ deny }` without calling `next`, or `next(e)` with its notice put ahead of the result's `context`. There is no `systemMessage` in a module's answer, which is why spawn-guard's warning, docs:session's owner line and close-guard's warning reach the owner through `$.ui.log`, a dim transcript row.
- **The gate.** `folderOpted(io, dir)` in `hooks/mods/guards.js`: the repo root is `git rev-parse --show-toplevel` run through `$.process.run` from the folder, climbed to the nearest folder that exists for a path not made yet (`rootOf` in `hooks/mods/optin.js`): the event's `cwd` (the written file's folder for an Edit or Write, the file read where it really is, so a linked file names its target's repo and a path not there yet keeps its spelling; the session's folder for `agent.spawn` and the Agent tool's `classic.PreToolUse`), and it opted in when `<root>/.workkit/settings.json` exists and does not hold `"enabled": false` (`settingsOptedIn` in `hooks/mods/gate.js`, the engine's `wk_settings_declined` rule turned round). `workflow:standards` and `workflow:reload-guard` are exempt. The guard chains gate once per call through `runChain` in `hooks/mods/guards.js`: a Bash chain by `optinRepo` (§ Where every hook stands down: the `cd` steps, the `gh` repos through the roster, and a command it cannot place runs the guards), a file chain by `gateDir`, the repo holding the file for an Edit or Write and the session folder's for a Read or Grep; `safety:issue-guard` is the one guard exempt. A hook that stands down says nothing and still leaves its line in the hooks log.
- **The kill switch.** `HOOK_DISABLE=1` in Claude Code's own environment makes every handler pass its event straight on, with no line in the hooks log.
- **Failure.** Each hook inside a handler fails open on its own: an error goes to the debug log and the hook says nothing. The exceptions are a failure of a whole `classic.PostToolUse` (Edit/Write) or `agent.spawn` handler, which refuses (a block, a deny) through its `.catch`, as the mods reference requires of a guard, and the guard chains: a guard that throws ends its chain, leaves `crashed` in the hooks log and is rethrown, so the three `tool.call` chains' `.catch` (`failClosed`) answers `{ deny }` ending with the failure's kind (`throw`, `timeout`), so a crash never lets the call through. The `classic.PostToolUse` (Bash) chain never blocks, and every other handler's `.catch` passes the event on.
- **The parity suite.** Where a rule keeps a shell home beside the module's, because a script still reads it there, `tests/hooks/twins.test.js` runs both on the same inputs and holds them to one answer: the tested package (`hook_test_package_dir`, `testPackageDir` in `hooks/mods/suite.js`), the opt-in read (`wk_settings_declined`, `settingsOptedIn` in `hooks/mods/gate.js`; an unreadable settings file reads opted out on both), the machine folder (`wk_user_dir`, `userDir` in `hooks/mods/log.js` and `workflow/user-dir.js`), the CHANGELOG path test (`wk_is_changelog`, `isChangelog` in `hooks/mods/changelog-guard.js`), the slug rule (`wk_slug_from_remote`, `slugFromRemote` in `workflow/slug.js` and in `hooks/mods/command.js`), the `Proof:` pattern (`workflow/ship/ship-items.sh`, `PROOF_RE` in `hooks/mods/proof.js`) and the hooks log line (`logLine` in `hooks/mods/log.js`). The prompt shape (`hooks/mods/frame.js`) and the manager config and model tier (`hooks/mods/manager.js`) have no shell side.
- **State.** Per-session state lives in `$.store` under `workkit:<session_id>:` (`test-reminder`, `checkpoint`, `feature`, `reload-guard`), and `session.end` drops it. The two caches outlive a session and stay files, written with `$.fs`: the inbox count under `~/.claude/logs/state-check` (`STATE_CHECK_CACHE` moves it) and the heal's daily marker under `~/.claude/logs/workflow-standards` (`WORKFLOW_STANDARDS_CACHE`), each named by the SHA-1 of its folder.
- **The variables it reads**, each through `$.env.get`: `HOOK_DISABLE`, `WORKFLOW_HOME`, `HOME` (`USERPROFILE` where there is none), `TMPDIR` (with `TMP`, `TEMP` and `LOCALAPPDATA`), `WORKFLOW_DIR` (the engine folder, the tests' override), `WORKFLOW_CLAUDE_HOME`, the two cache folders, `RELOAD_GUARD_ROOT` (the folder whose surfaces reload-guard reads, the plugin root by default), `MANAGER_LADDER`, `MANAGER_USER_SETTINGS`, `MANAGER_DEBUG` and `MANAGER_CLOSE_EDITS`. `claude plugin validate .` lists them, with the nine events and every `$` call. Each folder the shell spelled (`TMPDIR`, `/tmp` when unset, `WORKFLOW_HOME` and `HOME`) is read as the folder Git Bash means by it (`shellEnvOf` in `hooks/mods/markers.js`): on Windows `/tmp/<rest>` is the Windows temp folder (the first native `TMP` or `TEMP`, else `%LOCALAPPDATA%\Temp`) plus the rest and `/c/<rest>` is `C:/<rest>`, so a marker a script wrote, and the machine folder's files, are where the module looks.

### `workflow:standards`: SessionStart

- Runs the engine's heal in a participating repo, once per repo per day: `bash workflow/standards.sh <root>` under `QUIET=1`, through `$.process.run` with its ten-minute ceiling, past the heal's worst case. What the heal writes: `workflow/README.md`. The standard it heals to: the spec § Enforcement.
- The heal includes the one check that is the hook layer's own: the hooks module loads in `node`, which pulls in every module under `hooks/mods/`, the shell pieces the scripts source (`hooks/_lib.sh`, `hooks/lib/*.sh`) parse, and the tools both call are present (`workflow/standards/hooks.sh`).
- Reports only what it fixed: `QUIET=1` silences the heal's skips at the source, only the lines opening with the engine's ✓ or ⚠ are kept, and their indent and glyph are stripped before the report goes into the session's context (`engineLines` in `hooks/mods/standards.js`). A heal that exits non-zero is reported as unfinished and retries next session; only a clean one writes the day's marker. An undecided repo hears one offer and is never written to.
- The same daily run calls `workkit update --auto`, the machine-side upkeep, under the same ceiling: it updates a schedule a human already installed, links the `workkit` command and the `gh` shim into an existing `~/.local/bin`, and installs no schedule fresh. It warns about a cloud secret that is missing or stale, and says `identity: not signed in` when the machine has no sign-in.
- Above every gate sits the setup pester. A machine with no `~/.local/bin/workkit` is told, every session and in any directory, to run `workkit.sh setup` itself and hand the user only what it prints for them, a prompt, never an install. Outside a repo the pester is all it says.
- A missing `standards.sh` or unreadable `labels.json` is a broken install, said once, only for a repo whose settings said yes.

### `docs:state-check`: SessionStart

- Announces open `status:inbox` issues, a non-empty `.workkit/capture.md`, a repo `CLAUDE.md`, and an AGENTS.md that breaks its budget.

The user-level `~/.claude/CLAUDE.md` is never announced.

### `docs:checkpoint`: UserPromptSubmit

- Silent on a prompt Claude Code delivered itself, whatever words it holds: one carrying a frame line, or opening with a tag other than `<pasted_content` (`isSystemPrompt` in `hooks/mods/frame.js`, § Platforms). The check runs before any phrase is matched.

The second fire in a session asks for a DELTA instead, naming the time the instruction was last issued, so the second run files only what has been spoken since. ### `workflow:feature`: UserPromptSubmit

- Matches an issue-work line on every prompt, line by line and case-insensitively, with a curly apostrophe read as a straight one. A STRONG match is `#N` or a queue phrase as whole words; a WEAK match is a bare number.
  - The bare number is 2 to 4 digits bounded by non-alphanumerics. Single digits (`1.2.3`) and digits glued to letters (`a1234b`) stay silent, while a year, a port, a time or a two-digit version part fires.
  - The phrases: `work on`, `work the`, `do issue`, `the issues`, `next issue`, `what next`, `what's next` and `what's left` (each with or without the apostrophe), `continue`, `resume`, `keep going`, `what now`, `next one`, `go now`, `lets do`, `let's do`, `finish up`, `task list`, `the queue`, `the batch`, `open items`, `the board`. A phrase inside a longer word is silent: `framework only`, `presume`, `discontinued`.
- Silent on a prompt Claude Code delivered itself (a frame line, or an opening tag other than `<pasted_content`), through `isSystemPrompt` before any match: a task notification saying "work on #12" is not the owner asking.
- A match injects one instruction: load the `workkit:feature` skill before working the issue. The build procedure itself is the skill's own home, [`skills/feature/SKILL.md`](../skills/feature/SKILL.md).
- The session's `workkit:<session_id>:feature` key makes every later fire in the session silent: the skill is already in context, and a compaction summary keeps the skills invoked. Only a STRONG match writes it. A weak match injects the line and leaves no marker, so a false fire (`port 8080`) never spends the session's one load and a later `work on #374` still fires. A payload with no session id gets the full line every time and writes no marker.
- It never blocks a prompt.
- The logic is `featureMatch(prompt)` and `featureContext(prompt, marker)` in `hooks/mods/feature.js`.

### `docs:board-guard`: PostToolUse (Edit/Write)

- Bounces an `AGENTS.md` write that breaks the spec's budget (§ Repo docs). A `CLAUDE.md` write passes: `docs:state-check` names its fix at session start.
- `AGENTS.md`: the size budget, ≤250 lines, and the DENSITY rule beside it: no line over 400 bytes, since a markdown paragraph is one source line and a file can pass the line count while carrying a book in fourteen of them.
- A density violation lists the first few offenders as `line N (M bytes)` and says to bulletize or move the detail into `docs/<topic>.md`. The bounce names the spec file, the plugin's own `docs/project-state.md`.
- The unit is BYTES, each line's UTF-8 length, so the same file is judged alike on every platform. One rule, one unit, everywhere it is described.

- Bounces a CHANGELOG entry that is an essay instead of one short linked paragraph, only entries the write ADDED.

The path is `linterPath` in `hooks/mods/changelog-guard.js`, the one `safety:commit-gate` check 3 runs too (`script-shell.sh` resolves the same file through `workflow/lib/changelog.sh`); `WORKFLOW_DIR` names another engine folder.

### `docs:session-guard`: PostToolUse (Edit/Write)

- Holds `.workkit/agents/session.md` to the shape it exists in: the task queue a compacted or restarted session reads first. Left alone it grows into a journal of what already shipped, whose facts live in the CHANGELOG and the closed issue.
- Bounces a write that leaves it past either cap, both named at once: a bullet (optional indent, then `- ` or `* `) over 350 chars (`MAX_BULLET_CHARS`), named with its length and its first 60 characters; or the file over 40 content lines (`MAX_CONTENT_LINES`): non-blank, not a heading, not a blockquote, not an HTML comment, so the seeded template counts zero. The bounce says to promote anything durable to its issue or the CHANGELOG, delete what has already shipped, and split or trim the oversized bullet.
- It judges the resulting file, which is why it is POST: only the file on disk knows the length an edit leaves behind. A write that shrinks an oversized file but leaves it over still bounces.
- The content-line count and its bar of 40 are also `docs:session`'s, which warns past the same bar at session start: both read `contentLineCount` and `MAX_CONTENT_LINES` in `hooks/mods/session-guard.js`. The `workkit:ship` prune is what normally keeps the file under.

### `safety:test-reminder`: PostToolUse (Edit/Write)

- Asks at edit time whether a written code file needs a test, with one line in the agent's context: `<path> has no test naming it. Does this change need one? If not, say why in the Proof: line.` The rule it serves is the spec's (§ The proof): whether a change needs a test stays judgment, and a "no" is recorded in the `Proof:` line.
- A code file is the one `safety:commit-gate` check 1 asks about: a code extension, outside a test folder and a test name, never a `*.config.*` file or anything under `_attic/`. `isCodePath` in `hooks/mods/test-reminder.js` is its one home, which check 1 reads too.
- A test NAMES the file when its text carries the basename with its extension as a whole word (`thing.js`, `run.sh`; `index.json` never names `index.js`, nor `webapp.js` `app.js`), or `<parent>/<base>` when more than one repo file shares the basename (a root-level file keeps the basename), or a require or import path ending in the stem (`require('../lib/thing')`). The tests read are the repo's tracked and untracked test-shaped files.
- Once per file per session: the session's `workkit:<session_id>:test-reminder` key lists each file already asked about. A payload with no session id is asked every time, since silence would hide the question.

### `safety:test-bar`: PostToolUse (Edit/Write)

- Reads a written test file for the mechanical half of the test bar (`docs/tests.md` § The bar) and adds one line per finding to the agent's context, in line order: `test-bar: <file>:<line> <rule>`. Never a bounce: the write lands and the agent decides.
- A test file is a test path as `safety:test-reminder` reads one: a test name, or any file under a `test`, `tests` or `__tests__` folder (`isTestPath` in `hooks/mods/test-reminder.js`).
- The six rules, read off the text as written, comment lines skipped:
  - `mkTmp`: a `mkdtempSync(` or `tmpdir(` outside the scratch writer (`tests/lib/scratch.js`, or the kit's `workflow/test/lib/scratch.js`);
  - `serial`: a literal `/tmp/<name>` path or a literal port (`localhost:<n>`, `port: <n>`, `.listen(<n>`);
  - `worth`: a case (`test(`, `it(` or a `testUnless(...)(` call) whose every assertion is an `existsSync`, a mode or exec-bit check, or `assert.ok(true)`, named at its first;
  - `source-regex`: a `readFileSync` of a source path (a repo-root anchor or a repo-relative literal, never under `tests`) whose text reaches `assert.match`, inline or through the name it is held under;
  - `sleep`: a `setTimeout` past 1000 ms;
  - `helper-test`: a test-named file under `tests/lib/` (or the kit's `workflow/test/lib/`), named at line 1.
- It shares test-reminder's repo read (`repoRel` in `hooks/register.js`) and so its silences: no file path, a file that does not exist, a directory inside no git repository, or a file whose repository is not the session directory's. It keeps no per-session memory, so every write of the file is read again.
- The logic is `testBarContext({ root, rel, text })` in `hooks/mods/test-bar.js`, empty for a path that is not a test path or a file with no finding.

### `docs:session`: SessionStart

- Injects a participating repo's `.workkit/agents/session.md` on every source (the task queue a compacted or restarted session reads first) and warns when it has grown past the light bar: the `NOTE:` line past 40 content lines, counted by `contentLineCount` and `MAX_CONTENT_LINES` in `hooks/mods/session-guard.js`, the one home `docs:session-guard` reads too.
- Under a `---` rule that keeps them clear of the file's last heading, the injection closes with one line per reader.
- The manager is told to open its first reply in plain words with the state above.
- The owner (who otherwise cannot see that anything survived) hears one `$.ui.log` line, `workkit: state carried over. Say "continue" to resume the session queue`, a dim row in the transcript.
- Silent for a header-only or absent file, closing lines and owner line included.
- Gated by the module's opt-in like the rest. It finds the file from git's toplevel (the module's `git rev-parse --show-toplevel` from the event's `cwd`), so a session opened in a subdirectory still finds it, and a `cwd` git places in no repo says nothing. Every read goes through `$.fs`.

### `manager:close-guard`: Stop

### `safety:commit-gate`: tool.call (Bash)

- Blocks `git commit` unless: a green root `npm test` recorded the tree it commits, new source files come with test files, code carries a fresh review marker, any added CHANGELOG entry matches the format, and a commit closing an issue (`Fixes #N`) stages the entry it closes against. It is the first guard of the Bash chain.
- It reads only a real `git ... commit` (`findGitCommit` in `hooks/mods/command.js`), and walks the commit clause's flags through `commitFlags` in `hooks/mods/commit-gate/checks.js`: `-a`/`--all`, a pathspec, and a shell redirect after the clause (`2>&1`, `> out.txt`), which is syntax, never a pathspec; the `&` inside one never splits the clause, and one ahead of `git`, its subcommand or a shell's `-c` string never hides it.
- A stage-and-commit compound bounces, except in a repo with no origin: the guard reads the index before the in-command `git add` runs, so it cannot see what the commit will carry. Stage first, then commit.
- A check that stands down says so out loud instead of skipping in silence; the no-origin skip below is the one silent stand-down, by design. Every stand-down of one run arrives in ONE notice, a line each, the chain's `context` and `$.ui.log` line; a deny carries none.
- The record is required only for a commit carrying CODE in a repo whose root `package.json` declares a `test` script. A docs-only commit, a version-only bump in any `package.json` (exact pins equal to its version may move in lockstep with it), and one in a `.claude-plugin/plugin.json`, root or nested, need none and stand check 5 down (`isDocPath`, `isManifest` and `versionOnly` in `checks.js`).
- A commit whose files are ALL heal bookkeeping stands checks 1 and 2 down; the record is still required. Three arms (`hooks/mods/commit-gate/heal.js`), each proving its file is exactly the heal's output: the `.workkit/settings.json` version stamp (only `version` differs from HEAD, and never a new file); the DELETION of a linter copy once no workflow in the tree the commit produces still runs it; and a `.github/workflows/checks.yml` whose blob is byte for byte the heal's rewrite of HEAD's file. The copies, the still-runs question and the rewrite are `workflow/changelog/changelog-job.sh`'s, the file the heal runs, reached as a program through its entry, so the two cannot disagree: `copies` (`wk_linter_copies`), `names <file|-> [copy]` (`wk_names_linter_copy`, a mention outside a comment line, asked over the workflows of the tree the commit produces: the index's blobs, or under `-a` the folder's files) and `rewrite <checks.yml> [template]` (the template `wk_checks_template` names by default). A tool that fails inside an arm (any tool a check runs, `git` exiting past the probe's absent-means-no 1 included) is not a no: the gate blocks naming the arm, the failed command and its stderr, never the review bounce an unknown answer would otherwise read as. The verdict writes no file: the rewritten text is hashed through `git hash-object --path=<file> --stdin` (`hashOf`), and the gatherer hands the entry HEAD's file in one scratch folder (`mktemp -d`, through `cygpath -m` on Windows) that `rm -rf` removes. Each run of an arm, and the tree hash, may take ten minutes (`LONG_RUN_MS` in `hooks/mods/suite.js`; the tree hash is its `treeHash`).
- Check 3 lints the CHANGELOG entries the commit adds with `node workflow/changelog/changelog.js <file> --added-only` (`--staged` for the index), the linter `wk_changelog_lint` in `workflow/lib/changelog.sh` runs for `script-shell.sh`, with the same message: every staged `CHANGELOG.md` as the index holds it, the working tree under `-a/--all`, and the repo's own `CHANGELOG.md` for a pathspec commit. `WORKFLOW_DIR` names another engine folder; with no `node` to start, or no linter there, the check is skipped.
- Check 5 runs no tests; it reads the record. A green `npm test` at the repo root records the id of the working tree it started on, through npm's `script-shell`, and a green `workkit prove` records the index's tree (the record's shape and home, and its two writers: `workflow/README.md`, the `lib/suite.sh`, `script-shell.sh` and `prove.sh` rows), and the gate compares it with the tree the commit carries: the REAL index's id (`git write-tree`, `wk_suite_index_tree`'s one command), or under `-a/--all` the index plus every tracked change (`indexTreeId()`, `tree-hash.sh <root> -u`), so a commit whose content differs from what ran is not proved. A pathspec commit (`git commit -m x -- <path>`) carrying code bounces outright, since the gate cannot build its tree to compare: stage the files and commit from the index. On a match check 5 stands down in one line.
  - The record's first line is the tree id; a second line, `ms=<n>`, is the run's wall time in milliseconds, which older records may lack (`suiteRecordMs` in `hooks/mods/suite.js`; the reads match on the first line alone). On a match that time is held against `tests.budget`, the whole minutes the repo allows its root run (`settingGet`, the repo's `.workkit/settings.json` over `~/.workkit/settings.json`): past it, one more line beside the proved one, `test-budget: the root run took Nm, the budget is Mm`, minutes rounded up (`budgetLine` in `hooks/mods/commit-gate/budget.js`), and the commit still passes. No budget, or a record with no `ms=` line, adds nothing.
  - When the record proves the tree on disk (`bash workflow/lib/tree-hash.sh <root>`, `wk_tree_hash`'s one home) and the commit carries another (an untracked file or an unstaged edit it leaves out), the bounce names that gap and its two fixes: `git add -A`, or `workkit prove`, which runs the suite on a copy of the index and records the staged tree, leaving the folder as it is.
  - Any other case bounces, naming `npm test` at the repo root as the fix and the log that run writes its output to (`.workkit/suite.log` where git ignores it, else the `claude-suite.log` marker path, `wk_suite_log_path`'s rule). When npm's `script-shell` (`npm config get script-shell`, compared by physical path with the `workflow/script-shell.sh` beside the module) is not the kit's wrapper, the bounce says so and names `workkit setup` first; with no npm to ask that clause is left out. On Windows (a plugin root on a drive letter) npm's shell is the built `script-shell.exe` setup builds into `~/.workkit` (`wk_script_shell_exe`), which hands the call to the same wrapper under Git Bash, so the comparison there is by physical path with that file (the `scriptShellExe` fact, `<user dir>/script-shell.exe`), and a deleted file is not the kit's wrapper either. A nested package's suite is the root `test` script's job, never the gate's (spec § The proof).
- The gate judges the repo its session directory (the event's `cwd`) stands in, and skips one with no origin (`originless` in `hooks/mods/command.js`): a scratch or fixture repo is outside the pipeline, so its commit passes and says nothing, stage-and-commit in one call included, while the bounces that place the commit (a `cd`, `pushd` or `popd`, `git -C`, `--git-dir`, `--work-tree`, `GIT_DIR`, `GIT_WORK_TREE`, a wrapped commit) still apply. A fixture commit is made from inside the fixture, one Bash call to `cd` and the next to commit, and a brand-new local repo gets the gate the moment it has a remote. A commit made by a script file (`bash file.sh`, a Makefile, a package script) is not seen, since the gate reads the Bash command text; the proved-tree record the ship checks and CI are the backstop.
- A session directory inside no repository reaches the gate only when the opt-in gate lets the command through (§ Where every hook stands down): its `gh` clause names a rostered repo, a `cd` step lands in an opted-in repo, or the command is one it cannot place. The gate's own rules then bounce it: the placing bounces above, else its own bounce for a folder in no repo. A plain commit from there, and one behind a plain `cd` into a repo not opted in, are not gated.
- Check 6 is the proof: every issue the message closes (the same `Fixes/Closes/Resolves #N` parse check 4 uses, `closedIssues` in `checks.js`) must already carry a comment whose line starts `Proof:`. It names every unproved issue in the bounce, and fails open with one line on the stand-down notice when `gh` cannot answer.
- Check 7 is the stage: every OPEN issue of this repo the message names, as `#N` anywhere in it (a trailer, `Refs`, the subject), must be at `status:complete`, the owner's pass. The bounce names each other issue and its stage (`#12 is at status:qa`, or no status label). A closed issue passes, and a message naming no issue passes (a release commit, a small fix found on the way). A pull request passes too, merged or open: `gh` answers a PR number as well, and a `/pull/` url marks it as no work item (a trailer naming one asks no proof either).
  - A `#N` glued to a run that opens with a letter, `_`, `.`, `/`, `-`, `&` or `$` (digits may follow inside it) is not read (`namedIssues`): `owner/repo2#N` is another repo's, `page#12` a URL fragment, `&#12` an entity, `$#` shell. A run of digits alone opens none, so `#123#456` reads as #123 and #456. One in a code span IS read, since the rule is plain text, not markdown.
  - Checks 6 and 7 share ONE read per named issue (`gh issue view <n> --json state,labels,comments,url` at the repo root, `issueView` in `hooks/mods/gh.js`, its answers `viewStage` and `viewHasProof` in `hooks/mods/proof.js`), run only where a `CHANGELOG.md` marks the repo as in the pipeline, and fail open the same way: one line per issue `gh` could not answer, on the stand-down notice.
- The logic is `commitGateVerdict(facts)` in `hooks/mods/commit-gate.js`, the seven checks in this order (1, 2, 3, 4, 6, 7, 5), each deny opening with `BLOCK_PREFIX`. Its facts: `command`, `cwd`, `root` (the git toplevel or null), `originless`, `staged` and `changed` (the index's and the working tree's changed paths), `headTime` (the last commit's epoch seconds or null), `reviewMarker` (`{ mtimeMs }` or null), `suiteRecord` (the record's text or null), `treeId` (the working tree's id), `indexTreeId()` (the tree a `-a/--all` commit carries), `isWindows`, `scriptShell` (npm's raw value, null with no npm to ask), `kitRoot` (the plugin root), `scriptShellExe` (the Windows wrapper's path), `userSettings` (the machine's `settings.json` path, read for `tests.budget` under the repo's), `tmpdir`, `real(path)` (the physical path, null when missing), and the calls `show(rev, path)` (a `HEAD:` or `:` blob, null when git cannot), `run(argv, init)`, `read(path)` (a file's text, null when missing), `issueView(n)`, `lint(path)` (the linter's run over the index unless the commit carries `-a/--all` or a pathspec, null with no node or linter), `jobRewrite(a, b)` (the entry's rewrite of the text `a`) and `hashOf(path, text)` (the blob id). A fact may be a promise, so `commitGateGuard`, the gatherer the chain calls, reads the costly ones (the tree id, the records, npm) only when a check asks; the marker and record paths are `hooks/mods/markers.js`'s, and the marker's time is `$.fs.stat`'s (`stat` on the chain's facts).

### `safety:commit-language`: tool.call (Bash)

- Bounces commit messages using kill/destroy/dead wording, suggesting the neutral terms.
- Bounces a subject line that is not Conventional Commits, or that carries a version number outside `chore(release)`.
- It reads only real `git ... commit` commands (`findGitCommit` in `hooks/mods/command.js`), and only the quoted spans of their message flags (`-m`, `--message`, `-F`, `--file`), so a file named `kill-switch.md` never bounces. With no message span it scans every quoted span, toward gating. The format checks run only on flag spans read from the commit token onward, and merge, revert, fixup and squash subjects pass. Two accepted misses: a bare `git commit -F - <<EOF` body is unquoted, and the `'\''` apostrophe-escape idiom splits a span mid-word. One accepted false positive: the vocabulary scan keeps its whole-command reach, so a flag-adjacent quoted span elsewhere on the line (a `grep -F "..."`) can bounce; reword it.
- It skips a commit whose `cwd` sits in a repo with no origin, the scratch or fixture repo outside the pipeline (`originless` in `hooks/mods/command.js`, asked only once a real commit is found, so a plain command costs no `git` call), printing nothing. A brand-new local repo gets the check the moment it has a remote. A commit made by a script file (`bash file.sh`, a Makefile, a package script) is not seen, since the hook reads the Bash command text; the proved-tree record the ship checks and CI are the backstop.
- The logic is `commitLanguageVerdict({ command, cwd, originless })` in `hooks/mods/commit-language.js`.

### `safety:release-taken`: tool.call (Bash)

- Bounces a release whose version npm or the GitHub release tag ALREADY has, at the one moment the number is still free to change: the release commit (a real `git ... commit` carrying `chore(release): <x.y.z>` where a subject can sit: right after `-m` or `--message`, quote optional, or opening a line, where the `-m "$(cat <<'EOF'` idiom puts it) and `npm publish` (a clause whose command word, past the shared prefix peel, is `npm` and whose first non-option argument is `publish`; a redirect before either is skipped, and `--dry-run` publishes nothing). Found afterwards, a taken version costs a second release rather than a different number.
- The release commit asks npm for every package with publish intent, each at its own `package.json` version, and asks for the GitHub release `v<x.y.z>` once. The publish asks npm only: the GitHub release legitimately precedes it in the ship pipeline. The two strips and the commit finder are `hooks/mods/command.js`'s, so a quoted mention and a heredoc body are data; the version shape is `VERSION_RE` there, the one `safety:commit-language` accepts in a release subject. A quoted `eval "npm publish"` and `sh -c "npm publish"` walk past the npm walk: accepted misses, since neither is how a publish is typed.
- The project is the package.json at the git toplevel for a commit and at the cwd for a publish, plus every `workspaces` member (the array, or the object's `packages`): a literal directory read where it stands, `dir/*` every direct subdirectory of `dir` holding a package.json; any other glob shape, a pattern that matched nothing and a member with no package.json are each named and skipped. Publish intent is the publish plan's rule, and [`workflow/ship/publish-plan.js`](../workflow/ship/publish-plan.js) is its home: npm is asked about exactly the packages the plan would not skip (`"private": false` and a `files` or `publishConfig` key), plus a workspaces root that carries the intent itself.
- A publish naming its workspaces (`--workspace=<x>`, `--workspace <x>`, `-w <x>`, `-w=<x>`, as often as the command repeats them) asks about those members alone, matched by package name or by path from the root (`@fam/core`, `packages/core`, `./packages/core/`); the root is never one. Every publishing clause of a chain counts (a redirect's `&` never splits its clause), one naming no workspace checks the whole set, and `--workspaces` keeps the whole set. A name that matches no member, a quoted name and an empty one (`--workspace=`) stand down.
- The lookups are two programs run from the project root through `$.process.run`, concurrently, each with a 15-second `timeoutMs`: `npm view --no-update-notifier --fetch-retries=0 --fetch-timeout=15000 <name>@<version> version` (taken when the trimmed answer IS the version; an E404 is free; `onRegistry` in `publish-plan.js` asks the same question) and `gh release view v<x.y.z> --json tagName -q .tagName` (taken when the answer is `v<x.y.z>`; "release not found" is free). The bounce names the repo off the origin through `repoSlug`, left off rather than guessed at when the origin names none.
- Cannot tell is not free, and is never silent: a lookup that fails any other way (offline, unauthenticated, the tool missing), a message in a FILE (`-F`, `--file`), a publish behind a `cd`, `pushd` or `popd`, and every member left out are one line each in the chain's notice, and the call goes ahead. A bounce carries those lines first, then one `release-taken: BLOCKED <this release commit|this npm publish>: <npm|github-release> already has ...` line per taken pair, then what to do.
- The escape is `HOOK_DISABLE=1` and nothing narrower: releasing over a taken version is the owner's deliberate call, not a per-command habit.
- The logic is `releaseTrigger` and `releaseTakenVerdict({ command, cwd, packageJson, members, lookups, origin })`, `origin` the remote url the repo's owner/name is read off, in `hooks/mods/release-taken.js`; `releaseTakenGuard` gathers the facts, and only for a command that is a trigger.

### `safety:tree-guard`: tool.call (Bash)

- Blocks the git commands that DISCARD a working tree, since the tree is shared and no agent can see what else is uncommitted in it: a worker reverting its own files with `git checkout -- <files>` once took another agent's uncommitted work in the same files with it. The alternative it names is the scoped one: revert your own changes by reverse-editing your own hunks.
- What it bounces, found anywhere in a compound (the `&` inside a redirect never splits the clause) and through the prefixes `peelPrefixes` in `hooks/mods/command.js` peels (`git -C <path>`, `/usr/bin/git`, `command`, `env`, an unquoted `eval`, `VAR=x`, `(`, `{`, `time`): `git checkout` carrying a pathspec; `git switch` with `--discard-changes` or `-f`/`--force` (a plain switch takes no pathspec and stays legal); `git restore` except `--staged` (`-S`) without `--worktree` (`-W`); every `git stash` but the read-only `list` and `show`; `git clean` forced (`-f`, any cluster carrying `f`, `--force`); `git reset --hard`. A redirection and its target, and everything from an unquoted `#` on, are dropped first.
- The checkout line, drawn toward blocking: `--` anywhere, `-f`/`--force`, `--pathspec-from-file`, an operand that is `.`, `..`, `./…`, `../…`, absolute, `~/…`, carries a glob character, arrived quoted (quoting is how a glob reaches git, and the strip leaves it unreadable) or EXISTS in the session's directory, and more than one operand (`<ref> <path>`) all block. `git checkout main`, `git checkout -`, `git checkout -b new main` stay legal; a branch whose name is also a path in the tree blocks, the case git itself calls ambiguous.
- The accepted misses: a quoted eval body or interpreter string (`eval "git stash"`, `sh -c "git checkout -- ."`), a launcher or control-flow wrapper the peel does not list (`sudo`, `xargs`, `for … do`), and a command substitution. This is a tripwire on the honest reach, not a sandbox.
- Always on, with one escape, the owner's deliberate discard: `WORKKIT_ALLOW_DISCARD=1` as an assignment on the command, read off the quote-stripped text so a mention inside quotes is not one. The guard then stands aside out loud, one notice line (`tree-guard: stood aside for a deliberate discard: ...`), and the call goes on as if the guard were silent.
- The logic is `treeGuardVerdict({ command, cwd, exists })` in `hooks/mods/tree-guard.js`, `exists(rel)` asking whether `<cwd>/<rel>` is there.

### `safety:proof-guard`: tool.call (Bash)

- Blocks `gh issue edit <N> ... --add-label status:complete` and `gh issue close <N>` when one `gh issue view <N> --json comments` finds no comment whose line starts `Proof:`. The rule is the spec's (§ The proof): a missing proof is a hard gate, not a note at ship time.
- Two closes pass, in any quoting: `--reason "not planned"` (`-r` is the same flag) and `--duplicate-of <M>`. Nothing was built on either, so there is nothing to prove. Every other label flip but the qa one below, and every read, is untouched.
- The issue is read from every positional argument (`ghIssueNumbers` in `hooks/mods/gh-edit.js`): a bare number or `#N` wherever it sits among the flags, and an issue URL, whose repo then drives the read. A flag takes the next word as its value unless gh gives it none, so `--milestone 12 ... 14` reads only #14. A `--repo`/`-R` on the command rides the read in every spelling gh takes, attached ones included (`ghRepo`), so a cross-repo flip is judged against its own issue. The view runs from the command's folder with a 600-second `timeoutMs`.
- Fails open, out loud: a view `gh` cannot give (no `gh`, a non-zero exit, an answer that does not parse) leaves the command alone with one notice line saying the gate did not run on it. A block that follows carries those lines first.
- A `--repo` value it cannot resolve (a variable, a substitution, a backtick or a quoted span) blocks the flip to `status:qa`, the flip to `status:complete` and the close, asking for the repo written out as `owner/name`. An unreadable `--repo` is never answered by reading the local repo instead.
- A gated command behind a directory change bounces instead of being judged: a `cd`, `pushd` or `popd` clause ahead of a flip to `status:qa` or `status:complete`, or ahead of a close the gate reads, moves the command into a tree and repo other than the session directory, so the gate cannot place it (`ghBlocksCd`). The bounce says to run the `cd` in its own Bash call first, then the `gh` command alone. A directory change after the gated clause, or beside a close that proves nothing, is not one. The test is `clauseChangesDir` in `hooks/mods/command.js`, the one the git-commit finder asks too.
- Clause boundaries are quote aware, in one pass (`ghClauses`): a `;` or a `|` inside a quoted body is data and never splits a clause, and a redirect's `&` (`2>&1`, `&>file`) never splits its clause either. A redirect word before the issue number, an `--add-label` value or the `--repo`/`-R` value is skipped, never read as one. Detection reads the quote-stripped copy of each clause; the flag values are read off the clause's raw shell words (`ghFlagValues`), where a quoted span stays inside its word, so a flag named in a body is data.
- Two literal tests on the raw command come first (`proofTriggers`), so a `gh issue edit` that cannot be a flip costs nothing: the text has to spell `status:complete`, `status:qa` or `gh issue close`, which none of the three commands can do its work without.
- The flip to `status:qa` reads the records of the touched test files, once per command, in the repo the flip names, and runs no test. A flip with no `--repo`/`-R`, or one naming this tree's origin (owner/name, any letter case, read through `repoSlug`), is checked in the session's repo. One naming another repo is checked in that repo's folder on this machine's roster (`rosterPath` in `hooks/mods/optin.js`, the rule of `wk_roster_path` in `workflow/lib/slug.sh`: the enabled entries of `~/.workkit/.repos.json` whose origin is that slug, any letter case; a declined entry never matches), its base, touched list and records all keyed on that folder. A repo the roster does not hold, or holds as declined, is not opted in: when no repo the command acts on is opted in, the chain's gate stands the guard down (§ Where every hook stands down); when another clause's repo, or the `cwd`, let the command through, the check steps aside with one notice naming the repo. A command whose qa flips span more than one repo (the session's repo counts as one; repos compared by slug, any letter case) blocks before any record is read, naming the repos and asking for one command per repo.
- The touched list is the working diff at the repo root (`git diff HEAD --name-only --no-renames -z` and `git ls-files --others --exclude-standard -z`, the list `hook_working_paths` in `hooks/lib/tree.sh` prints for `scripts/red-proof.sh` and `scripts/review-covers.sh`), the committed leg below, deletions excluded. Every test-shaped path (`*.test.*`, `*.spec.*`, `*_test.*`: `isTestName` in `hooks/mods/test-reminder.js`) counts, whatever its extension. A file's package is the nearest folder at or above it, short of the root, whose `package.json` declares a test script (`testPackageDir` in `hooks/mods/suite.js`, the rule of `hook_test_package_dir`), and a file in no such folder is the root's, `.`. The flip passes when the suite record holds this tree, since a green whole root run covers every package (`suiteProved`), or when the package record holds this tree and names every package that owns a touched test file (`pkgProved`, `wk_pkg_proved`'s read). Each package must hold its own line: the root's `.` never covers a nested package's file, nor a nested package's line the root's. A package with no line blocks the flip, listing each such package with its touched files as a hint, never a ready command: the block asks for that package's own tests, `npm test -- <files>` run from its folder, with the paths in the form its runner takes.
- A repo can declare the packages whose proof is the root run alone: `.workkit/settings.json` takes `"proof": { "rootOnly": ["packages/backend"] }`, folders relative to the repo root, `.` for the root, read once per check. At the qa flip a declared package needs no package record: it is skipped and named in the pass notice as `proved by the root run alone (settings proof.rootOnly): <folder>`, while every other package keeps its line. A value that is not an array of strings (or a settings file that does not parse) gets one notice naming the key, on the pass notice or under the block, and the check runs as if nothing were declared. The declared package's proof is still the root `npm test` before the commit, and `safety:suite-guard`'s building hold is unchanged.
- The guard writes no record; npm's script shell (`workflow/script-shell.sh`) is the one writer of the package record, and the suite record keeps its two writers, the script shell and `workkit prove`. A green bare root `npm test` writes the suite record (§ `safety:suite-guard`). Every other green `test` event, a narrowed run anywhere or a nested package's bare run, writes the package record (`wk_pkg_marker_write`, `${TMPDIR:-/tmp}/claude-package-marker/<sha1 of the repo root>`, named here by `pkgMarkerPath` in `hooks/mods/markers.js`): line 1 the tree id hashed before the run (`wk_tree_hash`: untracked files in, ignored ones out), each following line a package folder relative to the root, `.` for the root. A second package proved on the same tree appends its line, a run on a different tree starts the file over, and a red run, or a run that changed the tree, writes nothing. The guard hashes the working tree the same way before it reads, through `bash workflow/lib/tree-hash.sh <root>` with a 600-second `timeoutMs`, so any edit makes a new tree whose packages are run again, while an edit undone byte for byte is the recorded tree again; a tree that cannot be hashed blocks the flip, naming the cause.
- A pass is heard as one notice: the packages whose records cover the touched test files, or that the whole-suite record does, or that no test file was touched; and a file under a `test`, `tests` or `__tests__` folder that is not test-shaped (a helper, a data file, a runner such as `tests/run.js`), named and never required; and a test file the root owns while the root has no test script, named as not required, since no `npm test` there can record a run. The committed leg reads the commits since `origin`'s default branch, else since this branch's upstream; with neither, or when HEAD shares no merge base with it, the notice says those commits were not read. The check's stand-downs speak on the same channel, one notice each: a repo not opted in on the roster (the case above), or a folder inside no git repository, which speaks only for a command the gate let through from there.
- The check's one skip is the committed `proof.rootOnly` declaration above, which names a package rather than standing the check down; no env var stands it down. What a package's `npm test` proves is that package's runner's to define; a layer skipped on purpose is recorded in the `Proof:` line for the reader, naming the layer and the reason, and is never handed to the guard.
- The third stage of the same gate is `safety:commit-gate` check 6, the `Fixes #N` trailer, which reads the same pattern. The pattern's homes change together: `PROOF_RE` in `hooks/mods/proof.js` (this guard's `viewHasProof`), `workflow/ship/ship-items.sh` (the ship's read), and `PROOF_LINE` in `tower/api/server/validate.js` and the dashboard's `libs/tower/github/writes.js`.
- The tower Board's own move of a card to Complete applies the same gate off the same read, on both of its write paths; the one difference is that a read the board cannot make refuses the move, where this guard stands down. Detail: `tower/README.md`.
- The logic is `proofGuardVerdict({ command, cwd, root, issueView, touched, packages, suiteRecord, packageRecord, treeId, roster, rootOnly })` in `hooks/mods/proof-guard.js`, with `slugOf`, `toplevel` and `baseless` beside them; the qa facts may be async functions of the repo root, and `proofGuardGuard` gathers each only when the qa check asks, once per root.

### `safety:spec-guard`: tool.call (Bash)

- Matches `gh issue edit <N> ... --add-label status:specced`, the label read whole in every spelling `safety:proof-guard` reads its flips in (`--add-label=status:specced`, a quoted list such as `"priority:high,status:specced"`). A `--remove-label status:specced`, a body that names the label, and every other command pass untouched and read nothing. The clause walk, the issue-number read and the `--repo`/`-R` forwarding are the `hooks/mods/gh-edit.js` reads both guards share, so a cross-repo flip is judged against its own issue.
- Reads the issue once, `gh issue view <N> --json body`, from the command's folder, and takes the `## Spec` section: the text from that heading to the next `## ` heading outside a code fence, or the end, CRLF read as LF.

The Contract's shape (Files, Names, Cases) is the spec's: `docs/project-state.md` § Specs. A `### Contract` outside the Spec section does not count.

- The logic is `specGuardVerdict({ command, cwd, issueView })` in `hooks/mods/spec-guard.js`, `issueView(n, repo)` gh's view or null.

### `safety:suite-guard`: tool.call (Bash)

- Blocks a REPEAT full suite run: the root suite on a tree a green root `npm test` already recorded. The first full run on a tree passes this check, since it is the deliberate one; a second on the same unchanged tree pays the same minutes twice. The rule is the spec's (§ The proof). There is no escape: a changed tree is a new tree, and its first run passes this check (the building hold below still applies). `workkit prove` is judged against the record of the INDEX tree (`git write-tree`), the tree it would prove: it bounces when the staged tree is already proved, and passes when only the working tree is, the state the commit gate names it for.
- A full run is the ROOT suite: `npm test`, `npm run test`, npm's `t` alias and npm's own flags in front of any of them (`npm --silent test`) when the folder the run really uses has the root as its nearest tested package; the root's `scripts.test` run directly from anywhere in the repo (`node tests/run.js` here); and `workkit prove` (the command, or the engine's `workkit.sh` by any path). `suiteRootRun` in `hooks/mods/suite-guard.js` is the guard's judgment.
- The run folder starts at the command's `cwd` and follows every `cd` step before the run through the shared walk, `stepDirs` in `hooks/mods/command.js`, the steps split on `;`, `&`, `|` and newlines (a redirect's `&` never splits one). A step is followed only when it is a plain `cd` with one plain folder, after the shared prefix peel (`builtin`, `command`, a leading `\`, `{`, `if`/`then`, a `NAME=v` assignment, a redirect). Any other step that changes folder leaves it unknown: `pushd`, `popd`, `env cd`, `cd -`, a flag, `~`, an expansion, extra arguments. A later `cd` to an absolute folder makes it known again.
- A subshell starts in its parent's folder and its `cd` reverts at the closing paren, so `(cd packages/x; npm test)` is judged in `packages/x` and a run after the paren in the folder before it.
- npm's flags then move it, and only these are known: `--prefix <dir>`, `--prefix=<dir>` and `-C <dir>` name the folder; `-w <name>`, `--workspace <name>` and `--workspace=<name>` name members (a package folder under the run folder by that name, else the package of that name); `-ws`/`--workspaces`; and `-s`/`--silent`, `-q`/`--quiet` and `--if-present`, which move nothing. npm takes any unambiguous abbreviation of a long flag, so every other flag (each `--include*` spelling among them) is judged full, and so is a command carrying any `npm_config_` setting, since npm reads its config from the environment too.
- The run passes when that folder, or every named member, holds its own test script apart from the root's: there `npm test` is that package's suite and is never judged, the rule `workflow/script-shell.sh` applies at run time. `-ws`/`--workspaces` runs only the members' scripts and passes. An unknown folder is judged full, and so are a member it cannot find, a folder outside the repo or in no tested package, a quoted folder (the guard reads the quote-stripped command, where it names no folder), `cd .`, a cd to the root and a cd into a folder with no test script of its own. The packages are every `package.json` git lists below the root, tracked or untracked (`packageFiles`), read only for a command that names an npm run. Each folder is compared with the root where it really is (the Bash facts' `real`), so a `cwd` or a `cd` spelled through a link (`/tmp` for `/private/tmp`) is judged as its target, and a folder that is not there reads as the root's, as `cd` failing did.
- It holds for EVERY class, the manager included, which the `docs/agents.md` rule alone could not reach: that one is written to the worker and the verifier.
- A narrowed run passes untouched: `npm test -- <scope>`, the form that proves a change and writes the package record, and `node --test <file>`, `node tests/<dir>/<name>.test.js`, `npx omega test <scope>` and the test script carrying an argument, none of which is the whole suite. A script whose name merely opens with `test` (`npm run test:unit`) is another script and is never this one. EVERY occurrence is judged, not the first: `npm test -- one && npm test` is a full run.
- Detection is the command TEXT in two passes, with no clause walk. The first reads the raw command; only a command that matched pays for the second, over the heredoc-stripped and quote-stripped copy (`hooks/mods/command.js`), so a MENTION of the suite bounces nothing: a commit message, a `gh issue comment`, a heredoc body. Only a full run on the stripped copy pays for the tree id (`bash workflow/lib/tree-hash.sh <root>`, `wk_tree_hash`) and the record read (`suiteProved`).
- Blocks a root run while any open issue of the repo is at `status:building`, since the full suite runs once, at the commit, after every item in the tree is parked and passed. The stage label alone holds it, never `agent:claimed`: an `agent:ok` item keeps that claim through the park until the ship close, so it would hold the ship's own run. The bounce opens `suite-guard: the full suite runs once, at the commit, after every item in the tree is parked and passed;`, names each such issue as `#N (status:building)`, says that work has to finish (tests green, its `Proof:` comment, its own park) and never a relabel, and asks for the narrowest test instead. The read is one `gh issue list --state open --label status:building` from the repo root (`buildingList` in `hooks/mods/gh.js`, read by `issuesBuilding` in `hooks/mods/proof.js`). The proved-tree bounce stays first, since it is local and cheap; this check runs only for a command already judged a root run, and stands down silently in a repo with no origin (no `gh` call at all). A `gh` that is missing or cannot answer passes the run with one notice saying the building hold did not run.
- The proved-tree bounce names the record's path (`suiteMarkerPath`). A session directory inside no git repository, or no root test script, leaves the command alone silently, and no record or a record naming another tree leaves it to the building hold.
- The logic is `suiteGuardVerdict({ command, cwd, root, testScript, memberDirs, suiteRecord, treeId, building })` in `hooks/mods/suite-guard.js`, `memberDirs` each member package below the root as `{ [folder]: { name, test } }` (its scripts.test or null), with `originless` and `tmpdir` beside them; `memberDirs`, `suiteRecord` and `treeId` may be async functions, which `suiteGuardGuard` hands it, so each is gathered only when the verdict asks.

### `safety:findings-guard`: tool.call (Bash)

- Makes the off default of `findings.file` hold on the ship path: a `gh issue create` whose title starts `review notes from` (the ship's review-notes issue, `skills/ship/SKILL.md` step 3.2b), letter case ignored, bounces while the setting reads anything but `true` (`findingsOn` in `hooks/mods/settings.js`, the repo's `.workkit/settings.json` at the `cwd`'s root over `~/.workkit/settings.json`).
- The bounce names the route (`findingsRoute`), the findings said in chat under 🧭 Findings for the owner to answer file or drop, and the toggle: `findings.file: true` in the repo's `.workkit/settings.json` or `~/.workkit/settings.json` turns filing on (`docs/project-state.md` § How big is one issue).
- The title is read off each create clause's raw shell words (`--title`, `--title=` or `-t`; `ghFlagValues` in `hooks/mods/gh-edit.js`), a heredoc body stripped first, so a body naming the phrase is data. A tripwire, not a sandbox: the title is read in the quoting an agent writes (a plain or quoted word); an escaped or substituted title passes. Two literal tests on the raw command come first (`findingsTriggers`), `gh issue create` and the phrase, so no other command reaches the walk or reads a settings file.
- Everything else passes silently: another title, a title where the phrase is not at the start, a `gh issue comment` or `edit` carrying it, and any create while the setting reads `true`. It runs in an opted-in repo only (§ Where every hook stands down).
- The logic is `findingsGuardVerdict({ command, cwd, route })` in `hooks/mods/findings-guard.js`, `route` the `findingsRoute` answer; the filing route is the on answer.

### `workflow:snapshot`: classic.PostToolUse (Bash)

- Takes the snapshot `scripts/red-proof.sh` runs against. After a command that moves an issue to `status:building` (the claim in `skills/feature/SKILL.md`), it copies the whole repo folder, gitignored files included and `.git` and every `node_modules` left out, to `tree/` in `wk_marker_path claude-red-snapshot <repo root>`, outside the repo.
- Beside the copy it records `head` (the HEAD it was taken at, one sha line), `paths` (the working-change list at that moment, NUL-separated, as `hook_working_paths` prints it) and `issues` (the claimed issue numbers, one a line).
- One snapshot per repo. A claim while it is live adds its issue numbers and leaves the copy alone. A snapshot whose recorded issues have all left `status:building` is stale, and a claim of a number it does not record replaces it; a claim of a number it already records keeps it, stale or not, so a re-claim after a block never swaps in a tree that already carries the edits.
- A release is the flip that ends the work: an add of `status:qa` or `status:complete`, or a `gh issue close`. On one, while a snapshot is there, it asks GitHub which issues in that repo are still building; none left removes the snapshot. A failed GitHub read leaves it, and the stale check catches it at the next claim. A `--remove-label status:building` that adds neither (a block, a re-spec) is not a release: it leaves the snapshot alone and calls no `gh`, as does every command that is neither a claim nor a release.
- The repo is the one the flip names: the session's repo when `--repo`/`-R` is absent or names its origin; another repo's folder on this machine's roster (`rosterPath` in `hooks/mods/optin.js`), as `safety:proof-guard` finds it. A repo off the roster is not opted in: when no repo the command acts on is opted in, the chain's gate stands the hook down (§ Where every hook stands down); when another clause's repo, or the `cwd`, let the command through, it gets one notice and no snapshot. Every clause that claims or releases is one step, run in order, so `gh issue edit 5 ... && gh issue edit 6 ...` records both numbers and a claim in each of two repos snapshots both; the notices of one command are joined into one.
- The module plans and `hooks/lib/snapshot.sh` acts: `snapshotPlan` reads the command, and `snapshotGuard` runs the file's entry, `bash hooks/lib/snapshot.sh take|add|stale|drop <root> [args]` (`hook_snapshot_take`, `hook_snapshot_add`, `hook_snapshot_stale`, `hook_snapshot_drop`, their exit status passed through), from the repo root with a 600-second `timeoutMs`, for the copy. The module writes no snapshot file of its own: the `issues` list is appended by the entry, and read whole by the module for the re-claim test. Sourced, the file defines its functions and runs nothing, as `scripts/red-proof.sh` and `workflow/prove.sh` source it.
- The copy per platform: macOS clones (`cp -c`), which costs almost nothing; Linux copies with `--reflink=auto`; Windows (Git Bash) streams through `tar`. No platform copies a `node_modules` folder: red-proof's copy makes each one a real folder with its entries linked from the live repo, and a workspace link points at the same path inside the copy, so a partial copy of a dependency tree cannot happen. The take builds the whole snapshot (`head`, `paths`, `issues`, then `tree/`) in a sibling folder `<dir>.XXXXXX` and moves it into place last, so two claims racing on one repo never leave a half tree under the final name. A failed take removes the sibling, keeps any snapshot already there, and is a notice naming the error. An old snapshot the take cannot remove is moved aside to a `<dir>.XXXXXX` sibling, named in a notice, and the new one takes its place; siblings older than 10 minutes (a take the timeout cut short) are swept at the next take.
- The fill that turns a folder into a runnable copy is `hook_snapshot_fill <tree> <root> <dest> [rel]...` in `hooks/lib/snapshot.sh`: `<dest>` filled from the folder `<tree>`, only the named paths when any are given, and each `node_modules` the live repo `<root>` holds rebuilt as above, on every platform. Red-proof fills from the snapshot's `tree/`; `workkit prove` fills from the live folder, naming only its gitignored paths, with its root spelled through `hook_snapshot_root`, since the fill compares link targets spelled by `pwd -P`. The copy's worktree is the shared pair both use: `hook_snapshot_worktree_add <root> <copy>` adds a detached worktree of HEAD with nothing checked out, tried three times against a racing add or prune, and `hook_snapshot_worktree_remove <root> <copy>` removes it, deleting the folder and pruning the list when git cannot.
- The other notices, each with no snapshot taken or dropped: a `--repo` value it cannot read (a variable, a substitution or a quoted span); a claim or release naming no `--repo` after a `cd`, `pushd` or `popd` in the same command; a claim from a session folder, or a roster folder, outside any git repository. A live snapshot that cannot take a later claim's numbers is a notice too. Every notice reaches Claude as context and the owner as one `$.ui.log` line.
- Never blocks: the `classic.PostToolUse` (Bash) chain never refuses, a failed copy or GitHub read included.
- The logic is `snapshotPlan({ command, cwd, roster, slugOf, building })` in `hooks/mods/snapshot.js`, answering a list of steps, one per clause that claims or releases: `{ take, issues, repo }`, `{ drop, repo }` or `{ note }` (empty for a command that does neither); `snapshotGuard` runs them in order.
- How red-proof builds its copy from the snapshot (HEAD checked out as its floor), its `--live` mode that swaps the snapshot's versions into the live tree instead, and the limits each accepts: [`agents.md`](agents.md) § Crew sizing.

### `safety:vendor-guard`: tool.call (Edit/Write)

- Blocks edits to generated, vendored, and gitignored files, the mechanical half of "edit the SOURCE, not the output": a `node_modules/`, `vendor/` or `.bundle/` segment, a `dist/` or `build/` directly under a package root (the repo root or a folder holding a `package.json`; a folder that is not there cannot be disproved and counts as one, and deeper in a source tree the folder is source), a lockfile, and a file `git check-ignore` matches in the repo holding its folder.
- `_attic/` is excepted first, so an attic may hold a parked `dist/`; `.env*` and `.workkit/` after the vendor checks, so a `.workkit/` nested in installed output stays blocked.
- It judges the path as the input typed it (a relative one is the session folder's, a backslash read as a slash), never where a link leads: a workspace link `node_modules/p` into `packages/p` is still installed output, and the block names the typed path. The repo for the gitignore check is asked from that path's folder.
- It runs first in the Edit/Write chain, so its deny ends the chain before `safety:capture-guard`.
- The logic is `vendorGuardVerdict({ file, root, ignored, kindOf })` in `hooks/mods/vendor-guard.js`: `root` the repo root or null, `ignored(path)` the `git check-ignore -q` answer, `kindOf(path)` `'file'`, `'dir'` or null off `$.fs.stat`.

### `safety:issue-guard`: tool.call (Bash)

- Blocks a `gh issue create/comment/edit/close/reopen`, a `gh pr create/comment/edit/merge/close`, a `gh api graphql` carrying a discussion or issue mutation, or a `gh api` REST WRITE to an issue or pull endpoint (a read of the same path is untouched), whose outbound text carries a local `.env` value or a token-shaped string.
- Every repo is assumed public (the spec § Issue anatomy), so it runs opted in or not (§ Where every hook stands down).
- It names the key or the kind, never the match.
- The outbound text is the command plus each body file it sends (`--body-file`, `-F`, the field flags, `--input`, and the GraphQL `-F body=@<path>` form), read relative to the `cwd`. Each pattern is tried line by line, as grep read it.
- Local `.env` values come from the session directory and the repo root above it, the committed example and template variants skipped, and an obviously plain value (under 8 characters, one lowercase word, a boolean, a bare number or version, a local URL with no credentials) never matches. Its limits: a mutation is known by its keyword in the command text, so an operation kept in `--input <file>` or a shell variable is not seen, and a REST body on stdin is not a file it can open.
- The `gh` shim (`workflow/identity/gh`) hands the bot's token to `gh` through the environment (`GH_TOKEN`), never in argv, so the command text this guard reads is unchanged and a `ghs_` token written into it is still blocked.
- The logic is `issueGuardVerdict({ command, envFiles, bodies })` in `hooks/mods/issue-guard.js`: `envFiles` `[{ path, text }]`, `bodies` each body file's text by the path the command spells (`bodyPaths`); `isOutbound` decides before any file is read.

### `safety:capture-guard`: tool.call (Bash, Edit/Write, Read/Grep)

- Gates `.workkit/capture.md` in both directions: the owner's capture surface, whose one sanctioned touch is the triage drain. It sits in all three chains.
- A read of its contents AND a rewrite of it (Edit/Write, `>`, plain `tee`, `sed -i`, `perl -i`) need the marker the `workkit:triage` skill records, stale after 30 minutes.
- An APPEND (`>>`, `tee -a`, or the capture CLI (`wk.sh note`, which names no path)) is blocked with the marker or without, since adding to it is the owner's alone.
- Counting stays open.
- The marker is `triageMarkerPath` in `hooks/mods/markers.js`, the file `scripts/triage-marker.sh` writes, keyed to the capture file's repo root, or for a file in no repo the `.workkit` folder's parent; its age is `$.fs.stat`'s mtime against `$.clock.now()`. A `~/`, `$HOME/` or `${HOME}/` path resolves through `HOME`, a relative one against the `cwd`. A Grep is gated only when its path points at the file or its folder (the file present there) or its glob names it; a repo-wide search stays open. A Bash command is judged by what it runs against the path: a reader (`cat`, `head`, `tail`, `less`, `more`, `grep`, `sed`, `awk`, `bat`), a rewrite or an append, and the capture CLI in command position. A count and a bare mention are neither.
- The write and rewrite blocks name where a finding goes instead, by `findings.file` read for the session's `cwd` (`findingsRoute` in `hooks/mods/settings.js`): said in chat under 🧭 Findings while it is off, the default; a `status:inbox` issue when it is on (`docs/project-state.md` § How big is one issue).
- A substring tripwire, not a sandbox: an interpreter-level write and a case-folded path pass.
- The logic is `captureTarget({ tool, input, cwd })` (the path a call reaches and its mode) and `captureGuardVerdict({ tool, input, cwd, root, markerAgeS, route })` in `hooks/mods/capture-guard.js`, `markerAgeS` the marker's age in seconds or null.

### `docs:change-tracker`: classic.Stop

- Nags about uncommitted work, keeping the issue true, promoting findings out of `.workkit/`, and unfiled captures: uncommitted code (a `git status --porcelain` path that is not docs: a `docs/` path, a `*.md`, `CHANGELOG*` or `LICENSE*` name and anything under `.workkit/` are docs, a code extension winning over the `docs/` path), or unfiled entries in `INBOX.md` or `.workkit/capture.md` (a line not a heading, a quote or blank). A clean tree or a docs-only change is silent, and so is a stop the turn already continued (`stop_hook_active`).
- The nag is `hooks/mods/change-tracker/prompt.md`, read from the plugin root (missing, it says so in one `$.ui.log` line and nags nothing), then one FINDINGS line chosen by `findings.file` (`findingsOn`): off, the default, says each finding outside the issue in hand in chat under **🧭 Findings** and files nothing; on, files each as a `status:inbox` issue with the `Filed:` trail. A `PROGRESS.md` still there adds the BOARD line, unfiled entries the INBOX and SCRATCH counts.
- The answer is `{ block }`: the reason line, then the nag. It joins any block from beneath, and continues the turn on purpose.
- Once per change: it fingerprints what it nags about, the status, `git diff HEAD` (`git diff` with no HEAD), each untracked file's text in path order (`git ls-files --others --exclude-standard -z`) and both capture surfaces' text, as one SHA-1, and stays silent on every stop whose fingerprint is the one in `.workkit/agents/.change-tracker`. The fingerprint has no clock in it, so two identical trees fingerprint alike.
- The state file is written whole through `$.fs.write`, one hex line, and only where `.workkit/` is a folder that gitignores it: a repo with no `.workkit/`, or one whose `.workkit/` is not gitignored, keeps no memory and hears the nag every stop. Nothing is written on a stop with nothing to say. It reads git and files only, never `gh`: a network round trip on every stop is latency nobody agreed to pay.
- The logic is `changeTrackerVerdict({ stopHookActive, porcelain, diff, untracked, inbox, capture, previous, prompt })` in `hooks/mods/change-tracker.js`, async for the SHA-1, answering `{ block, context, fingerprint }` or null; `cwd`, `findings`, `board` and `surfaces` (the two surfaces' text) shape the lines after the prompt and the fingerprint. `changeTrackerGather(io, env, e)` gathers them and writes the state file.
